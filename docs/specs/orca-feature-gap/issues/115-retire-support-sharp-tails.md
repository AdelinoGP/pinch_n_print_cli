## Question

Filed by ticket 22, from the 2026-09-01 grilling ruling **Q13**: *"remove field,
hardcode `true`"*, classed rule-out-of-scope — *"Canonical lists it in
`PrintConfig.cpp`'s obsolete-key `ignore` set (rule 3) and froze behaviour at
`g_config_support_sharp_tails = true`; port runs it off."* Flagged for its own
ticket because it is a **geometry change needing its own verification**, unlike
the two sibling severed-plumbing keys (`enforce_support_layers`,
`bridge_no_support`) which were ruled in-session fixes and which packet 265 has
since handled for `enforce_support_layers`.

Verified in-tree (2026-09-02):

- `crates/slicer-ir/src/resolved_config.rs` declares the CLI/typed field
  `support_sharp_tails: bool = true`.
- `crates/slicer-core/src/algos/overhang_annotation.rs` carries the consuming
  params field.
- `resolve_contact_params`
  (`crates/slicer-runtime/src/builtins/support_analysis_producer.rs`) hardcodes
  `support_sharp_tails: false`, under a comment claiming these knobs *"have no
  production config source yet"* — which is false; the field exists and is
  emitted into the config map.

So the port declares `true`, never reads it, and runs the behaviour **off**. Both
the declared default and canonical's frozen behaviour say `true`. Flipping it is
a real geometry change on every model with sharp tails — which is why this is a
ticket and not a one-line edit.

Decide and execute:

1. **Confirm canonical's frozen state** — that the key is genuinely in
   `PrintConfig.cpp`'s obsolete-key `ignore` set and that
   `g_config_support_sharp_tails` is fixed `true` in `libslic3r.h`. Cite by file
   + symbol, never line numbers.
2. **Remove the config key** (the `ResolvedConfig` field and any manifest
   declaration) rather than wiring it — a key canonical no longer honours should
   not be a knob here either. Confirm no back-compat alias is warranted; an old
   profile setting it will fall into `extensions` silently, which is the same
   deliberate break as Q14(b) and ticket 107.
3. **Hardcode the behaviour `true`** at the consumer and delete the misleading
   comment in `resolve_contact_params`.
4. **Verify the geometry change**, which is the substance of this ticket:
   identify which fixtures change output, re-baseline them with measured
   justification, and confirm the change is the sharp-tail behaviour appearing —
   not something else moving.
5. Check whether `bridge_no_support` was fully handled by packet 265 or is still
   severed; the audit grouped the three together and only one has a recorded
   resolution.

Out of scope as a queue key (dead in canonical, rule 3), so it does not change
the queue count.

## Answer

**Resolved 2026-09-10. The key is retired, the behaviour is frozen ON, and the
geometry change is verified by re-baselined tests.** Steps 1–5 of the question,
in order:

### 1. Canonical's frozen state — confirmed against the designated oracle

- `libslic3r.h` (`D:\slicerProject\pinch_n_print_cli\OrcaSlicerDocumented`,
  the map's only oracle, ticket 33): `static constexpr bool
  g_config_support_sharp_tails = true;` under the comment "some global const
  config which user can not change, but developer can".
- `PrintConfig.cpp`'s `PrintConfigDef::handle_legacy` obsolete-key `ignore`
  set lists `support_sharp_tails` verbatim
  (`"support_sharp_tails","support_remove_small_overhangs",
  "support_with_sheath"`, …), and `handle_legacy` discards any ignored key
  before it reaches the pipeline.
- Live canonical consumers of the frozen constant: `SupportMaterial.cpp`
  (`detect_overhangs`'s `layer_id == 0` sharp-tail collection at the
  `g_config_support_sharp_tails &&` bbox test, and the ordinary-layer append in
  the `else if` branch's per-expoly loop) and `TreeSupport.cpp`
  (`config_detect_sharp_tails`, the extend-higher loop, and the
  `is_auto && g_config_support_sharp_tails && !detect_first_sharp_tail_only`
  pass entry).

### 2. The config key is removed, not wired

`crates/slicer-ir/src/resolved_config.rs`: the `support_sharp_tails: bool`
`cli`-declared field is deleted from the `declare_resolved_config!` block, from
`to_config_map`, and from the hand-written `PartialEq` / `Hash` impls. It was
declared in **no** module manifest (the tier table's "ResolvedConfig-only keys"
ruling), so nothing else to delete there. No back-compat alias: an old profile
setting the key falls into `ResolvedConfig::extensions` silently — the same
deliberate break as Q14(b) and ticket 107, and exactly what canonical's own
`ignore` set does to the same profile. The generated docs followed:
`docs/config/host-keys.toml` and `docs/15_config_keys_reference.md` drop the row
(generated by `xtask gen-config-docs`; 59 → 58 host keys), and the doc-lock test
`host_keys_doc_lock_tdd::resolved_config_keys_match_default`
(`crates/slicer-runtime/tests/unit/host_keys_doc_lock_tdd.rs`) drops its
`resolved_bool` arm — it passes, locking the removal.

### 3. The behaviour is hardcoded `true` at the consumer

`crates/slicer-core/src/algos/overhang_annotation.rs` replaces the
`SupportContactParams::support_sharp_tails` field with
`SHARP_TAIL_OBJECT_BOTTOM_EXCEPTION: bool = true`, the developer-only edit point
the frozen canonical constant corresponds to. `resolve_contact_params`
(`crates/slicer-runtime/src/builtins/support_analysis_producer.rs`) no longer
sources the field, and the misleading "these knobs have no production config
source yet" comment (which the key-corrected audit, Q15, proved false for the
field while it existed) is deleted — the replacement comment names exactly what
is frozen and why.

**Scope correction the verification surfaced (and the doc-comment records):**
the removed key gated this port's *object-bottom* exception — the reproduction
of canonical `detect_overhangs`' (`SupportMaterial.cpp`) unconditional
`layer_id == 0` branch (whole slice becomes the overhang set; the per-region
tiny-spot `continue` is never reached), narrowed here to fire only when a region
contour is pointed (three points). Canonical's `g_config_support_sharp_tails`
test proper sits in the **other** branch — the `else if (auto_normal_support)`
ordinary-layer append, which walks `layerm->raw_slices`, classifies a slice as a
sharp tail when it does not `overlaps` the eroded lower layer and its area is
below `area_thresh_well_supported`, appends to `diff_polygons`, and feeds
`sharp_tails_height` for the extend-higher pass
(`SupportMaterial.cpp`, `TreeSupport.cpp`). **That branch is not modelled in
this port** — `detect_support_contacts` has no `raw_slices` equivalent and no
`sharp_tails_height` accumulator — and freezing the constant ON does not change
that: the "Not modelled" section of `detect_support_contacts` now names it
explicitly so the freeze cannot be read as ordinary-layer parity.

### 4. The geometry change — verified by re-baselined tests, both directions

The change, concretely: at the object's bottom layer (`layer_id == raft_layers`,
0 without a raft), a pointed region now yields its whole cross-section as a
support contact even where the ordinary lower-layer offset would consume it,
**and** the tiny-spot filter (`-0.1 × fw` erosion) is suppressed there.
`crates/slicer-core/tests/support_overhang_detection_tdd.rs` (feature-gated
`host-algos`) is the re-baseline:

- `sharp_tails_disabled_by_default_emits_none` →
  `sharp_tails_are_frozen_on_and_emit_at_object_bottom`: the same pointed
  object-bottom input with wholly default params now **emits** a contact. This
  flipped assertion IS the ticket's geometry change, named as such.
- `sharp_tails_add_first_layer_contacts_when_enabled` →
  `sharp_tails_add_object_bottom_contacts` (input unchanged; the knob is gone).
- New: `tiny_spots_are_filtered_out` moved to `layer_id: 1` — the exception
  suppresses the filter at the object bottom, so the tiny-spot fixture had to
  leave it to keep exercising the filter — plus the bracket
  `object_bottom_layer_is_exempt_from_the_tiny_spot_filter`: the same 0.02 mm
  ledge is filtered away one layer up (control) and survives at the object
  bottom (the second half of the geometry change). The fixture guard asserts
  `layer_id == raft_layers` so the pair cannot silently drift.
- `object_bottom_predicates_are_raft_aware`
  (`crates/slicer-runtime/tests/contract/raft_object_bottom_tdd.rs`, in the
  `contract` binary) drops its `support_sharp_tails: true` field pokes —
  unchanged semantics, raft indices still respected (the exception fires at
  `raft_layers`, never on the raft itself).

**Production reach, stated honestly:** the committed contact stream skips
global layer 0 (`layer_index.checked_sub(1)?` in `commit_support_analysis_builtin`'s
per-region closure, `crates/slicer-runtime/src/builtins/support_analysis_producer.rs`)
— layer 0 rests on the bed and has no layer below — so the live prepass produces
a *changed* candidate set only for **raft-bottomed objects** (`layer_id ==
raft_layers > 0` with a pointed object-bottom region): without a raft the
exception's layer never enters detection in production, which is also why every
no-raft fixture in the tree is untouched. Under a raft, the object's bottom
layer previously had its pointed bottoms filtered away (tiny-spot) or eroded
(offset); they now generate contacts, matching canonical's `layer_id == 0`
branch reading `object_config->raft_layers` for the same boundary. The unit +
contract suites above are the proof of the predicate; the production-seam
difference at defaults is confined to that raft case because no other layer
index satisfies the gate.

### 5. `bridge_no_support` — already handled, no new ticket

The audit grouped three keys; all three are now accounted for:

- `enforce_support_layers` — still severed (hardcoded `0` in
  `resolve_contact_params`), but **owned**: draft packet 265 (P13, ticket 20)
  specifies the read, and its `requirements.md` already reports the sharp-tail
  and bridge sourcing as other tickets' work. No new ticket; the packet owns it.
- `bridge_no_support` — **wired, verified in-tree**: the flag is sourced from
  `config.bridge_no_support` (P30, commit `e7404ff1`, 2026-09-05), and the
  commit loop supplies `bridge_polygons` per region from
  `SlicedRegion::bridge_areas` (stamped by `assemble_bridge_areas`
  (`crates/slicer-core/src/algos/prepass_slice.rs`) during `PrePass::Slice`,
  flat-bridge siblings included). The consumer subtracts a 1.2 mm margin when
  the gate is set (`overhang_annotation.rs` step 4). Both default-off.
- `support_sharp_tails` — this ticket.

The sibling Phase-5 area-loss defect found by ticket 98's session is
[150](150-phase5-width-limit-drops-area-instead-of-returning-it-to-base.md),
unrelated to this key.
