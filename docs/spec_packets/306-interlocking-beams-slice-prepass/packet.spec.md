# Packet Contract: 306-interlocking-beams-slice-prepass

## Goal

Make all six `interlocking_*` queue keys drive a real beam-interlocking structure at parity with canonical `InterlockingGenerator::generate_interlocking_structure` (`Feature/Interlocking/InterlockingGenerator.cpp`) and its supporting `VoxelUtils` grid walk — voxelise the shell of each pair of differently-toned regions of one object, keep the cells both occupy, stamp a two-phase beam microstructure into them, and rewrite both regions' slice outlines so each mesh grows beams into the other — delivered as a new host prepass built-in `host:interlocking_beams` on a new host-only stage `PrePass::InterlockingBeams` registered immediately after `PrePass::PaintSegmentation`.

## Scope Boundaries

This packet carries **six** queue keys, not three: the P89 trio (`interlocking_beam`, `interlocking_beam_layer_count`, `interlocking_beam_width`) plus the P90 trio (`interlocking_depth`, `interlocking_orientation`, `interlocking_boundary_avoidance`), because canonical's enabling gate reads four of the six in one condition and `interlocking_depth` — a P90 key — is one of them. A P89-only packet would have to hardcode the rotation, the interface dilation depth and the air-filtering switch inside the kernel and then unpick all three in P90, rewriting every acceptance test; the split buys nothing because the *work* is the voxel generator and the generator needs all six. Wayfinder ticket 97 is therefore dissolved into this packet on the ticket-31 (P24) precedent, not authored separately. One of the six, `interlocking_beam`, is **partially live in this tree under a PnP-invented name** — `mmu_segmented_region_interlocking_beam` (`crates/slicer-ir/src/resolved_config.rs`), a spelling canonical does not have — so the packet renames it to the canonical spelling and preserves its existing Phase-5 suppression read site. The tier table's owner, `new interlocking module`, is **corrected** to a host prepass built-in under ticket 27's re-derive-the-owner rule, for three independently sufficient reasons set out in `requirements.md` §Problem Statement. Rule 4 does not fire: the six keys are scalar parameters of one geometric pass, not an enum selecting between competing algorithms, so no claim is minted. Canonical's `min` / `max` on five of the six are GUI hints and this packet adopts none of them (ticket 113) — canonical's own runtime gate already no-ops every degenerate value. Queue count is unchanged at 409; no supporting non-queue key is carried.
