# Design: 205-editions-xtask-dist-ci

## Controlling Code Paths

- Primary code path: `dist_command` (`xtask/src/dist.rs`) — today a fixed five-phase sequence (build guests → `cargo build -p pnp-cli` → wipe/recreate `target/dist/` → copy `pnp_cli[.exe]` → loop `discover_guests` staging every `GuestTree::Core` guest's `<stem>.wasm` + `<stem>.toml` into `target/dist/modules/<stem>/`). It gains a resolution phase in front and an edition-scoped staging set.
- Secondary: the `Some("dist")` arm of the subcommand match in `xtask/src/main.rs` (today a three-way `args.get(1)` match on `None | Some("--debug") | Some(other)`), and the `USAGE` const in the same file.
- Oracles for the core module set: `build_guests::discover_guests(ws_root) -> (Vec<GuestSpec>, Vec<String>)` and `GuestTree::{Core, TestGuest}` (`xtask/src/build_guests.rs`). `GuestSpec` has seven public fields (`crate_name`, `lib_name`, `manifest_path`, `guest_dir`, `artifact_path`, `tree`, `stage_id`); this packet reads only **`artifact_path`** (for the `.wasm`/`.toml` source paths and the `file_stem` that names the staged directory) and **`tree`** (to filter to `Core`) — the other five are deliberately out of read scope, not absent. `docs/01_system_architecture.md` §"Producing the tier-4 layout" states that `dist` reuses `discover_guests` "so the shipped set tracks the same validated walk"; ADR-0014 is the decision that rejects enumerating guests any other way. Together: no step may hardcode a module list or count.
- Config source: `xtask::editions::load_editions` / `EditionSpec { integrate_all, integrated_modules }` / `EDITIONS_CONFIG_PATH` (`xtask/src/editions.rs`) — **FORWARD-DEP**, created by packet 204, read-only here.
- Neighboring tests/fixtures: the in-file `#[cfg(test)] mod tests` blocks that every other `xtask` module already carries (`build_guests.rs`, `check_deviations.rs`, `compact_specs.rs`, `gen_config_docs.rs`, `test.rs`, `wit_verify.rs`). `xtask/Cargo.toml` declares no `[lib]`, so there is no importable surface and no `xtask/tests/` directory — every new unit test in this packet lives in `#[cfg(test)] mod tests` inside `xtask/src/dist.rs`. Packet 204 established this same constraint for `editions.rs`.
- CI: `.github/workflows/ci.yml` — four jobs today (`fmt`, `docs-guard`, `clippy`, `test`), none of which invokes `cargo xtask dist`. The `test` job is the template for a wasm-capable job: `dtolnay/rust-toolchain@stable` with `targets: wasm32-unknown-unknown`, `Swatinem/rust-cache@v2`, and `taiki-e/install-action@v2` with `tool: wasm-tools`.
- OrcaSlicer comparison: none. Distribution packaging has no canonical C++ equivalent; there is no `OrcaSlicer Reference Obligations` section in `packet.spec.md` or `requirements.md` for that reason.

## Architecture Constraints

- **Disjointness is an invariant, not a convention (ADR-0056 §Consequences).** Integrated modules occupy search tier 5; an external copy of the same `module.id` at any higher tier wins first-root-wins dedup and dispatches over WASM. An edition that stages both is therefore a Developer build wearing an edition's name, distinguishable only by a provenance warning on stderr (packet 201's `external module 'X' shadows integrated module 'X'`). Enforcement must be a hard `Err`/non-zero exit, never a warning, and must be checked **twice**: against the planned staging list (cheap, catches a logic bug) and against the directory names actually present under `target/dist/<edition>/modules/` after copying (catches a leftover from an interrupted run, a non-wiped directory, or a future refactor that stages from a different source). Both calls go through one pure `assert_staging_disjoint`, which is what AC-N1 tests.
- **Set derivation over enumeration (ADR-0014's rejection of hardcoded guest lists; ADR-0057).** The integrated set, the feature list, and the staged set are all derived from two inputs — `dist/editions.toml` and `discover_guests` — and never written down anywhere else. ADR-0057 is explicit that the Hybrid set is "a dist-configuration list, not a hardcoded constant". Consequence for tests: an assertion like "N modules staged" with a literal N is forbidden even though it is true today; assert `external_stage.len() == core_stems.len() - integrated.len()` and `external_stage ∪ integrated == core_stems` instead.
- **`integrate_all = true` means every core module, and is allowed to fail today.** ADR-0057's table row for Integrated reads "every core module" / "none staged". Resolving it to "every module the registry happens to cover" would produce an artifact that calls itself Integrated while staging the remainder externally — exactly the shadowing the previous bullet forbids. So `plan_edition` expands `integrate_all` to every core stem, and `verify_integrated_feature_coverage` then rejects the plan with a named list of modules lacking an `integrated-<name>` feature in `crates/pnp-cli/Cargo.toml`. Until a later packet integrates every core module with its ADR-0056 Decision item 4 parity gate, `--edition integrated` is *expected* to fail with that message. That is the honest behaviour and it is asserted by AC-N2, not worked around.
- **Fail fast, before any build.** Resolution → coverage check → plan-time disjointness check all precede `build_guests::build_command` and `cargo build -p pnp-cli`. A typo in `--edition` must cost a config parse, not a full guest build. AC-N3 asserts both the exit code and that nothing was created.
- **Exit-code convention is pre-existing and must be matched.** Every other xtask subcommand arm exits `2` on an unknown flag after printing `USAGE`, and propagates the command's own status otherwise. `dist` keeps that: `2` for a malformed command line, `1` for a valid command line with an invalid value (unknown edition, coverage failure, disjointness violation, copy failure) — the code `dist_command` already returns for every I/O failure.
- **Guest WASM staleness applies to what `dist` produces, not to what this packet edits.** No path in this packet's change surface (`xtask/src/*.rs`, `crates/pnp-cli/Cargo.toml`, `.github/workflows/ci.yml`, docs) is a guest-WASM input per `CLAUDE.md` §"Guest WASM Staleness", so the canonical staleness bullet does not apply to the edit set. It applies to the *verification*: AC-5 stages real `.wasm` artifacts, so `cargo xtask build-guests --check` must report clean before it runs, and `dist_command` continues to call `build_guests::build_command` itself as its first build phase. A stale guest staged into a dist bundle is indistinguishable from a correct one by inspection.
- No public schema or version constant is bumped, and no existing struct gains a field. `DistPlan` is net-new with no pre-existing literal sites, so the struct-literal blast-radius discipline does not bind and no step carries a literal sweep. `crates/pnp-cli/Cargo.toml`'s new features are additive and off by default, so `cargo build -p pnp-cli` with no `--features` is byte-identical in behaviour to today.
- Coordinate units are not involved (no geometry, no mm↔unit conversion), so the `coord-system` constraint bullet is deliberately absent.

## Code Change Surface

- **Selected approach:** resolve-then-verify-then-build. A pure planning layer converts (`dist/editions.toml`, `discover_guests`) into a `DistPlan`; three pure verification functions gate the plan; `dist_command` becomes a thin executor of the plan. Everything falsifiable is in the pure layer and testable with `cargo test -p xtask` in seconds; only AC-5 pays for a real build.
- **Exact functions, structs, manifests, tests, and files:**
  - `xtask/src/dist.rs` — new pure items, all `pub(crate)` with in-file unit tests:
    - `pub(crate) struct DistArgs { pub edition: Option<String>, pub debug: bool, pub plan_only: bool }` and `pub(crate) fn parse_dist_args(args: &[String]) -> Result<DistArgs, String>`. Accepts `--edition <NAME>`, `--debug`, `--plan` in any order; `Err` on an unknown flag or on `--edition` with no following value. The `main.rs` caller maps `Err` to exit `2` after printing `USAGE`.
    - `pub(crate) struct DistPlan { pub edition: String, pub out_dir: PathBuf, pub cargo_features: Vec<String>, pub integrated: BTreeSet<String>, pub external_stage: Vec<GuestSpec> }` plus `pub(crate) fn external_stems(&self) -> Vec<String>` for the disjointness call and `--plan` output. Keeping `GuestSpec` values (not just stems) in `external_stage` preserves each guest's `artifact_path`, which the copy loop needs; the stems are derived from `artifact_path.file_stem()` exactly as the current loop does.
    - `pub(crate) fn plan_edition(ws_root: &Path, edition: &str) -> Result<DistPlan, String>` — calls `editions::load_editions(ws_root)`, looks up `edition` (on miss: `Err` naming the requested name, `EDITIONS_CONFIG_PATH`, and the sorted available keys), calls `build_guests::discover_guests(ws_root)`, filters `tree == GuestTree::Core`, expands `integrate_all` to every core stem or takes `integrated_modules` verbatim, computes `external_stage` as the complement, and builds `cargo_features` as sorted-deduplicated `format!("integrated-{name}")`. `out_dir = ws_root/target/dist/<edition>`.
    - `pub(crate) fn assert_staging_disjoint(edition: &str, integrated: &BTreeSet<String>, staged: &[String]) -> Result<(), String>` — `Err` naming the first offending module, the edition, and the word `disjoint`, with a one-line pointer to ADR-0056. Pure over `&[String]` deliberately: the post-stage caller reads directory names off disk and hands them in, so the negative test needs no temp directory and `xtask` needs no new dev-dependency.
    - `pub(crate) fn pnp_cli_integrated_features(ws_root: &Path) -> Result<BTreeSet<String>, String>` — parses `crates/pnp-cli/Cargo.toml` with the already-present `toml = "0.8"` dependency and returns every `[features]` key beginning with `integrated-`. **No new xtask dependency.**
    - `pub(crate) fn verify_integrated_feature_coverage(edition: &str, integrated: &BTreeSet<String>, available: &BTreeSet<String>) -> Result<(), String>` — `Err` listing every module lacking `integrated-<name>`, naming the edition and `crates/pnp-cli/Cargo.toml`.
    - `pub(crate) fn preflight_edition(ws_root: &Path, edition: &str) -> Result<DistPlan, String>` — the **single named pre-build gate**, composing `plan_edition` → `verify_integrated_feature_coverage` (against `pnp_cli_integrated_features(ws_root)`) → plan-time `assert_staging_disjoint`. Its existence is what makes the ordering assertable: `dist_command` calls `preflight_edition` exactly once, before any build phase, and AC-N2 asserts positionally that its call site precedes the first `build_guests::build_command` call site in `xtask/src/dist.rs`. Without this composition the ordering could only be asserted by grepping for a function name that is defined in the same file by construction — a check that passes whether or not it is ever called.
    - `pub(crate) fn print_plan(plan: &DistPlan)` — writes `edition\t<name>`, `out_dir\t<path>`, `features\t<comma-joined or empty>`, then one `integrated\t<name>` line per integrated module and one `external\t<name>` line per staged module, all in sorted order. Fixed format; four ACs parse it.
    - `dist_command(ws_root: &Path, args: &DistArgs) -> i32` — signature changes from `(ws_root, debug: bool)`. Order: `preflight_edition` (resolve → coverage → plan-time disjointness) → if `plan_only` print and return `0` → build guests → `cargo build -p pnp-cli` with `--features <comma-list>` appended only when non-empty → wipe/create `out_dir` → copy binary → stage `external_stage` → re-read `out_dir/modules/` directory names → `assert_staging_disjoint(post-stage)` → success line naming the edition and the output path.
    - `#[cfg(test)] mod tests` — the six unit tests named by AC-1..AC-4 and AC-N1..AC-N2. The three `plan_edition` tests run against the real workspace root via `build_guests::workspace_root()`, consistent with how `build_guests.rs`'s own in-file tests reach the tree.
  - `xtask/src/main.rs` — the `Some("dist")` arm delegates to `parse_dist_args(&args[1..])`, exits `2` with `USAGE` on `Err`, otherwise calls `dist::dist_command(&ws, &parsed)`; and `USAGE` gains `dist --edition <NAME>` and `dist --plan` lines. `mod editions;` is added by packet 204, not here — if it is missing, 204 has not landed and this packet cannot proceed.
  - `crates/pnp-cli/Cargo.toml` — `[features]` gains `integrated-<name> = ["slicer-integrated-modules/<name>"]` for every module in the resolved Hybrid set beyond the `integrated-classic-perimeters` packet 203 adds. The exact names are read from `dist/editions.toml` at implementation time and are **not** written into this document (204's profiling may change them).
    - **The inner (registry-crate) feature name is the bare module-directory name.** AC-7's body assertion depends on it: this packet supplies the `integrated-` prefix at the *edition* layer, so a prefixed registry feature would make the delegation `slicer-integrated-modules/integrated-<name>` and AC-7 would go red through no fault of this packet. 201's `design.md` §Open Questions previously left this to the implementer; that `[FWD]` is now **closed to the bare name** precisely because of this dependency. If the registry nonetheless lands prefixed, treat it as a 201 defect and STOP — do not adapt AC-7.
  - `.github/workflows/ci.yml` — new job `dist` with `name: Dist editions`: checkout, `dtolnay/rust-toolchain@stable` with `targets: wasm32-unknown-unknown`, `Swatinem/rust-cache@v2`, `taiki-e/install-action@v2` with `tool: wasm-tools`, then `cargo xtask dist --edition developer --debug`, `cargo xtask dist --edition hybrid --debug`, and a verification step (inline `sh`) that for each edition parses `cargo xtask dist --edition <e> --plan` and fails with a message naming the disjointness invariant if any `integrated` name has a directory under `target/dist/<e>/modules/` or the staged directory count differs from the `external` line count.
  - `docs/01_system_architecture.md`, `README.md` — the doc edits enumerated in `packet.spec.md` §Doc Impact Statement.
- **Rejected alternatives and reasons:**
  - *Keep the output at `target/dist/` and let editions overwrite each other.* Rejected: the CI job builds two editions in one checkout, and `dist` wipes its output root by design (the wipe is what stops deleted modules lingering — `docs/01_system_architecture.md` says so explicitly). Two editions in one root means either no wipe (stale modules ship) or one artifact (nothing to compare). `target/dist/<edition>/` keeps the wipe semantics per edition.
  - *Derive the feature list from `crates/slicer-integrated-modules/Cargo.toml` instead of `crates/pnp-cli/Cargo.toml`.* Rejected: `dist` builds `pnp-cli`, so `--features` must name **pnp-cli** features. Checking coverage against the registry crate would pass while the build fails on an unknown feature — a check that is green exactly when it matters least.
  - *Express editions as cargo feature groups (`hybrid = [...]`) in `crates/pnp-cli/Cargo.toml` and drop `dist/editions.toml`.* Rejected for the reason packet 204 already recorded: a feature group cannot express the **complement** (which modules an edition still stages externally), which is the entire input to the disjointness invariant; and it would put a second source of truth beside 204's locked one.
  - *Enforce disjointness only at plan time.* Rejected: the plan-time check is tautological — `external_stage` is computed as the complement, so it can only fail if the derivation itself is broken. Keeping it is cheap insurance, but the check with real diagnostic value runs against the directory names on disk after copying, where a leftover or a partially-wiped root can actually produce an overlap.
  - *Resolve `integrate_all = true` to "every registry-available module".* Rejected: contradicts ADR-0057's table ("Integrated | every core module | none") and manufactures precisely the silently-shadowed artifact ADR-0056 forbids. Failing loudly with a named list is the correct behaviour while the registry is partial.
  - *Build all three editions in CI.* Rejected on cost and on truth: `--edition integrated` cannot succeed until every core module is integrated, so a CI step for it would be a permanent red or a permanently skipped step. Developer and Hybrid are the two editions that can actually be produced today, and they exercise both branches that matter (empty integrated set, non-empty integrated set with a non-empty complement). Cost impact is unmeasured; the deliberate choices that keep it down are `--debug` over `--release` (the job verifies **layout and disjointness**, not optimization), one shared guest build per edition run, and `Swatinem/rust-cache@v2` as used by the existing `clippy` and `test` jobs. When the Integrated edition becomes buildable, adding a third step is a one-line change plus one verification loop iteration.
  - *Add a `--release`/`--profile` selector alongside `--edition`.* Rejected as scope creep: `--debug` already exists and composes with `--edition`; nothing in ADR-0057 asks for more.
  - *Skip the guest build for `--edition integrated`.* Rejected as premature: `build_guests::build_command` builds test-guests too and is the freshness contract for the whole tree. Revisit only if the Integrated edition becomes buildable and the guest build measurably dominates that job.

## Data and Contract Notes

- **IR/manifest contracts:** unchanged. No module manifest, IR type, claim, or stage id is touched. `dist` continues to copy each core module's `<stem>.toml` verbatim.
- **WIT boundary:** unchanged. No file under `crates/slicer-schema/wit/` is read or edited.
- **Config keys:** the only keys involved are `dist/editions.toml`'s `schema_version`, `integrate_all`, and `integrated_modules` — all snake_case, all owned and parsed by packet 204's `load_editions`, all dist config rather than module config, so `docs/15_config_keys_reference.md` is unaffected. This packet introduces no new config key.
- **CLI surface:** `cargo xtask dist` gains `--edition <NAME>` (default `developer`) and `--plan`; `--debug` keeps its meaning. `--plan` output is a stable machine-readable contract: `<kind>\t<value>` lines, kinds `edition` / `out_dir` / `features` / `integrated` / `external`, sorted, no header.
- **Determinism:** `plan_edition` sorts every emitted collection (`cargo_features`, `integrated` is a `BTreeSet`, `external_stage` sorted by stem) so `--plan` output and the `--features` string are byte-stable across runs and platforms. A `HashSet`-ordered feature list would make the cargo build cache-thrash and the ACs flake.

## Locked Assumptions and Invariants

- **Locked:** edition membership has exactly one source of truth, `dist/editions.toml`, reached only through `xtask::editions::load_editions`. No module name from that file may be copied into Rust code, CI YAML, docs, or an AC. Every consumer re-derives it, from `load_editions` or from `--plan` output.
- **Locked:** the three-way name identity from packet 204 — `modules/core-modules/<name>` directory == `slicer-integrated-modules` cargo feature == `<name>.wasm` / `<name>.toml` staged stem — is extended by exactly one hop here: `pnp-cli` feature `integrated-<name>`. The `integrated-` prefix is the only transformation, and it exists because `pnp-cli` features share a namespace with `report` and any future unrelated feature.
- **Locked:** an edition's staged external set and its integrated set never intersect, enforced as a non-zero exit at plan time and after staging (ADR-0057 §Decision, ADR-0056 §Consequences).
- **Locked:** `integrate_all = true` means every core module returned by `discover_guests`, never a subset.
- **Locked:** `--plan`'s line format, once Step 2 lands. Four ACs and the CI verification step parse it.
- **Reversible:** `cargo xtask dist` with no flags remains a working command producing today's layout for today's module set; only its output path moves from `target/dist/` to `target/dist/developer/`. Every new `pnp-cli` feature is off by default, so `cargo build -p pnp-cli` is unchanged.

## Risks and Tradeoffs

- **The output-path move (`target/dist/` → `target/dist/<edition>/`) is a user-visible break.** Anything scripted against the old path stops working. Accepted because the alternative (editions overwriting one another in a shared root) defeats the packet's purpose. **Measured at authoring** (`rg -n "target/dist" CLAUDE.md README.md xtask/src/main.rs docs/*.md .claude/*.md`), the complete set of surfaces naming the path is **four** files, not two: `docs/01_system_architecture.md`, `README.md`, `CLAUDE.md` (§"Build & Test Commands", the `cargo xtask dist` comment), and `xtask/src/main.rs` (the `USAGE` string's `dist` line, "stage them under target/dist/."). All four are in this packet's edit set and all four are gated by AC-8's negative grep — a positive `--edition` grep alone would pass while a surface still promised the old root. Confirmed independently by `rg -l 'target/dist' --glob '!target/**' --glob '!.git/**' .` — the complete set naming the path is those four files **plus `docs/specs/multi-edition-distribution-plan.md`**, which already describes the per-edition layout and needs no edit. No `.yml`/`.yaml` names it, so CI is unaffected; shell scripts *do* exist (`OrcaSlicerDocumented/build_{flatpak,linux,release_macos}.sh`) but none references `target/dist`. (Two earlier drafts of this bullet were wrong: one claimed the tree contains no scripts at all, the other claimed no file outside the four names the path. Use the `rg -l` command above rather than a `docs/*.md` glob — that glob does not recurse into `docs/specs/`, which is exactly how the fifth surface was missed twice.)
- **`--edition integrated` is red on arrival.** It will fail `verify_integrated_feature_coverage` until a later packet integrates all core modules with their parity gates. This will look like a bug to anyone who reads ADR-0057's table without reading the error message — so the error message must name the missing modules and say the edition is not yet buildable, not merely "missing feature". Mitigated by AC-N2 asserting the message names the edition and `crates/pnp-cli/Cargo.toml`.
- **Packet 203's `pnp-cli` → `slicer-integrated-modules` dependency edge is asserted by no AC in 203.** It is described in 203's `requirements.md`/`design.md` and implied by its `integrated-classic-perimeters` feature, but an implementer working from 203's acceptance criteria alone could satisfy all of them without adding the dependency. This packet's Step 4 would then fail at `cargo check` with an unresolved feature target, and the failure would look like a 205 defect. Mitigated by a Step 4 precondition that verifies the edge exists and STOPs — attributing the gap to 203 — rather than adding the dependency here (`crates/pnp-cli/Cargo.toml`'s `[dependencies]` table is 203's surface; this packet owns only its `[features]` table).
- **The FORWARD-DEP surface is the largest risk to the packet.** Nothing this packet reads from packets 203/204 exists yet: `dist/editions.toml`, `xtask/src/editions.rs`, the registry features, and the `pnp-cli` → `slicer-integrated-modules` dependency wiring. If 204's `load_editions` returns a different type or `EditionSpec` uses different field names, Step 1 adapts the callers. If 203 wires the `pnp-cli` dependency differently (e.g. optional vs unconditional), Step 4's feature bodies follow the tree. Mitigated by Step 1 being a read-only reconciliation step with an explicit falsifying exit.
- **CI cost is added to a workflow that had no dist job.** The new job runs a full guest build plus a `pnp-cli` build twice. The absolute cost is **unmeasured** — no CI timing data exists in the tree, and this packet does not estimate one. The three deliberate cost controls are recorded under Rejected alternatives: `--debug` instead of `--release`, two editions instead of three, and `Swatinem/rust-cache@v2`. If the job proves too slow once measured, the correct response is to gate it on `pull_request` only or to drop to one edition — not to remove the verification step, which is the only thing that makes the job worth running.
- **A green CI dist job can still ship a stale guest.** `dist` builds guests itself, so this is unlikely in CI (clean checkout); locally it is the standard hazard. The AC-5 dispatch contract requires `cargo xtask build-guests --check` to report clean first.
- **`--plan` output is now a contract with no schema version.** A later change to the separator or the kind names silently breaks four ACs and the CI step. Accepted for a developer-facing tool surface; the `#[cfg(test)]` test for `print_plan`'s format is what catches an accidental change.

- Aggregate: `M`
- Largest step: `M` (Step 2 — the planning layer plus its four unit tests)
- Highest-risk dispatch and required return format: the `xtask/src/editions.rs` shape dispatch (`SNIPPETS`, 1 snippet, ≤30 lines). ## Open Questions

- `[FWD]` Should `target/dist/developer/` also be reachable as a `target/dist/` symlink or copy for backward compatibility? Recommendation: no — a second path is a second thing to keep correct, and the two doc surfaces that name the path are edited in the same step. Implementer-resolvable; does not change scope.
- `[FWD]` Should the CI job upload the edition artifacts with `actions/upload-artifact`? Out of scope as authored (this packet verifies the tree, it does not publish). If added, it is one step per edition and changes no assertion. Release packaging as a whole is explicitly out of scope per `requirements.md`.
- `[FWD]` Should `--plan` emit JSON instead of tab-separated lines? TSV was chosen because the ACs and the CI step parse it with `rg` + `cut`, with no `jq` dependency (CI installs no JSON tooling today). If a future consumer needs JSON, add `--plan-json` rather than changing `--plan`'s format, which is a locked contract. Implementer-resolvable.
- `[FWD]` When the Integrated edition becomes buildable, does the CI job gain a third step or does it iterate over `load_editions`' keys? Recommendation: iterate, so the job needs no edit when an edition is added or removed — but only after the Integrated edition is actually buildable, since iterating today would make the job permanently red. Deferred to the packet that completes the integrated set.
