# 212-extra-perimeters-parity

## Goal

Make `arachne-perimeters` honour the `extra_perimeters` config key by folding it into the auto-derived `max_bead_count` in `arachne_params_from_config` (`modules/core-modules/arachne-perimeters/src/lib.rs`), so switching `wall_generator` no longer silently discards bonus walls, and close DEV-132's read gap while re-filing its modelling half as its own deviation row.

## Problem Statement

`DEV-132` (`docs/DEVIATION_LOG.md`) records two coupled divergences around `extra_perimeters`.

**(a) The read gap.** `classic-perimeters` registers `[config.schema.extra_perimeters]` in `classic-perimeters.toml` and `run_perimeters` (`modules/core-modules/classic-perimeters/src/lib.rs`) applies it on every layer as `let base_wall_count = base_wall_count + extra_perimeters;`, pinned by `crates/slicer-runtime/tests/integration/extra_perimeters_config_tdd.rs`. `arachne-perimeters` registers no such key and `arachne_params_from_config` (`modules/core-modules/arachne-perimeters/src/lib.rs`) never reads it — verified this session: the only `extra_perimeters` matches under `modules/core-modules/arachne-perimeters/` are two `extra_perimeters_on_overhangs` hits in the manifest, zero in `src/`. A user who sets `extra_perimeters` and flips `wall_generator` to `arachne` silently loses the bonus walls on every layer, with no warning.

**(b) The modelling divergence.** PnP models `extra_perimeters` as a global config key. Canonically it is `Surface::extra_perimeters`, an `unsigned short` member of `Surface` (`Surface.hpp`), folded into the wall count in *both* generators via `int loop_number = this->config->wall_loops + surface.extra_perimeters - 1;` (`PerimeterGenerator::process_classic` and `PerimeterGenerator::process_arachne`, `PerimeterGenerator.cpp` — identical but for whitespace). There is no `add("extra_perimeters", ...)` in `PrintConfigDef::init_fff_params` (`PrintConfig.cpp`); the only quoted `"extra_perimeters"` name upstream is `#define JSON_SURF_EXTRA_PERIMETERS` in `Print.cpp`, a serialization tag.

DEV-132 filed these together because "fixing either alone entrenches the other". **This packet resolves that tension with evidence rather than by deferring both.** Two grounded facts decide it:

1. Canonical's only in-code writer of `Surface::extra_perimeters` is `PrintObject::make_perimeters` (`PrintObject.cpp`), and the BBS patch short-circuits that loop body with a bare `continue`, so the field is in practice always `0` upstream. The other writer is `from_json(const json&, Surface&)` (`Print.cpp`), i.e. deserialization only. Building per-`Surface` plumbing would therefore port a field that upstream never sets.
2. PnP cannot express per-region config at this seam today anyway: `SliceRegionView` (`crates/slicer-sdk/src/views.rs`) carries no `config_id`, and `LayerModule::run_perimeters` takes one layer-wide `&ConfigView` for the whole `&[SliceRegionView]` slice. Half (b) is an IR + WIT + marshalling change, not a module-local one.

So the packet **stages** them: fix (a) now, and re-file (b) as its own deviation row with the above evidence rather than leaving it silently absorbed into a "closed" DEV-132. Half (b) is explicitly out of scope here.

The unit relation for (a) is fixed by canonical: `process_arachne` constructs `Arachne::WallToolPaths(..., coord_t(loop_number + 1), ...)` and `WallToolPaths::generate` computes `max_bead_count = 2 * inset_count`, giving `max_bead_count = 2 * (wall_loops + extra_perimeters)`. PnP's `arachne_params_from_config` already auto-derives `max_bead_count = (2 * wall_count).max(1)`; the fix adds `extra_perimeters` inside that derivation.

## Architecture Constraints

- `ConfigView::from_declared` (`crates/slicer-ir/src/slice_ir.rs`) copies only keys present in the module's declared set. A read of an undeclared key returns `None` on every live slice, so the manifest registration and the code read MUST land in the same step or the fix is dead in production while passing every direct-invocation test (direct-invocation tests build a `ConfigView` via `ConfigViewBuilder`, bypassing `from_declared` entirely — this is exactly the blind spot that made `extra_perimeters` look wired).
- `docs/15_config_keys_reference.md`'s config-key tables are GENERATED by `cargo xtask gen-config-docs` and `docs/07_implementation_status.md`'s Open Deviation Map by `cargo xtask check-deviations` (which also VERIFIES the doc-15 sections under `--check`) and CI fails on drift via `--check`. They must be regenerated, never hand-edited.
- `crates/slicer-runtime/tests/integration/manifest_default_reconcile_tdd.rs` is exhaustive by enumeration with set-equality in BOTH directions: adding `[config.schema.extra_perimeters]` to the arachne manifest without adding `("extra_perimeters", Int(0))` to `ARACHNE_FALLBACKS` fails the suite, and vice versa. This is a mandatory part of this packet's blast radius, budgeted into Step 2.

## Data and Contract Notes

- IR/manifest contracts: one new `[config.schema.extra_perimeters]` entry in `arachne-perimeters.toml`. `ConfigView` is a flat `HashMap<String, ConfigValue>` filtered by the declared set; no IR struct changes. No `min-ir-schema` / `max-ir-schema` bump — the manifest's `[compatibility]` block is untouched.
- WIT boundary: none. `ConfigView` marshalling is key-agnostic; no `crates/slicer-schema/wit/**` edit, so no bindgen invalidation beyond the module's own source.
- Determinism/scheduler constraints: `max_bead_count` is a pure function of config; the fold introduces no ordering, no floating-point, and no host call. The `2 * (wall_count + extra_perimeters)` product keeps `max_bead_count` EVEN, which `LimitedBeadingStrategy` requires — an odd cap triggers its warning and its odd-centre `compute` branch dumps the surplus region thickness into one wide centre bead. This evenness invariant is the reason the bonus is applied as `2 * (a + b)` rather than as a separate `+extra` addend.

## Locked Assumptions and Invariants

- **Locked:** `max_bead_count`'s auto-derive branch stays EVEN for every non-degenerate input. Any future change to this derivation must preserve `max_bead_count % 2 == 0`, per `LimitedBeadingStrategy`'s odd-cap behaviour documented in `arachne-perimeters.toml`'s `[config.schema.max_bead_count].description`. **Carve-out:** the pre-existing `.max(1)` floor on that arm yields the odd value `1` when `wall_count == 0 && extra_perimeters == 0`. This hole predates the packet (`(2 * wall_count).max(1)` had it identically) and is preserved unchanged; it is unreachable through a validated config because `[config.schema.wall_count]` declares `min = 1`.
- **Locked:** a positive explicit `max_bead_count` is honoured verbatim and is NOT adjusted by `extra_perimeters`. Pinned by AC-N1; `alternate_extra_wall_tdd.rs` depends on it.
- **Locked:** the `extra_perimeters` fold happens inside `arachne_params_from_config`, hence strictly before the `alternate_extra_wall` `+= 2` bump and before the `only_one_wall_first_layer` clamp — mirroring classic, where the addition sits before the DEV-125 guard and the clamp still wins on the first printed layer.
- **Not locked / reversible:** the behaviour change is fully reversible by leaving `extra_perimeters` at its `0` default, which is the manifest default and the code fallback; a default-config slice produces byte-identical output to today.

## Risks and Tradeoffs

- **Behaviour moves for users who already set `extra_perimeters` while running arachne.** That is the point of the packet, but it means arachne goldens or parity fixtures that happen to carry a non-zero `extra_perimeters` will shift. Mitigation: the key defaults to `0` everywhere and no existing arachne fixture sets it (verified: zero `extra_perimeters` occurrences under `modules/core-modules/arachne-perimeters/src/` and the only manifest hits were `extra_perimeters_on_overhangs`). If `cargo check`/`clippy`/the targeted tests are green and a broader golden still moves, that is a genuine finding to report, not a fixture to re-record.
- **The `emitted == max_bead_count / 2` mapping is empirical, not structural.** It was measured for `LimitedBeadingStrategy`'s filtered sentinel pair on one specific fixture. Step 1 re-measures on the fixture it actually uses before pinning literals. If the measurement disagrees with AC-1/AC-2/AC-N1/AC-N2, escalate as `[BLOCK]` — never relax the assertion to match the observation.
- **Registering a key makes it user-visible in `config-schema` output and doc 15.** Accepted: that is the intended parity outcome — the same key must mean the same thing under either `wall_generator`.
- **Half (b) survives as an open deviation.** Accepted and explicit. The tradeoff is a tracked, evidence-carrying open row versus building per-region IR plumbing for a canonical field that upstream never sets.
