# 205-editions-xtask-dist-ci

## Goal

Give `cargo xtask dist` an edition dimension driven by packet 204's committed `dist/editions.toml` — resolving each edition into a `pnp-cli` cargo feature list, a staged external module set that is its exact complement, and a per-edition output root `target/dist/<edition>/` — with the ADR-0056 disjointness invariant enforced as a hard, unit-tested failure at both plan time and post-stage time, and a new CI job that builds and verifies the Developer and Hybrid edition artifacts (CI runs `dist` for the first time).

## Problem Statement

ADR-0057 decides that three editions ship — Developer (no integrated modules, every core module staged loose), Hybrid (an evidence-driven integrated set, the rest staged loose), Integrated (every core module integrated, nothing staged) — but the only distributable that exists is `dist_command`'s single fixed layout in `xtask/src/dist.rs`: build every guest, build `pnp-cli` with default features, wipe `target/dist/`, copy the binary, copy every `GuestTree::Core` guest's `<stem>.wasm` + `<stem>.toml` into `target/dist/modules/<stem>/`. There is no edition selector, no path from `dist/editions.toml` (packet 204's committed config) into the `pnp-cli` cargo feature set, and no complement logic — so no edition other than Developer is expressible.

Worse, the layout is unverified: `.github/workflows/ci.yml` never invokes `cargo xtask dist` in any of its four jobs (`fmt`, `docs-guard`, `clippy`, `test`). A broken dist bundle ships silently.

The invariant that makes editions meaningful is ADR-0056's consequence: *an edition must never stage an external copy of a module it integrates*, because integrated modules sit at search tier 5 and any higher-tier disk copy wins first-root-wins dedup — the artifact would look like a Hybrid build and behave like a Developer build, with only a provenance warning on stderr to distinguish them. That invariant currently has no enforcement point anywhere in the tree.

## Architecture Constraints

- **Disjointness is an invariant, not a convention (ADR-0056 §Consequences).** Integrated modules occupy search tier 5; an external copy of the same `module.id` at any higher tier wins first-root-wins dedup and dispatches over WASM. An edition that stages both is therefore a Developer build wearing an edition's name, distinguishable only by a provenance warning on stderr (packet 201's `external module X shadows integrated module X`, ADR-0056's consequence bullet verbatim). Enforcement must be a hard `Err`/non-zero exit, never a warning, and must be checked **twice**: against the planned staging list (cheap, catches a logic bug) and against the directory names actually present under `target/dist/<edition>/modules/` after copying (catches a leftover from an interrupted run, a non-wiped directory, or a future refactor that stages from a different source). Both calls go through one pure `assert_staging_disjoint`, which is what AC-N1 tests.
- **Set derivation over enumeration (ADR-0014's rejection of hardcoded guest lists; ADR-0057).** The integrated set, the feature list, and the staged set are all derived from two inputs — `dist/editions.toml` and `discover_guests` — and never written down anywhere else. ADR-0057 is explicit that the Hybrid set is "a dist-configuration list, not a hardcoded constant". Consequence for tests: an assertion like "N modules staged" with a literal N is forbidden even though it is true today; assert `external_stage.len() == core_stems.len() - integrated.len()` and `external_stage ∪ integrated == core_stems` instead.
- **`integrate_all = true` means every core module, and is allowed to fail today.** ADR-0057's table row for Integrated reads "every core module" / "none staged". Resolving it to "every module the registry happens to cover" would produce an artifact that calls itself Integrated while staging the remainder externally — exactly the shadowing the previous bullet forbids. So `plan_edition` expands `integrate_all` to every core stem, and `verify_integrated_feature_coverage` then rejects the plan with a named list of modules lacking an `integrated-<name>` feature in `crates/pnp-cli/Cargo.toml`. Until a later packet integrates every core module with its ADR-0056 Decision item 4 parity gate, `--edition integrated` is *expected* to fail with that message. That is the honest behaviour and it is asserted by AC-N2, not worked around.
- **Fail fast, before any build.** Resolution → coverage check → plan-time disjointness check all precede `build_guests::build_command` and `cargo build -p pnp-cli`. A typo in `--edition` must cost a config parse, not a full guest build. AC-N3 asserts both the exit code and that nothing was created.
- **Exit-code convention is pre-existing and must be matched.** Every other xtask subcommand arm exits `2` on an unknown flag after printing `USAGE`, and propagates the command's own status otherwise. `dist` keeps that: `2` for a malformed command line, `1` for a valid command line with an invalid value (unknown edition, coverage failure, disjointness violation, copy failure) — the code `dist_command` already returns for every I/O failure.
- **Guest WASM staleness applies to what `dist` produces, not to what this packet edits.** No path in this packet's change surface (`xtask/src/*.rs`, `crates/pnp-cli/Cargo.toml`, `.github/workflows/ci.yml`, docs) is a guest-WASM input per `CLAUDE.md` §"Guest WASM Staleness", so the canonical staleness bullet does not apply to the edit set. It applies to the *verification*: AC-5 stages real `.wasm` artifacts, so `cargo xtask build-guests --check` must report clean before it runs, and `dist_command` continues to call `build_guests::build_command` itself as its first build phase. A stale guest staged into a dist bundle is indistinguishable from a correct one by inspection.
- No public schema or version constant is bumped, and no existing struct gains a field. `DistPlan` is net-new with no pre-existing literal sites, so the struct-literal blast-radius discipline does not bind and no step carries a literal sweep. `crates/pnp-cli/Cargo.toml`'s new features are additive and off by default, so `cargo build -p pnp-cli` with no `--features` is byte-identical in behaviour to today.
- Coordinate units are not involved (no geometry, no mm↔unit conversion), so the `coord-system` constraint bullet is deliberately absent.

## Data and Contract Notes

- **IR/manifest contracts:** unchanged. No module manifest, IR type, claim, or stage id is touched. `dist` continues to copy each core module's `<stem>.toml` verbatim.
- **WIT boundary:** unchanged. No file under `crates/slicer-schema/wit/` is read or edited.
- **Config keys:** the only keys involved are `dist/editions.toml`'s `schema_version`, `integrate_all`, and `integrated_modules` — all snake_case, all owned and parsed by packet 204's `load_editions`, all dist config rather than module config, so `docs/15_config_keys_reference.md` is unaffected. This packet introduces no new config key.
- **CLI surface:** `cargo xtask dist` gains `--edition <NAME>` (default `developer`) and `--plan`; `--debug` keeps its meaning. `--plan` output is a stable machine-readable contract: `<kind>\t<value>` lines, kinds `edition` / `out_dir` / `features` / `integrated` / `external`, sorted, no header.
- **Determinism:** `plan_edition` sorts every emitted collection (`cargo_features`, `integrated` is a `BTreeSet`, `external_stage` sorted by stem) so `--plan` output and the `--features` string are byte-stable across runs and platforms. A `HashSet`-ordered feature list would make the cargo build cache-thrash and the ACs flake.

## Locked Assumptions and Invariants

- **Locked:** edition membership has exactly one source of truth, `dist/editions.toml`, reached only through `xtask::editions::load_editions`. No module name from that file may be copied into Rust code, CI YAML, docs, or an AC. Every consumer re-derives it, from `load_editions` or from `--plan` output.
- **Locked:** the three-way name identity from packet 204 — `modules/core-modules/<name>` directory == `slicer-integrated-modules` cargo feature == `<name>.wasm` / `<name>.toml` staged stem — is extended by exactly one hop here: `pnp-cli` feature `integrated-<name>`. The `integrated-` prefix is the only transformation, and it exists because `pnp-cli` features share a namespace with `report` and any future unrelated feature.
- **Locked:** an edition's staged external set and its integrated set never intersect, enforced as a non-zero exit at plan time and after staging (ADR-0057 §Decision, ADR-0056 §Consequences).
- **Locked:** `integrate_all = true` means every core module returned by `discover_guests`, never a subset.
- **Locked:** `--plan`'s line format, once Step 2 lands. Four ACs and the CI verification step parse it.
- **Reversible:** `cargo xtask dist` with no flags remains a working command producing today's layout for today's module set; only its output path moves from `target/dist/` to `target/dist/developer/`. Every new `pnp-cli` feature is off by default, so `cargo build -p pnp-cli` is unchanged.

## Risks and Tradeoffs

- **The output-path move (`target/dist/` → `target/dist/<edition>/`) is a user-visible break.** Anything scripted against the old path stops working. Accepted because the alternative (editions overwriting one another in a shared root) defeats the packet's purpose. **Measured at authoring** (`rg -n "target/dist" CLAUDE.md README.md xtask/src/main.rs docs/*.md .claude/*.md`), the complete set of surfaces naming the path is **four** files, not two: `docs/01_system_architecture.md`, `README.md`, `CLAUDE.md` (§"Build & Test Commands", the `cargo xtask dist` comment), and `xtask/src/main.rs` (the `USAGE` string's `dist` line, "stage them under target/dist/."). All four are in this packet's edit set and all four are gated by AC-8's negative grep — a positive `--edition` grep alone would pass while a surface still promised the old root. Confirmed independently by `rg -l 'target/dist' --glob '!target/**' --glob '!.git/**' .` — the complete set naming the path is those four files **plus `docs/specs/multi-edition-distribution-plan.md`**, which already describes the per-edition layout and needs no edit. No `.yml`/`.yaml` names it, so CI is unaffected; shell scripts *do* exist (`OrcaSlicerDocumented/build_{flatpak,linux,release_macos}.sh`) but none references `target/dist`. (Two earlier drafts of this bullet were wrong: one claimed the tree contains no scripts at all, the other claimed no file outside the four names the path. Use the `rg -l` command above rather than a `docs/*.md` glob — that glob does not recurse into `docs/specs/`, which is exactly how the fifth surface was missed twice.)
- **`--edition integrated` is red on arrival.** It will fail `verify_integrated_feature_coverage` until a later packet integrates all core modules with their parity gates. This will look like a bug to anyone who reads ADR-0057's table without reading the error message — so the error message must name the missing modules and say the edition is not yet buildable, not merely "missing feature". Mitigated by AC-N2 asserting the message names the edition and `crates/pnp-cli/Cargo.toml`.
- **Packet 203's `pnp-cli` → `slicer-integrated-modules` dependency edge is asserted by no AC in 203.** It is described in 203's `requirements.md`/`design.md` and implied by its `integrated-classic-perimeters` feature, but an implementer working from 203's acceptance criteria alone could satisfy all of them without adding the dependency. This packet's Step 4 would then fail at `cargo check` with an unresolved feature target, and the failure would look like a 205 defect. Mitigated by a Step 4 precondition that verifies the edge exists and STOPs — attributing the gap to 203 — rather than adding the dependency here (`crates/pnp-cli/Cargo.toml`'s `[dependencies]` table is 203's surface; this packet owns only its `[features]` table).
- **The FORWARD-DEP surface is the largest risk to the packet.** Nothing this packet reads from packets 203/204 exists yet: `dist/editions.toml`, `xtask/src/editions.rs`, the registry features, and the `pnp-cli` → `slicer-integrated-modules` dependency wiring. If 204's `load_editions` returns a different type or `EditionSpec` uses different field names, Step 1 adapts the callers. If 203 wires the `pnp-cli` dependency differently (e.g. optional vs unconditional), Step 4's feature bodies follow the tree. Mitigated by Step 1 being a read-only reconciliation step with an explicit falsifying exit.
- **CI cost is added to a workflow that had no dist job.** The new job runs a full guest build plus a `pnp-cli` build twice. The absolute cost is **unmeasured** — no CI timing data exists in the tree, and this packet does not estimate one. The three deliberate cost controls are recorded under Rejected alternatives: `--debug` instead of `--release`, two editions instead of three, and `Swatinem/rust-cache@v2`. If the job proves too slow once measured, the correct response is to gate it on `pull_request` only or to drop to one edition — not to remove the verification step, which is the only thing that makes the job worth running.
- **A green CI dist job can still ship a stale guest.** `dist` builds guests itself, so this is unlikely in CI (clean checkout); locally it is the standard hazard. The AC-5 dispatch contract requires `cargo xtask build-guests --check` to report clean first.
- **`--plan` output is now a contract with no schema version.** A later change to the separator or the kind names silently breaks four ACs and the CI step. Accepted for a developer-facing tool surface; the `#[cfg(test)]` test for `print_plan`'s format is what catches an accidental change.
