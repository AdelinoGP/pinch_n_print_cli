# Packet Contract: infill-pattern-specific-keys

## Goal

Ship OrcaSlicer's three pattern-specific sparse-infill algorithms as three new `claim:sparse-fill` core modules — `lateral-lattice-infill` (canonical `FillLateralLattice`), `lateral-honeycomb-infill` (canonical `FillLateralHoneycomb`), and `locked-zag-infill` (canonical `FillLockedZag`) — each owning, in its own manifest, exactly the P09 keys that drive *its* algorithm, so that all 10 keys become live behaviour-changing decision points selected through the existing `sparse_fill_holder` / `module_overrides` holder resolution. No key is declared without a consumer; no key is padded into the CONFIG_BLOCK as a deliverable.

## Scope Boundaries

The packet creates three module crates under `modules/core-modules/` (each: `Cargo.toml`, `src/lib.rs`, `<name>.toml` manifest, `wit-guest/` cdylib wrapper, `tests/`), registers them in the workspace and the integrated-module registry (`Cargo.toml` members, `crates/slicer-integrated-modules/{Cargo.toml,src/lib.rs}`, `crates/pnp-cli/Cargo.toml` `integrated-<name>` passthrough features), and updates the core-module-count and claim-resolution suites. It does **not** change any WIT interface, any IR schema version, or any `ResolvedConfig` field: holder selection already exists as `ResolvedConfig.sparse_fill_holder` (`crates/slicer-ir/src/resolved_config.rs`) and dual extrusion width is already expressible as per-vertex `Point3WithWidth.width` on `ExtrusionPath3D` (`crates/slicer-ir/src/slice_ir.rs`). It does not implement the zigzag/crosszag patterns, `multiline` for the new modules (that is packet 262a's `fill_multiline`), canonical's ant-colony monotonic ordering, or any behaviour change to `rectilinear-infill` / `gyroid-infill` / `lightning-infill`.
