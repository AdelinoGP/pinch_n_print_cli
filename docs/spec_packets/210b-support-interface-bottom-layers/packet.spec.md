# Packet Contract: 210b-support-interface-bottom-layers

> **SUPERSEDED 2026-08-12 by the support-families and anchored-entities sequence** (`docs/specs/support-families-anchored-entities-plan.md`). DEV-129's bottom-interface (floor) bands become a standard semantic role in the structural `SupportPlanIR` (packet 220), and both family planners (packets 221/222) emit interface polygons; the code-1003 stub is retired by the family-contract migration rather than by a post-pass over the old `SupportPlanEntry` rows. Directory retained intact for provenance; do not implement as-is.

## Goal

Replace `support_interface_bottom_layers`' warn-only code-1003 stub with real bottom-interface (floor) bands (DEV-129): port canonical's `< 0 ⇒ use the top count` fallback, detect where a branch chain lands on model geometry, densify upward with the same scan-line emitter the top band uses, and retire the stub. The pass runs as a post-pass over the already-emitted `SupportPlanEntry` rows, **after** `smooth_branches`, so the band is centred on the position that will actually be printed.

**This packet writes no new geometry primitives.** It consumes `210a`'s migrated shapes — `split_column_into_chains`, `point_in_any_expoly`, integer `first_point_xyw`, unit-typed `push_interface_scan_lines` — and adds a second *caller* to the first of those. It does not reopen `smooth_branches`.

**Which membership helper, and why it matters.** The model-landing test asks whether a chain's smoothed XY lies inside `collision_cache[L_end - 1].collision_polys`. That field is `Vec<ExPolygon>` (`slicer_ir::ExPolygon { contour: Polygon, holes: Vec<Polygon> }`), so the helper this packet calls is `210a`'s `point_in_any_expoly(polygons: &[ExPolygon], p: Point2) -> bool`. It is **not** `point_in_polygon_units(poly: &[Point2], p: Point2) -> bool`, which takes a single ring: the types do not connect, and the obvious workaround — passing `ex.contour.points` — silently drops hole handling, which on support geometry means dropping a floor band inside a model hole. `point_in_polygon_units` remains `210a`'s private ring-level primitive that `point_in_any_expoly` composes from; this packet neither calls it nor edits it.

## Scope Boundaries

In scope: `modules/core-modules/support-planner/src/lib.rs` (the `SupportPlanner.support_interface_bottom_layers` field and its `from_config` parse, the net-new `resolve_interface_bottom_layers`, the net-new `should_densify_bottom_interface` guard predicate, the net-new `densify_bottom_interface` post-pass and its call site in `plan_for_object`, and the code-1003 stub deletion); `modules/core-modules/support-planner/support-planner.toml` (one stale comment); `modules/core-modules/support-planner/tests/diagnostics_tdd.rs` (two cases rewritten to the retired contract); `modules/core-modules/support-planner/tests/interface_bottom_layers_tdd.rs` (net-new); and both frozen-golden fixture pairs under `resources/golden/` if and only if bands-on-by-default moves them.

Out of scope: everything `210a` owns — `PlannedSupportNode`'s types, the MST, the avoidance clamp, `smooth_branches`, and the **bodies** of `split_column_into_chains`, `point_in_any_expoly` and `point_in_polygon_units` (this packet calls the first two and does not touch the third), plus `tests/multi_neighbour_mst_tdd.rs`, `tests/smooth_nodes_tdd.rs`, `DEV-128`. Also out of scope: the WIT/IR wire format (AC-N3 in `210a` pins it and nothing here widens it); the support **top**-interface band; the bottom **gap** (`support_bottom_z_distance`, for which PnP has no key); canonical's `num_bottom_base_interface_layers` base/interface split; diagnostic codes 1001 and 1002; and every other core module.
