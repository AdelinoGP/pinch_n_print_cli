# Independent properties for region mapping, paint, support and lightning

## Goal

Complete H-REGIONMAP, H-PAINT, H-SUPPORT and the delegated H-LIGHTNING module obligation with independently checked bounded properties, real driver witnesses, concrete defect regressions and measured Windows execution.

## Why

The approved input is `docs/specs/proptest-openrscad-adoption.md` §§3–7, 10–13 and queue row 11. The existing examples are useful stimuli, not an independent combinatorial or layered-scene model. A passing chain helper cannot prove that its driver uses the intended axis order; a production Boolean cannot validate its own partition; and an empty support or lightning result is not automatically a failure or proof of correct nonempty geometry.

The input's lightning path has become historical: `crates/slicer-core/src/algos/mod.rs` no longer declares lightning. `Generator` now belongs to the private kernel of the `lightning-infill` workspace member; `docs/02_ir_schemas.md` § Lightning legacy IR retirement and ADR-0074 record the move. This packet follows that actual owner, rather than resurrecting a host prepass. Its scope and the module-coverage credit are unchanged.

## Scope

- In: the four assigned families; actual region-map and wrapper observations; the approved coordinated priority/name ordering correction across RegionMapping, paint composition and selection/config identity; independent Cartesian, orthogonal-cell, schedule, layered-contact and small-tree checks; full-source identity and defined empty/error paths; host support analysis, role regularization and territory clearance at their real seams; owner-local lightning properties; deterministic counterexamples, witness-preserving shrinking, profiles, Windows routine/extended evidence, and focused canonical-correct fixes with named concrete regressions for confirmed defects.
- Out: SCAD/engine requirements, general mesh/Boolean correctness already owned by #9, general scheduler or runtime-dispatch properties, a randomized WASM/guest or pipeline campaign, new IR/WIT/schema fields, widening private APIs for tests, arbitrary support-family planner/renderer algorithms, lightning support-mode implementation, a replacement lightning strategy or a claim of canonical parity. #14 owns planner/renderer feasibility, decline reasons and impossible routing; #13 credits this packet for the lightning generator instead of duplicating it. A larger defect blocks the affected coverage rather than being skipped or weakened.
- The source plan's **Locked decisions / Ordered chain identity** row authorizes `(priority, semantic name)` throughout RegionMapping, composition, selection and exact-chain config lookup, plus reconciliation of DEV-199. This packet authorizes the coordinated production, fixture and documentation changes specified below, not any further policy change. No generated packet or queue is edited as part of #11.

## Design notes

### Live seams and coordination boundaries

- `execute_region_mapping_with_cap` calls `execute_region_mapping_inner` (`crates/slicer-core/src/algos/region_mapping.rs`). `commit_region_mapping_builtin` (`crates/slicer-runtime/src/builtins/region_mapping_producer.rs`) calls the latter with the real plan's aggregate and commits the result to the blackboard. The kernel calls `enumerate_canonical_chains` (`crates/slicer-ir/src/region_split_registry.rs`). The separately defined `canonical_variant_chain_order` (`crates/slicer-scheduler/src/region_split.rs`) currently has no non-test caller; helper coverage is not driver coverage.
- **Approved oracle and current discrepancy.** Sort declared semantic axes by `(AggregatedRegionSplitEntry.priority, semantic name)`, using name only as the tie-breaker; every emitted chain is a subsequence of that axis order. The name-keyed `BTreeMap` storage itself still iterates by name, and `enumerate_canonical_chains` (`crates/slicer-ir/src/region_split_registry.rs`) preserves the axis/value order supplied by its caller. RegionMapping's `scan_paint_data` keeps the established discrete value order. Composition emits the same ordered vector, and selection/config lookup preserves and matches that exact vector; it does not sort or normalize identities. `docs/02_ir_schemas.md` § Config Key Namespaces separately mandates **lexical paint-config overlay precedence**, with tool overlay last: changing chain order must not change that rule.
- **Discriminating independent expectations.** For one parent with `material@100` / `PaintValue::ToolIndex(0)` and `fuzzy_skin@200` / `PaintValue::Flag(true)`, the complete set of ordered chains is `{ [], [("material", ToolIndex(0))], [("fuzzy_skin", Flag(true))], [("material", ToolIndex(0)), ("fuzzy_skin", Flag(true))] }`. Compare sets of ordered vectors and full `RegionKey`s, never `RegionMapIR.entries` iteration order. Also use legal community axes `com.example.zeta@1000`, `com.example.alpha@1100`, `com.example.beta@1100`: their combined axis order is `[com.example.zeta, com.example.alpha, com.example.beta]`, demonstrating both priority overriding lexical name and lexical tie-breaking. Derive the model from the fixture declarations, not from either production sorter.
- **Production correction and source-API fallout.** Today `execute_region_mapping_inner` takes raw name-ordered map keys and `compose_variants` (`crates/slicer-core/src/algos/paint_segmentation/compose_variants.rs`) groups axes in name order. In the core mapping kernel sort the aggregate entries by `(entry.priority, name)` before calling the IR enumerator; compute that order locally rather than adding a core → scheduler dependency. Preserve the separate lexical overlay precedence by applying paint-semantic configs in namespace-key order rather than folding in chain order; retain tool-last handling. These are source-derived discrepancies, not executed failure claims.
- `execute_paint_segmentation` (`crates/slicer-core/src/algos/paint_segmentation/mod.rs`) receives a `RegionMapIR`, not the priority registry. For each actual pre-paint `(layer, object, base region)`, obtain the ordered axis names from that parent's maximal-length non-modifier RegionMap chains; the real RegionMapping cross-product has the same complete axis-name sequence in all such maximal chains. Project that sequence onto the semantic outputs for this parent, independent of HashMap insertion/iteration and of other objects. Change `compose_variants` to preserve the caller-supplied **first occurrence order of semantic axes** when grouping and constructing each chain; `execute_paint_segmentation` supplies its per-parent inputs in the map-derived order. Its existing signature stays unchanged, but its public native input-order contract changes: direct callers must supply axes in their desired canonical order. Update its rustdoc and all in-tree direct calls/tests; do not add a name-sort fallback, fabricate priorities for custom semantics, expose a new API solely for testing, or change behavior of the documented empty/no-paint/seam-only passthroughs. The valid production-map precondition is not a new general malformed-map validator. Preserve per-semantic value handling, longer-chain-first claiming, BASE residual, support/seam annotation routing and exact geometry ownership.
- **Real cross-stage identity.** `RegionKey` (`crates/slicer-ir/src/slice_ir.rs`) includes the ordered vector in equality/hash. `region_map_key_for_sliced_region` and `build_layer_selection_index` (`crates/slicer-wasm-host/src/selection.rs`) retain it, and selection's `config_for` requires an exact map entry or returns `SelectionError::MissingModelConfig`. Separate kernel/helper assertions do not prove this join. ### Independent charters

Every registered property calls its real SUT through `PropertyRun::new` / `bound` / `check` with a fresh `CaseGuard` per generated and shrink invocation. Its charter in prerequisite `docs/testing/properties.md` includes all source-plan §5 fields: owner/path, precise contract and mode, bounded domain, required witness, strategy, actual oracle dependencies, tolerance/overflow proof, shrinking, feature/profile/isolation, failure/replay and acceptance. Rare witnesses also run deterministically. Test-local models and their controls share the **same checker**; none calls the SUT's Boolean, enumerator or validator to construct its expected answer.

**H-REGIONMAP.** Generate unique `(layer, object, region)` identities, one source object per ID, legal discrete registered axes and bounded distinct `Flag`, `ToolIndex` or `Custom` values; include absent paint, duplicate facet values, undeclared semantics, two objects and multiple layers. Independently sort fixture `(priority, name)` declarations and derive choices using a bounded Cartesian/ordinal model, checked before allocation. For each parent, compare the complete set of ordered chain vectors and the full `RegionKey` set to actual output; cardinality is the sum of each parent object's products `∏(1 + distinct values)`. The empty chain occurs exactly once per parent. Observe `config_for`/`config_for_raw`, a deliberately nondefault base config, and idempotent default interning against an independently constructed expected value/first-occurrence model, not `configs[0]` as the expected production config. For positive expected counts compare cap at exact count and just below it, including `CapExceeded { entry_count, cap, top_contributors, .. }` for a unique top contributor; test the zero-count/zero-cap mode separately and do not assume tied contributor ordering.

The deterministic `prepass_regionmap_order_and_cap_controls` also drives `execute_region_mapping_inner` with `host_config = None` on the material/fuzzy witness: give fuzzy and material distinct `line_width` values `0.5` and `0.75`, respectively. The combined key is material-then-fuzzy but its resolved width is `0.75`, because lexical overlay order is fuzzy-then-material. With a tool-0 config of `1.0`, the same combined key resolves to `1.0` (tool last). This exposes the current compatibility-path risk where changing the chain loop alone would reverse config precedence. Test this against actual configs, not a local sorter.

Drive `ScalarInRegionSplitFacetValue { object_id, semantic, scalar_bits }` only for a declared axis; an undeclared scalar is not that error. A duplicated full active identity must produce `DuplicateRegionKey { key }` with a nonbinding cap. Test #6's parent boundary at the **caller**: a real nonempty parameter-modifier mesh cross-section on an unsupported base parent gives `ModifierParentRegionIdOutOfRange { key }`; no effective footprint, empty mesh, out-of-layer mesh and support-only modifiers do not exercise that mint. Also exercise the painted-parent boundary after a real chain is minted, including the separate possibility that `paint_variant_region_id` overflows before `modifier_sub_region_id_fits`; classify and fix a confirmed reachable panic rather than asserting a fabricated error today.

Exercise a genuine modifier-ID collision: find and retain two **different**, valid sliced parameter-modifier footprints with the same `modifier_sub_region_id` for one object/parent; pass their actual meshes through `execute_region_mapping_with_cap` and require `DuplicateRegionKey` rather than silent overwrite. Calling the mint helper to establish an adversarial stimulus is not an oracle for collision handling. Identical footprints intentionally group and are not that collision. Verify the actual sliced footprints and retain concrete coordinates; if a valid collision fixture cannot be constructed, this obligation remains blocking, not skipped. Different full identities are not automatically collisions. Separately investigate the `paint_variant_region_id` comment claiming both region-map and segmentation callers reject colliding painted IDs: the inspected map inserts full keys including the chain, whereas `register_paint_variant_region_id` in `crates/slicer-core/src/algos/paint_segmentation/mod.rs` rejects a same-object synthesized-ID collision. Its fast-path/modulo formula gives a concrete **raw type-level** collision candidate: single `material` chains with `ToolIndex(0)` and `ToolIndex(999_999)` have the same payload for the same base; the latter is not a claim that such a physical printer tool exists. Establish the actual consumer contract and a real reachable scene before fixing code or correcting a stale comment; do not assert universal hash injectivity.
