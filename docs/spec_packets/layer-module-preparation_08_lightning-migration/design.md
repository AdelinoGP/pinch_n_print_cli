# Design: lightning-migration

## Decision State

**Implementable draft.** The planner and the two plan types move from the host into the consuming artifact; the move is proven by recorded behavioural equivalence and then the host contract is deleted. The ADR conflict is resolved by [ADR-0074](../../adr/0074-lightning-migration-on-recorded-equivalence.md), the accepted decision record that supersedes ADR-0029's host-ownership decision and amends ADR-0066's retirement precondition; the two dated `## Amendment — 2026-10-20` sections in those ADRs carry the clause-by-clause replacement, and `D-LMP08-ADR-0066-RETIREMENT-PRECONDITION` / `D-LMP08-ADR-0029-HOST-OWNERSHIP` in `docs/DEVIATION_LOG.md` are the registered deviations. ADR-0029's Future-Reviewer Note is not superseded: preparation is whole-print, so the move is not the per-layer approximation that note retires. No `[BLOCK]` remains and no deviation row is an entry condition.

What is still open is only the *outcome* of running the equivalence comparison, which cannot be authored in advance.

## Decisions That Replace the Former Blockers

### D1 — Correctness is recorded equivalence to the live producer (was B1)

The migration's promise is "same output, different owner". The oracle is the current producer's own output, recorded before removal:

- **Capture**: a committed baseline fixture produced by a recorder test driving the real pipeline with the live host producer. Per case: plan entries keyed by `(global_layer_index, object_id, region_id, ordered variant_chain)` → directed edge multiset + grounding/root witnesses; the final caller-attributed segment multiset; `sha256` of the plan payload and of the inputs it was derived from.
- **Compare**: after the move, native and fresh-WASM preparations each reproduce that baseline. Key identity is the full key; edges compare as a **multiset** with multiplicity; segments compare per case and per caller. Adapters are compared to the baseline, never to each other.
- **Diagnose**: the separate input digest is what makes an "algorithm differs" claim honest — a run whose inputs hash differently has a plumbing defect, and its plan comparison says nothing about the algorithm.

**Corruption controls** (AC-N1) exist because a comparator is easy to make vacuous: a dropped entry, reversed edge, dropped `variant_chain` element, duplicated entry, swapped region identity, or a length-only stub must each be rejected, and an empty population must fail its own control.

**The case material is transformed, and the transformation is recorded.** "The five Classic inputs" means the five fixture cases **as transformed by the recorder**, not the fixture geometry verbatim. The recorder applies `GEOMETRY_SCALE = 0.25` to the recorded XY geometry before building the per-region meshes. This is measured, not aesthetic: the live producer seeds one tree per unsupported distance-field cell and resolves each seed against every existing tree, so cost grows with region area while the cell size is fixed by `line_width / (6 · infill_density)`. At scale 1.0 the `anchor_bridge_classic` case had not finished planning after 40 minutes (its generator call alone ran past 7 minutes) in the debug profile the recorder is invoked under; at 0.25 the five cases' planning calls total ~93 s and a full recorder run finishes in ~160 s. Topology (holes, islands, region split) and every config scalar are preserved exactly. The committed baseline's `derivation.geometry_scale` records the value, `derivation.geometry_scale_reason` records the measurement, and `inputs_sha256` pins the scaled inputs the oracle was actually derived from. A reader must not treat the baseline as evidence about the unscaled fixture geometry.

**The baseline must exercise non-empty variant chains.** The five fixture case identities carry empty `variant_chain` values. An all-fixture baseline would therefore compare empty chains to empty chains, and a migration that dropped or reordered a chain would still pass AC-2/AC-3 on the one identity axis most specific to this module. The recorder paints one top-face triangle of `hole_void_classic`'s first region object with `PaintValue::ToolIndex(1)` in the `material` semantic. The real paint segmentation turns that patch into a painted sub-region, and the committed plan and caller records carry `[("material", ToolIndex(1))]` on layers 4–6. `derivation.synthetic_paint` records the patch, and the recorder's caller dedup keys on the **full** identity including the ordered chain: a layer/object/region-only key silently dropped the painted caller because the painted sub-region shares object and region id with its base region, which is exactly the identity-collapse defect this coverage is meant to catch.

**Equivalence is not parity.** It preserves whatever the live producer does, including its existing deviations. Row 07's `Gate A outcome: fail` and row 09's unexecuted Gate B remain recorded and are neither consumed nor improved here.

### D2 — Inputs come from the committed typed preparation surface (was B2)

The host producer reads `Blackboard::slice_ir()` (per-region `object_id`, `region_id`, `variant_chain`, `polygons`) plus `ResolvedConfig.{sparse_fill_holder, infill_density, layer_height, infill_angle, line_width}` resolved through `flow::resolve_role_width(ExtrusionRole::SparseInfill, …)`.

The guest's typed equivalent. All three accessors return `Result<Vec<…>, PreparationInputError>` — the error is part of the contract. A declaration that does not grant a read surfaces as `PreparationInputError::AccessDenied` (the `permits` check in `crates/slicer-wasm-host/src/preparation_input.rs`, and the reader in `crates/slicer-wasm-host/src/preparation_native.rs`); a declared `*_optional` capability read with no committed product surfaces as `PreparationInputError::MissingRequired { read }` from `validate_reads`:

| Host input | Guest source |
| --- | --- |
| `SliceIR.regions[].polygons` | `PrintPreparationInput::regions(layer_index, offset, max_items) -> Result<Vec<PreparationRegion>, PreparationInputError>` → `polygons` (holes travel inside each `ExPolygon`), plus `sparse_infill_area`, `infill_areas`, `internal_solid_fill`, `internal_bridge_areas` |
| `object_id` / `region_id` / `variant_chain` | `PreparationRegion::{object_id, region_id, variant_chain}`, `PreparationVariantChain = Vec<(String, PreparationPaintValue)>` |
| `layer_index` / `z` | `PreparationRegion::{global_layer_index, z}` |
| `ResolvedConfig` scalars | `PrintPreparationInput::region_configs(layer_index, offset, max_items) -> Result<Vec<PreparationRegionConfig>, PreparationInputError>` → `PreparationRegionConfig.config: ConfigView` (`get_float`/`require_float`), cross-checked against `PreparationRegion.effective_layer_height` |
| selected targets / eligibility | `PrintPreparationInput::selected_targets(layer_index, offset, max_items) -> Result<Vec<PreparationSelectedTarget>, PreparationInputError>` (`invoke`, `source`, `config`, `held_claims`, `resolved_role_tool`). The target list itself is host-side (`slicer_wasm_host::selection::LayerSelection::targets`) and feeds the shared predicate; the module never re-reads it |

**Who builds the kernel input, and why the planner's signature does not change.** The kernel keeps the host entry point's shape — `generate_lightning_trees(&[SliceIR], &ResolvedConfig) -> Result<Arc<KernelPlan>, KernelError>` — and the two plan types relocate into `modules/core-modules/lightning-infill/src/kernel/plan.rs` as `KernelPlan`/`PlanEntry`, `pub(crate)`, no `serde`, no `schema_version` field and no schema-version constant, so there is nothing to assert a version about. `KernelPlan`'s empty value is `KernelPlan { entries: Vec::new() }` (a private `Default` impl is acceptable because it carries no version), which is why the eligibility branch's early return keeps its shape. `SliceIR`, `SlicedRegion` and `ResolvedConfig` are **not** plan IR: they stay in `slicer-ir`, the guest imports them from `slicer-ir`, and the adapter builds them. So `mod.rs`'s computation keeps operating on the same two input types and changes only the names it imports — this is what makes "planning numeric logic frozen" verifiable rather than aspirational.

**The adapter is NET-NEW and additive.** `modules/core-modules/lightning-infill/src/planning_input.rs` constructs the planner's inputs from the typed records (the row-07/09 `feasibility-kernel/` stub's own planned `KernelInput` API is a different workstream and is not used or edited here):

- `PreparationRegion` → one `SliceIR` per distinct `global_layer_index`: `SliceIR { global_layer_index, z, ..SliceIR::default() }`, grouping every `PreparationRegion` that shares that index into one `regions: Vec<SlicedRegion>`. Each `SlicedRegion` starts from `SlicedRegion::default()` and carries `object_id`, `region_id`, `polygons` copied verbatim (`region.polygons.clone()`) and `variant_chain: region.variant_chain.iter().map(|(k, v)| (k.clone(), slicer_ir::PaintValue::from(v))).collect()` — the concrete conversion of `PreparationVariantChain = Vec<(String, PreparationPaintValue)>` into `Vec<(String, PaintValue)>`, which `slicer_ir::PaintValue`'s `impl From<&PreparationPaintValue>` supplies. The planner reads only `global_layer_index`, `regions` and, per region, `object_id`, `region_id`, `variant_chain`, `polygons`; every other `SlicedRegion` field is therefore left at its default, and `z` is carried for layer identity even though the relocated computation does not read it.
- `ConfigView`/`effective_layer_height` → `ResolvedConfig { sparse_fill_holder: "lightning-infill".into(), line_width, infill_density, layer_height, infill_angle, ..Default::default() }`, i.e. exactly the five fields the planner reads. `line_width == 0.0` is the host's automatic sentinel: `ExpansionResolver::expand_key`'s `is_plain_zero` branch (`crates/slicer-config/src/lib.rs`) expands it to `1.125 × nozzle_diameter` before the config is committed, so the kernel never sees `0.0` — a committed value that is still `0.0` means the sentinel survived expansion and the step stops for an input-contract fix instead of forwarding a zero width. Constructibility is verified: `SliceIR` has public fields and an `impl Default`, `SlicedRegion` derives `Default`, and `ResolvedConfig` is macro-generated with public fields plus `impl Default`, so all three are constructible outside `slicer-ir` without a new constructor.

**The native prepared pair is exported by the integrated-module registry.** AC-2's native leg must run the module's real paired artifact, not a hand-built surrogate. `crates/slicer-integrated-modules/src/lib.rs` currently exposes `native_entries()`, which returns only the plain `NativeStageEntry`; the generated `__slicer_prepared_native_entry()`/`__SLICER_PREPARATION_SCHEMA` pair exists only after `#[slicer_module(preparation)]` is attached (Step 7b). Step 7c adds `prepared_native_entries() -> Vec<(ModuleId, NativePreparedStageEntry, PreparationExportSchema)>` to the same crate, gated on the `lightning-infill` feature and compiled only for non-`wasm32` targets, which is exactly the tuple shape `SliceRuntimeExtensions::prepared_native` already accepts and `run.rs` already freezes through `freeze_native`. This is an export/access addition, not a new scheduler path: the runtime's selection, suppression and preparation flow are unchanged. Today the returned set contains the lightning module only because it is the only integrated module that declares preparation; the function's contract is "every enabled integrated module that declares the capability", so later modules join by declaring the capability, not by editing the accessor.

**`layer_height` and `infill_angle` must be declared.** `lightning-infill.toml`'s `[config.schema]` declares `infill_density` and `line_width` but not `layer_height` or `infill_angle`, and `ConfigView::from_declared` drops undeclared keys. The two keys are added to the manifest (the pattern every other infill module already follows), so `region_configs` can supply them.

**The planner's reads are print-wide; the typed reads are per region.** The host passed one `default_resolved_config` to `generate_lightning_trees`. The adapter therefore requires the five scalars to **agree across every `PreparationRegionConfig` it reads** and fails preparation with `ModuleError` code `57412`, `config disagrees across committed regions: {key}`, if they do not, instead of silently picking one. `layer_height` is additionally cross-checked against `PreparationRegion.effective_layer_height` for the same reason: the planner multiplies `config.layer_height`, not the effective per-region height, so substituting the latter would be a behaviour change on adaptive-layer prints rather than an adaptation. That cross-check fires only when the region **carries** a height: paint segmentation and region split rebuild their regions from `SlicedRegion::default()`, so the field holds the `f32` default `0.0` there, and a non-positive reading means "not supplied" rather than a competing value (no layer can be 0 mm — `lightning-infill.toml` floors `layer_height` at 0.01). Measured on the painted `hole_void_classic` case, whose layer-0 base region reads `0.0` against a committed `0.2`; without this rule that case fails preparation with `57412 layer_height` before planning starts.

Manifest declaration: `[preparation] interface = "slicer:layer-preparation/prepare@1.0.0"`, `input_reads = ["layer_plan", "slices", "region_map"]`, `views = ["planning_geometry"]` — the same section shape the prepared test guests use under `crates/slicer-wasm-host/test-guests/`. `layer_plan` is the enumeration read: preparation is whole-print, so the module must learn the committed schedule's own layer indices to publish one piece per layer (including layers that carry no regions), and no other granted accessor supplies them. `selected_targets` is deliberately **not** declared: selection is read by `PrintPreparationScope::capture_committed_selection` to decide whether this module participates at all, and the module never re-reads it, so declaring it would grant a read that nothing consumes. Step 7b confirms each declared read against `validate_reads` in `crates/slicer-wasm-host/src/preparation_input.rs` and the accessor it feeds. `fixture` grants no typed read and is not declared.

**Eligibility moves from a config string to selection — and the branch stays.** Verified: the planner's only eligibility test is `if config.sparse_fill_holder != "lightning-infill" { return Ok(Arc::new(LightningTreeIR::default())) }` in `crates/slicer-core/src/algos/lightning/mod.rs`, and the prepass closed the same predicate before calling it (`default_resolved_config.sparse_fill_holder == "lightning-infill"` in `crates/slicer-runtime/src/prepass.rs`). The true branch was therefore unreachable in every baseline run. Resolution: keep the branch verbatim (it is part of the frozen computation), pin `sparse_fill_holder = "lightning-infill"` in the adapter's constructed `ResolvedConfig`, and let selection remain the gate. The field is a host fill-holder key, not a module config key — no module manifest declares it, so no typed read can supply it — and the input digest covers it, so a print where selection and the old string disagree is reported as an input-digest divergence rather than as an algorithm difference. After migration, preparation runs when the shared predicate in `PrintPreparationScope::capture_committed_selection` holds: `index.selection_for(layer.index, &frozen.module_id).is_some_and(|s| s.invoke && !s.targets.is_empty())`. AC-N3 asserts the gating behaviour, AC-3 asserts the output.

### D3 — Private pieces are module-owned, versioned and bounded (was B3)

- **Granularity**: one piece per layer, named `lightning-layer-{global_layer_index}`. Cross-layer tree construction happens inside preparation; a consumer only needs its own layer, so every read stays bounded and no offset table or shared codec is needed. If the row-03 name validator rejects the spelling, the step records the accepted form and uses it — the format is settled here, the exact accepted spelling is a step exit condition.
- **Encoding**: module-local, little-endian, fixed width. Header `b"LTPL"`, `u16` format version `1`, `u32` entry count; per entry `u32` object-id length + UTF-8, `u64` region id, `u32` layer index, `u32` variant-chain count + per element (`u32` key length + UTF-8, `u8` paint tag + payload), `u32` edge count + per edge four `i64` coordinates in **units** (1 unit = 100 nm). No float crosses the boundary.
- **Paint payloads**: tags `0`/`1`/`2`/`3` are `Flag`/`Scalar`/`ToolIndex`/`Custom`. `Flag` is one `u8` (0 or 1), `ToolIndex` one `u32`, `Custom` a `u32` length + UTF-8. `PaintValue::Scalar` is the one painted value that carries a float, and it travels as `f32::to_bits()` — a `u32`, not a float field — because `PaintValue`'s own equality is bit-based, so a bit-exact integer encoding is what "identity round-trip" means here. An unknown tag is malformed; a new `PaintValue` variant needs a new tag.
- **Decode errors**: missing piece keeps the inherited `PreparedPlanView::require` contract — `ModuleError` code `57401`, `fatal == true`, `message == format!("required preparation piece missing: {}", name)`. Malformed body → `57410`, `malformed lightning plan piece: {name}`. Unsupported version → `57411`, `unsupported lightning plan piece version: {version}`. The two codes partition by cause, not by proximity: `57411` means a **structurally valid header** carrying a version this decoder does not read (the version number, not the piece name, is in the message), while a body that fails the magic, truncates anywhere, over-runs a declared length, mis-encodes UTF-8, carries an unknown paint tag, or leaves bytes after the declared entries is `57410`. Trailing bytes are malformed rather than an extension point because the version field is the extension point. `ModuleError.code` is documented "module-specific" (`crates/slicer-sdk/src/error.rs`), so these are this module's own scoped codes, deliberately kept in the same `574xx` family as the row-03/05 fixture decoder convention (`57402`/`57403` in `crates/slicer-wasm-host/src/preparation_native.rs` and the `preparation-lifecycle-*` / `preparation-transport-*` test guests, and `docs/05_module_sdk.md` names `57403` as that fixture's malformed-payload code). Same family, different module, no shared allocation and no collision. The adapter's config-disagreement failure is `57412`. AC-N2 asserts all of these on the lightning module's own errors, and asserts that absent, malformed, unsupported-version and config-disagreement remain four distinct failures.
- **Opaque to the host**: no runtime or CLI code decodes these bytes, discovers views by piece name, or receives them serialized. Bounds are enforced on every `read(offset, max_bytes)` in module code.

### D4 — Retirement is partitioned, with the contract package deleted whole (was B4)

The inventory below is re-derived from the tree. The previous revision's WIT citation was stale twice over: the accessor lives in `lightning-queries.wit::lightning-query-view`, and the package's *only* member is that resource, so retiring the accessor retires the interface and the package. Deleting a hollow interface instead would leave a package nothing imports.

Each deletion step owns every constructor, literal, exhaustive match, old-value assertion, registration and doc line its symbol removal breaks. The edit cap is three files for ordinary production source; a step whose single symbol removal is atomic across its constructors and readers declares that set in place (11c at six, 12b and 13b at four), a test-retarget step batches at most six test files and names per file the contract that survives, and a single test binary that cannot compile in halves is split into two seven-file halves (14c/14d) rather than one fourteen-file sweep.

### D5 — The evidence harness is the fixture, not a status field (was B5)

The former non-zero `python -c … sys.exit('BLOCKED …')` hold is deleted. Its replacement is the baseline fixture plus its validator, which fail when the baseline is missing, stale (input digest mismatch) or incomplete (a case absent). Capture-time determinism was the recorder's own condition and is no longer re-derivable from this tree: the recorder was retired with the producer it drove (Step 14f), and AC-1's approved 2026-10-23 amendment scopes the validator to the committed artifact rather than a re-run. Nothing in this packet reads a gate status to decide eligibility, so no synthetic status can substitute for evidence.

### D6 — Failure-path reachability is module-owned (new)

AC-N2's `57401`/`57410`/`57411` are produced **inside** the module: `57401` comes from the inherited `PreparedPlanView::require` contract, and `57410`/`57411` come from the module's own piece decoder. There is no host-side surface that can hand the real consumer a missing, malformed or stale-version piece: the store stages opaque bytes that only the module decodes, and the runtime facade exposes no piece injector. A host-side injection API would therefore have to bypass the module decoder to manufacture the failure, which would test the injector rather than the deployed artifact. The packet instead adds a **module-owned, config-gated diagnostic publication mode**, because the module is the only owner of the code path the criterion protects.

- **Key**: the module-scoped `prepared_plan_diagnostic` is declared in `lightning-infill.toml` as `type = "enum"`, `values = ["none", "missing_piece", "malformed_piece", "unsupported_version", "empty_plan"]`, `default = "none"`, `advanced = true`. It is a snake_case config key like every other declared key; the ordinary consumer ignores it, and no host code reads it.
- **Read point**: preparation reads it once from the first committed `PreparationRegionConfig.config` (all regions carry the registry-seeded default). It is deliberately **excluded** from the five-scalar agreement check: it is a diagnostic, not a planner scalar, and a per-region difference in it must not produce `57412`.
- **Application point**: only after the plan is computed. `none` publishes the normal pieces and scene. `missing_piece` plans normally but omits the piece for the topmost planned layer, so the real consumer's `require` returns `57401`. `malformed_piece` stages a body the module decoder rejects, returning `57410`. `unsupported_version` stages a well-formed header with an unsupported format version, returning `57411`. `empty_plan` encodes one empty `KernelPlan` per layer and publishes an empty `lightning-plan` scene (`primitives: []`, classes declared), which is the `Ready`/no-work case and AC-4's explicit empty scene.
- **Why it is not a planning change**: the key never reaches the kernel, never alters an input scalar, and never changes a piece or scene on the `none` path. AC-2/AC-3 run with the default. The mode is a diagnostic contract the module owns, and its failure outputs are the module's own error codes.
- **Test-quality justification**: the protected surface is the module's decoder and `require` contract. The mode makes those surfaces reachable through the deployed artifact instead of through a mock; it is inert by default; and every assertion names the module code, the fatal flag and the message. A host-side injector would be a fake of the very boundary under test. The AC-N2 test carries the waiver `// test-quality: the diagnostic key is the only real-adapter trigger for the module-owned decoder failure paths named by AC-N2; it is inert at its default and never reaches the kernel.` The AC-N3 empty/foreign test carries a matching waiver for the `empty_plan` trigger.

**The foreign/disposed-owner leg needs no new API.** `PreparedOwnerStore`, `freeze_native`, `NativePreparationArtifact::Prepared`, `create_owner`, `begin`, `finish`, `open` and `PreparedPieceHandle::read` are already public. The harness can freeze the module's real prepared pair, stage a piece, open a handle, dispose the owner or the store, and assert `AccessDenied` on the subsequent read. That is the store's own authority contract, not a test-only path.

## Behavioural Equivalence Contract

Equivalence is asserted at three points, and the distinction matters:

1. **Input identity** — the baseline records `sha256` of the exact inputs the producer consumed, computed over the constructed `Vec<SliceIR>` and the constructed `ResolvedConfig` (all five scalars, `sparse_fill_holder` included); a differing input hash is a plumbing defect, not an algorithm verdict. **Implemented note (AC-2):** the arm's digest is computed over the `SliceRunOptions::config_overrides` the run is handed, not over a `ResolvedConfig` read back from the adapter. A dropped or rewritten override therefore diverges — the plumbing defect this point exists to catch — but a defect *inside* the adapter's resolution of those already-supplied scalars would not move the digest, because the module publishes no resolved-config view. That residual limit is recorded in `docs/07_implementation_status.md` TASK-577 and Step 14f.
2. **Plan identity** — key set equality with full identity including ordered `variant_chain`, edge multiset equality with multiplicity, grounding/root witness set equality.
3. **Output identity** — per caller, the emitted segment multiset, role `ExtrusionRole::SparseInfill`, widths, and the `variant_chain` that reached the emitted region.

## Controlling Code Paths (current, verified)

- **Producer**: `crates/slicer-runtime/src/builtins/lightning_tree_producer.rs::{LIGHTNING_TREE_PRODUCER, commit_lightning_tree_ir_builtin}` declares `host:lightning_tree` on stage `PrePass::LightningTreeGen`, `ir_writes: &["LightningTreeIR"]`, and calls `slicer_core::algos::lightning::generate_lightning_trees` with the print-wide `default_resolved_config`. Wired directly in `crates/slicer-runtime/src/prepass.rs` via `run_builtin_stage`, gated by the `sparse_fill_holder` string; `runtime_builtins()` deliberately does not register it.
- **Algorithm**: `crates/slicer-core/src/algos/lightning/` — `mod.rs` (`generate_lightning_trees(&[SliceIR], &ResolvedConfig) -> Result<Arc<LightningTreeIR>, LightningTreeError>`), `generator.rs` (`Generator::generate_trees`, `committed_segments_for_layer`), `layer.rs`, `tree_node.rs` (`Node`/`NodeRef`), `distance_field.rs` (`DistanceField`), `error.rs`; behind `#[cfg(feature = "host-algos")]` in `crates/slicer-core/src/algos/mod.rs`. ## Diagnostic Representation

Declare only `planning_geometry`; scene id `lightning-plan`. `planning_domain` uses `PreparationProjectionGeometry::Polygon { polygon: ExPolygon, filled: bool }` with holes preserved; `tree_branch` uses `Polyline` with open paths; `tree_root` and `grounding` use `Point(Point2)` with labels carrying source/checkpoint identity. Primitive ids are deterministic and scene-local, derived from the plan key plus an edge or node index — never an assumed array position. A requested empty scene declares its classes and publishes `primitives: []`; a requested-but-missing scene is a named row-06 error. Layer Z comes from the host schedule, never from module payload. Diagnostic classes are not extrusion roles and carry no width.

Pieces and scene are built from the same in-memory `KernelPlan` inside one `prepare_print` call and share the transaction: a projection failure fails the preparation.

## Architecture Constraints

- Same selected artifact and frozen identity; one `prepare_print` per owner before any consumer. Host owns transport/access/lifetime only.
- No `LayerArena` survives preparation. `retained_bytes == 0` after success, failure and cancellation. Disposal reports `Busy` for active guards; callers join, never spin or revoke.
- **Planning numeric logic is frozen, and the permitted deltas are enumerated.** The relocated code may differ from `crates/slicer-core/src/algos/lightning/` only in: (a) file location; (b) the plan-type import — `kernel::plan::{KernelPlan, PlanEntry}` instead of `slicer_ir::{LightningTreeIR, LightningTreeEntry}`; (c) `crate::` → `slicer_core::` on the ungated helper paths listed above; (d) the error type's own name and path; (e) the NET-NEW `planning_input.rs` adapter, which supplies inputs and changes no arithmetic; (f) doc comments that named the moved types now name `KernelPlan`/`PlanEntry`, because AC-5 greps the module's own `src/` as a public-name leak check — comment text only, no code token changes. Everything else in `generator.rs`, `layer.rs`, `tree_node.rs`, `distance_field.rs`, `error.rs` and the computation in `mod.rs` — layer iteration order, domain and parameter derivation, grounding, clipping, and the `sparse_fill_holder` branch — is unchanged. Any seventh difference is a stop, not a review note. AC-2/AC-3 are the proof, not the intent.
- **Deletion order is compile-forced.** The public plan types leave `crates/slicer-ir/src/slice_ir.rs` only after their last consumer is gone: the host producer (Step 10b) and then the host algorithm copy (Step 10c), which is why the IR step (12a) follows them. No step deletes the IR while `crates/slicer-core/src/algos/lightning/mod.rs` still returns it; that would be a compile-fatal contradiction, not a migration.
- After retirement, nothing under `crates/slicer-runtime/**` or `crates/slicer-wasm-host/**` references the lightning kernel; the only production caller is the module.
- No speculative public version bump. Deleting the WIT package is an affected-contract change: regenerate affected bindings and rebuild guests.

## Locked Invariants and Risks

- No reference contamination: the baseline is read only by the comparator; planning reads typed inputs and config, nothing else.
- No plan injection: tests instantiate the real module and let it prepare.
- Multiplicity survives unions, splits and subtractions; a set comparison is a defect even when it passes.
- Empty successful preparation is `Ready`/no-work; a missing piece is an error, never an empty result.
- **Risk — the input adaptation changes a value.** `SliceIR` regions and typed `PreparationRegion` values may differ (notably `sparse_infill_area` after `sync_perimeter_infill_areas_into_slice`), and the planner's config reads are print-wide while the typed config reads are per region. The recorded input digest exposes both; the agreement check on the five scalars turns the second into a named `57412` failure instead of a silent pick, and the fix belongs in the input contract. If it cannot be expressed there the packet stops for re-approval.
- **Risk — relocation is not behaviour-free.** The enumerated path/import deltas are permitted only if equivalence holds. If equivalence fails for a reason that cannot be fixed without changing a planning decision, the packet stops.
- **Risk — retirement is wide.** The four legacy symbols are named across many files, most of them tests and docs, plus a whole WIT package whose expectations are hardcoded in `xtask`. The partition bounds ordinary production steps to three files, allows one declared atomic blast radius per symbol removal (11c at six), caps a test-retarget batch at six test files, and splits an indivisible test binary into two named seven-file halves (14c/14d); the risk this controls is compiler-driven cleanup that drops an unrelated assertion.
