# Packet Contract: top-fill-order-and-calibration-order

## Goal

Make `top_surface_fill_order`, `bottom_surface_fill_order`, and `calib_flowrate_topinfill_special_order` drive real ordering decisions on the center-based surface fills, by adding a shared `slicer-sdk` ordering helper that emits an `order_lock` block and by extending the host's order-lock remap and validation from `InfillRegion::sparse_infill` to all four of its extrusion vectors.

## Scope Boundaries

This packet does **not** create any fill module: `archimedean-chords-infill`, `concentric-infill`, and `octagram-spiral-infill` are shipped by packet 264 and are a forward dependency here. It adds one `slicer-sdk` module (surface fill ordering + block locking), extends three functions in `crates/slicer-runtime/src/layer_executor.rs` to cover `solid_infill`, `ironing`, and `internal_bridge_infill`, and appends `[config.schema]` entries plus call sites to the three center-based modules 264 creates. It adds no WIT interface, no IR field, no `ResolvedConfig` field, and no schema-version bump — `ExtrusionPath3D::order_lock` already exists at IR schema `1.4.0`.

## Acceptance Criteria

- **AC-1. Given** a source polyline and its clipped fragments, **when** `slicer_sdk::surface_fill_order::order_center_based_fragments` is called with `SurfaceFillOrder::Default` and `calibration_special_order = false`, **then** the returned fragment order is exactly the nearest-neighbour chain the helper produces today for that input and no fragment is reversed — the helper is order-neutral at its default, so a module adopting it changes nothing until a non-default key is set. | `cargo test -p slicer-sdk --test surface_fill_order_tdd default_order_is_neutral 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-2. Given** the same source polyline and fragments, **when** `order_center_based_fragments` is called with `SurfaceFillOrder::Default` and `calibration_special_order = true`, **then** the single longest fragment by path length is emitted **last**, every other fragment precedes it in nearest-neighbour chain order, and the longest fragment's first point is closer to the origin of the source polyline than its last point (inside-out) — reversing it when it was not. This mirrors canonical `FillPlanePath::fill_surface`'s `is_flow_calib` branch (`std::max_element` on `Polyline::length`, reverse when `first_point().squaredNorm() > last_point().squaredNorm()`, `chain_polylines` the remainder, then `push_back` the spiral). | `cargo test -p slicer-sdk --test surface_fill_order_tdd calibration_special_order_emits_spiral_last_inside_out 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-3. Given** the same source polyline and fragments, **when** `order_center_based_fragments` is called with `SurfaceFillOrder::Outward` and then `SurfaceFillOrder::Inward`, **then** `Outward` returns the fragments in the order they appear along the source polyline (which runs from the center outwards) and `Inward` returns that sequence reversed with every fragment individually reversed — canonical `FillPlanePath::fill_surface`'s non-Default branch, which calls `restore_source_path_order` (`ClipperUtils.cpp`) and then flips both the sequence and each polyline for `Inward`. Euclidean distance from the centroid must NOT be used as the sort key. | `cargo test -p slicer-sdk --test surface_fill_order_tdd outward_and_inward_follow_source_path 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-4. Given** a slice of `ExtrusionPath3D` and an `OrderLockAllocator`, **when** `slicer_sdk::surface_fill_order::lock_block` is called, **then** every path in the slice carries the **same** `order_lock` tag (one contiguous block, which is what `coalesce_locked_candidates` in `path-optimization-default` collapses into a single non-reversible candidate), the tag has bit 63 clear (invocation-local, awaiting host remap), and calling it twice with the same allocator yields two distinct tags. | `cargo test -p slicer-sdk --test surface_fill_order_tdd lock_block_assigns_one_shared_local_tag 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-5. Given** an `InfillIR` whose regions carry local order-lock tags on `solid_infill`, `ironing`, and `internal_bridge_infill` as well as `sparse_infill`, **when** `remap_infill_order_locks_from` runs, **then** every tag in all four vectors is rewritten to a global tag (bit 63 set), the global tags are unique across all four vectors of all regions, and `next_global_infill_tag` computes its starting value from all four vectors — so a tag on `solid_infill` can never collide with one on `sparse_infill`. | `cargo test -p slicer-runtime --test executor order_lock_remap_covers_all_infill_vectors 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-6. Given** a previous `InfillIR` with a locked two-path block in `solid_infill` and a replacement in which that block is split, reordered, or dropped, **when** `validate_infill_order_locks` runs, **then** it returns `Err` naming the tag, exactly as it already does for `sparse_infill`; and given a replacement that preserves the block contiguously, it returns `Ok`. The same holds for a locked block in `ironing` and in `internal_bridge_infill`. | `cargo test -p slicer-runtime --test executor order_lock_validation_covers_all_infill_vectors 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-7. Given** `archimedean-chords-infill.toml`, **when** the schema guard parses it, **then** it declares `top_surface_fill_order` (`type = "string"`, `default = "default"`, allowed values `default` / `outward` / `inward`), `bottom_surface_fill_order` (same shape and default), and `calib_flowrate_topinfill_special_order` (`type = "bool"`, `default = false`), each with a `group`, a `display` name, and a `description` naming its canonical consumer; and `concentric-infill.toml` and `octagram-spiral-infill.toml` declare the two fill-order keys but **not** the calibration key, because canonical's `is_flow_calib` branch is gated on `dynamic_cast<FillArchimedeanChords*>(this)` and the key would be declaration-only on the other two (map Authoring rule 1). | `cargo test -p archimedean-chords-infill --test surface_fill_order_config_schema_tdd 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-8. Given** an `archimedean-chords-infill` run over the annulus fixture (a square with a square hole, so the clipped spiral yields more than one fragment) producing `TopSolidInfill`, **when** `calib_flowrate_topinfill_special_order = true` and `top_surface_fill_order = "default"`, **then** the emitted `solid_infill` paths for that region are the calibration order of AC-2, every one of them carries the same non-`None` `order_lock` tag, and at `calib_flowrate_topinfill_special_order = false` (the default) the paths carry `order_lock: None` and are in the helper's Default order — a behaviour change asserted at a non-default value. | `cargo test -p archimedean-chords-infill --test calibration_order_tdd 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-9. Given** the same annulus fixture and `calib_flowrate_topinfill_special_order = false`, **when** `top_surface_fill_order = "outward"` and then `"inward"` are set, **then** the emitted `TopSolidInfill` path order differs between the two values and both differ from `"default"`, and every emitted path carries the same non-`None` `order_lock` tag in both non-default cases — a forced fill order must survive `path-optimization-default`, which is exactly why canonical sets `no_sort` and `can_reverse = false` for it. The same assertion holds for `bottom_surface_fill_order` against `BottomSolidInfill`. | `cargo test -p archimedean-chords-infill --test calibration_order_tdd 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-10. Given** a layer whose `solid_infill` carries a locked block from `archimedean-chords-infill`, **when** `path-optimization-default` runs its `group_then_nearest_neighbor` ordering, **then** the block appears in the final entity order contiguously, in its original relative sequence, with no entity reversed — `coalesce_locked_candidates` must see the block through `OrderedEntityView::order_lock`, which requires the host remap of AC-5 to have promoted the tag. | `cargo test -p slicer-runtime --test contract solid_infill_order_lock_survives_path_optimization 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-11. Given** a per-object overlay `object_config:<id>:calib_flowrate_topinfill_special_order = "1"` (the shape an Orca flow-rate-calibration 3MF carries, since canonical sets the key on `_obj->config` in the Plater's calibration object generator), **when** the pipeline resolves that object's config, **then** the key arrives at `archimedean-chords-infill`'s `SliceRegionView::config()` as a boolean true for that object only, and a second object in the same slice sees the default `false`. | `cargo test -p slicer-scheduler --test scheduler_integration per_object_calibration_order_flag 2>&1 | tee target/test-output.log | grep -E "^test result"`
- **AC-12. Given** `cargo xtask gen-config-docs` has run, **then** `docs/15_config_keys_reference.md`'s generated module-key table carries `calib_flowrate_topinfill_special_order` exactly once with owner `archimedean-chords-infill`, and `top_surface_fill_order` and `bottom_surface_fill_order` three times each (one row per center-based module). | `cargo xtask gen-config-docs --check && [ "$(rg -c '^\| `calib_flowrate_topinfill_special_order`' docs/15_config_keys_reference.md)" = "1" ]; echo "exit=$?"`
- **AC-13. Given** `docs/02_ir_schemas.md`, **when** its `ExtrusionPath3D.order_lock` documentation is read, **then** it states that the host remap and cross-module validation cover all four `InfillRegion` extrusion vectors (`sparse_infill`, `solid_infill`, `ironing`, `internal_bridge_infill`), replacing the prior sparse-only scope, and that the schema version is unchanged because no field was added. | `rg -q 'internal_bridge_infill' docs/02_ir_schemas.md && rg -q 'order_lock' docs/02_ir_schemas.md; echo "exit=$?"`

- **AC-14. Given** the annulus fixture with `top_surface_fill_order = "inward"` (so the top fill is locked) and sparse infill present in the same region, **when** the infill linker runs, **then** (a) every locked top-fill path's swept footprint lies inside that region's top-surface partition polygon — the self-clipping guarantee ADR-0063 places on the producer — and (b) the region's sparse-infill paths are **unchanged** from the same slice with `top_surface_fill_order = "default"`, because the ADR-0063 carve differences the locked footprint out of untagged fill of the same region and top fill must not overlap sparse infill. A non-empty carve here means an ordering key silently changed sparse geometry; that is out of scope and the implementer must stop rather than absorb it. | `cargo test -p slicer-runtime --test contract solid_infill_order_lock_survives_path_optimization 2>&1 | tee target/test-output.log | grep -E "^test result"`
