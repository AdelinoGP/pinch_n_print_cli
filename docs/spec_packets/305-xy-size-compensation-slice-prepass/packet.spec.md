# Packet Contract: 305-xy-size-compensation-slice-prepass

## Goal

Make the P88 key pair drive real XY size compensation at parity with canonical `PrintObject::_shrink_contour_holes` and its two-pass application inside `PrintObject::slice_volumes` (`PrintObjectSlice.cpp`) — grow or shrink each layer's outer contours and its holes by independent signed millimetre deltas, positive pass then negative pass, with canonical's separate single-region and multi-region-merge branches — delivered as a new host prepass built-in `host:xy_size_compensation` on a new host-only stage `PrePass::XySizeCompensation` between `PrePass::Slice` and `PrePass::OverhangAnnotation`.

## Scope Boundaries

P88 is two Tier-C queue keys, `xy_contour_compensation` and `xy_hole_compensation`, whose only occurrence in any **code** path in this tree is the pair of `ORCA_CONFIG_PADDING` twins in `crates/slicer-gcode/src/serialize.rs` — map rule 2 non-evidence, and a file this packet never opens. The remaining occurrences are all documentation (the gap source, the gap-inventory assets, packet 303's cross-reference); none is a read site. Both pass map rule 3: canonical reads them in the slicing pipeline, in `PrintObject::slice_volumes` via `PrintObject::_shrink_contour_holes` (`PrintObjectSlice.cpp`), and they are `PrintObjectConfig` members (`PrintConfig.hpp`), i.e. per-object keys. The tier table's owner — `new contour-compensation module`, Tier C — is **corrected** here under ticket 27's re-derive-the-owner rule, for three independently sufficient reasons set out in `requirements.md` §Problem Statement: the pass must run before the prepass consumers of the slice footprint, a second coarse `SliceIR` mutator cannot be ordered against packet 303's on `Layer::SlicePostProcess` without a scheduler cycle, and canonical's positive-growth branch merges a whole object's layer rather than a single region. Rule 4 does not fire: the two keys are scalar parameters of one geometric pass, not an enum selecting between competing algorithms, so no claim is minted. Canonical declares neither a `min` nor a `max` on either key and this packet adds none (ticket 113). The queue count is unchanged at 409; no supporting non-queue key is carried. Canonical's two painted-object suppressions and their `active_step_add_warning` calls are **not** ported — see `requirements.md` §Out of Scope and the deviation row.
