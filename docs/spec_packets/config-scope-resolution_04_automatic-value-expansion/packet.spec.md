# Packet Contract: automatic-value-expansion

## Goal

Implement Phase B automatic-value expansion after each applicable scope resolution and before interning or `ConfigView` binding, using a registry-driven `ExpansionContext` for nozzle and tool bases, one width-family implementation, typed percent bases including the overhang-speed family, and the two config-only `-1 = auto` mirrors.

## Scope Boundaries

This packet owns expansion of config-only placeholders in every already-merged configuration currently materialized by the runtime: global/default, object, tool, and paint-semantic maps. Covered values are `line_width = 0`, `support_line_width = 0`, values whose `RegistryEntry.base_key` identifies one scope-resolved absolute config base, all four `overhang_1_4_speed` through `overhang_4_4_speed` percent forms over typed base `outer_wall_speed`, `support_interface_bottom_layers = -1`, and `support_bottom_interface_spacing = -1`. It centralizes those rules, makes `resolve_role_width` dispatch over already-expanded bases, and removes the duplicate support-width resolver and guest-side mirror fallbacks. Canonical `PrintConfig.cpp::PrintConfigDef::init_fff_params` declares the overhang family as float-or-percent over `outer_wall_speed`; numeric `0` remains the existing no-override value interpreted against the actual extrusion-role reference speed. Queue row 5 must call the same export after its future layer-range/modifier scope-delta merges; queue row 10 retains only emitter volumetric `0 = auto`, geometry/per-move rules, and other context-dependent `-1` sentinels.

## Prerequisites and Blockers

- Depends on: **unsatisfied FORWARD-DEP** on active packet `config-scope-resolution_01_config-schema-registry`; active status is not completion, so the exact exports must still be reconciled against implemented code as required by `design.md` §Open Questions.
- Unblocks: queue row 5 (`config-scope-resolution_05_scope-resolution-module`) and queue row 10 (`config-scope-resolution_10_remaining-automatic-values`).
- Activation blockers: active packet 1 must complete and its implemented exports must match the accepted FORWARD-DEP names and shapes before this packet can activate; there are no additional packet-local blockers.
