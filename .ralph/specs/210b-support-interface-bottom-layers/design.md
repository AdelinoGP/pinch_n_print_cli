| Symbol | Expected shape after `210a` | Used here for |
| --- | --- | --- |
| `split_column_into_chains(entries: &[SupportPlanEntry], column: &[usize]) -> Vec<(usize, usize)>` | private; half-open ranges into `column`; returns **every** range including those shorter than 3 | the chain iteration in `densify_bottom_interface` (its second caller; AC-19) |
| `point_in_any_expoly(polygons: &[ExPolygon], p: Point2) -> bool` | exact integer membership over a whole `ExPolygon`: inside the contour and outside every hole (`210a` AC-N8 pins the hole term) | **the model-landing test** |
| `first_point_xyw(entry: &SupportPlanEntry) -> Option<(Point2, f32)>` | position in **units**, width in mm, **no `z`** | the chain's XY and the band radius |
| `push_interface_scan_lines(out, centre: Point2, z: f32, half_units: i64, width_mm: f32, spacing_units: i64, parity: i32, avoidance_polys, collision_polys)` | centre/half/spacing in units; `z` and width in `f32` mm | band emission |
| `LayerCollisionCache` | **one** struct carrying both `collision_polys: Vec<ExPolygon>` and `avoidance_polys: Vec<ExPolygon>` | the landing test reads `collision_polys`; the emitter reads `avoidance_polys` — from the *same* cache entry |

Because `first_point_xyw` returns no `z`, `densify_bottom_interface` reads `z` directly from `entry.branch_segments.first()?.first()?.z`. That is a consequence of `210a`'s signature, not a choice made here.

**The membership helper is `point_in_any_expoly`, and the type argument is decisive.** `LayerCollisionCache.collision_polys` is `Vec<ExPolygon>` — `slicer_ir::ExPolygon { contour: Polygon, holes: Vec<Polygon> }`, each `Polygon` carrying `points: Vec<Point2>` (`crates/slicer-ir/src/slice_ir.rs`). `210a`'s ring-level `point_in_polygon_units(poly: &[Point2], p: Point2)` cannot be applied to it: the types do not connect. The tempting workaround, `collision_polys.iter().any(|ex| point_in_polygon_units(&ex.contour.points, p))`, compiles and is **wrong** — it treats a hole as solid, so a chain whose landing XY sits inside a model hole is classified "on model" and gets a floor band drawn into empty space inside the model. `point_in_any_expoly` already composes the correct answer (contour ring, then each hole ring) and is `210a`'s exported model-landing helper. Call it; do not re-derive it, and do not reach past it into `point_in_polygon_units`.

## Architecture Constraints

- **`smooth_branches` is not reopened.** `210a` rewrote it once; this packet adds only a second caller to `split_column_into_chains`. If an edit to `smooth_branches` seems necessary, the extraction contract was violated in `210a` — stop and report rather than editing.
- **The bottom band's `z`.** `push_interface_scan_lines` requires `z: f32`, and the band spans several layers. The `z` for each band layer is read from **that layer's own entry** — its first `Point3WithWidth.z` — never from the landing entry's. `branch_points_match_entry_layer_z` (AC-17) fails immediately on the wrong choice.
- **The landing test's accepted approximation.** Canonical `TreeSupport::draw_circles` searches *every* object layer below a support component for `stTop`/`stBottom` surfaces and treats the lowest such intersection as the true contact. `SupportGeometryView.entries[..].outlines` carries no surface classification, so PnP asks the reduced question: *does the chain's lowest emitted layer `L_end` have model footprint directly beneath it at `L_end - 1`?* Correct whenever a chain stops because it hit the model (the code-1002 drop condition is literally "the moved target is inside `collision_polys`"), and correct for a chain reaching layer 0 on open plate. It differs for a chain stopped by the per-layer branch cap directly above model geometry. This and the cap-truncation false positive are filed as a **new `Open` deviation row**, not buried in `DEV-129`'s closure cell.
- **The `support_on_build_plate_only` guard is unobservable end-to-end, so it is extracted.** `plan_for_object` rejects to-model contacts at creation with `if self.support_on_build_plate_only && !to_buildplate { continue }` — **twice**, at both contact-admission sites. Under that flag every surviving chain is a to-buildplate chain that reaches global layer 0, and `densify_bottom_interface`'s `L_end == 0` early return already skips those. A planner-level assertion of the form "with `support_on_build_plate_only = true`, no band appears anywhere" therefore holds *whether or not the guard exists*, and cannot detect its deletion. The resolution is to lift the whole call-site condition into a pure `pub fn should_densify_bottom_interface(support_on_build_plate_only: bool, bottom_n: u32, interface_spacing_mm: f32) -> bool` and test it directly (AC-12), with a static check that it is actually wired (AC-12b). This makes the guard observable without weakening anything.
- **Two independent skip reasons, two independent criteria.** `densify_bottom_interface` skips a chain when `L_end == 0` (early return) *and* when the landing XY is outside `collision_cache[L_end - 1].collision_polys` (`found_contact == false`). The early return fires first, so a fixture whose chain reaches global layer 0 can never exercise the collision test. AC-11 (synthetic chain with `L_end >= 1`, no footprint beneath) and AC-11b (`L_end == 0`) are separate cases precisely so that deleting either guard fails exactly one of them. Both are direct in-file unit tests on `densify_bottom_interface`, because only a hand-built `entries` / `collision_cache` pair can hold "`L_end >= 1`" and "no model footprint beneath" simultaneously — the planner will keep propagating such a chain down to layer 0.

## Code Change Surface

Selected approach: **detect the landing from the emitted plan plus the per-layer collision cache, densify upward, and retire the stub — all as additive code on top of `210a`'s migrated shapes.**

- `SupportPlanner` — new field `support_interface_bottom_layers: i32`. **Struct-literal blast radius (grep-verified, complete): two sites** — `Ok(Self { … })` at the end of `from_config`, and `default_planner()` in the in-file `#[cfg(test)] mod tests`. `SupportPlanner` is `pub`, but no external test constructs it by literal — all files under `modules/core-modules/support-planner/tests/` go through `SupportPlanner::from_config(&config)`.
- `from_config` — parse `support_interface_bottom_layers` with the same `Int`/`Float`/default arm shape as the adjacent `support_interface_top_layers`, defaulting to `-1`.
- `run_support_geometry` — delete the `interface_bottom_layers` local and the whole code-1003 `push_diagnostic` block including its `// ── Packet 118 D11 …` banner. `_config` stays (trait signature) and may become fully unused; keep the underscore.
- `resolve_interface_bottom_layers(bottom_layers: i32, top_layers: i32) -> u32` — **net-new, `pub`.** `let n = if bottom_layers < 0 { top_layers } else { bottom_layers }; n.max(0) as u32`. Doc comment cites canonical `number_of_support_interface_bottom_layers` (`SupportParameters.hpp`) by function + file.
- `should_densify_bottom_interface(support_on_build_plate_only: bool, bottom_n: u32, interface_spacing_mm: f32) -> bool` — **net-new, `pub`.** `!support_on_build_plate_only && bottom_n > 0 && interface_spacing_mm > 0.0`. Public solely so AC-12 can pin the guard that is otherwise unobservable (see §Architecture Constraints). The call site in `plan_for_object` must call it rather than re-inlining the three conditions — AC-12b requires an invocation **within `plan_for_object`'s own body** (a tempered-dot PCRE that cannot cross the body's closing `\n    }`), in addition to the declaration and a ≥3 whole-file mention count.
- `densify_bottom_interface(entries: &mut [SupportPlanEntry], collision_cache: &[LayerCollisionCache], bottom_n: u32, branch_distance_mm: f32, interface_spacing_mm: f32)` — **net-new, private.** Note the parameter list carries **one** cache: `LayerCollisionCache` holds `collision_polys` *and* `avoidance_polys` on the same struct, so there is no separate `avoidance_cache` argument (an earlier draft of this design invented one; it has no counterpart in the tree). Signature is otherwise not locked (see §Locked Assumptions); a context struct is acceptable if `clippy::too_many_arguments` fires. Behaviour: for each `(object_id, region_id)` column from `group_branches_into_columns` and each range from `split_column_into_chains` (no length filter): entries are sorted descending by `global_layer_index`, so the range's last index is the lowest layer `L_end`. Skip if `L_end == 0` (AC-11b). Read that entry's position via `first_point_xyw` and test it against `collision_cache[L_end - 1].collision_polys` with `point_in_any_expoly` (that field is `Vec<ExPolygon>`; the ring-level `point_in_polygon_units` does not type-check against it and a `.contour.points` workaround would drop hole handling); if outside, skip (AC-11, canonical's `found_contact == false` path). Otherwise walk the range upward for `bottom_n` entries and call `push_interface_scan_lines` on each, using **that entry's own** `z` (from `entry.branch_segments.first()?.first()?.z`) and its own emitted `width`, with `radius = width / 2.0`, `half_units = mm_to_units(radius + branch_distance_mm * 0.5)`, `spacing_units = mm_to_units(interface_spacing_mm)`, `parity = global_layer_index.rem_euclid(2)`, and `collision_cache[layer].avoidance_polys` / `.collision_polys` from that layer's own cache entry, exactly as the top band does.
- `plan_for_object` — after `smooth_branches(&mut entries_in_order, 100);`, add `let bottom_n = resolve_interface_bottom_layers(self.support_interface_bottom_layers, self.support_interface_top_layers); if should_densify_bottom_interface(self.support_on_build_plate_only, bottom_n, self.tree_support_interface_spacing_mm) { densify_bottom_interface(…); }`.
- `support-planner.toml` — delete the `# Not yet implemented — see docs/specs/support-modules-orca-port.md` line above `[config.schema.support_interface_bottom_layers]`. Nothing else changes.
- `tests/diagnostics_tdd.rs` — rewrite `interface_bottom_layers_emits_one_typed_diagnostic` (value 3 ⇒ **zero** code-1003 records; keep the `assert_eq!(ibl_diags.len(), …)` shape at 0 and keep the observed-code dump in the failure message) and `interface_bottom_layers_default_emits_no_typed_diagnostic` (unchanged in outcome, re-commented to say the code is **retired** rather than unreached). The `let d = ibl_diags[0];` binding and the severity/`layer` assertions that follow it are **deleted** — they are only reachable when the count is 1, and AC-N4 greps for their absence plus the word `retired`, because without those two clauses the criterion is green both before and after the rewrite. ### AC-14's baseline, and why the merged packet's was wrong

The merged packet asserted that a `support_interface_bottom_layers = 0` run produced the same per-layer `branch_segments` counts as a `support_on_build_plate_only = true` run. **That comparison fails on a correct implementation.** `support_on_build_plate_only` rejects to-model contacts at creation, and AC-10's fixture must contain a model-landing chain, so that chain is absent from the `support_on_build_plate_only` run entirely — the two entry sets differ for reasons that have nothing to do with bands.

The replacement uses two anchors that both live inside the *same* run:

1. **Absolute (proves `0` emits nothing):** in the `bottom = 0` run, the landing entry `L_end` carries exactly the same `branch_segments.len()` as a mid-chain, non-interface entry of the same chain. If `0` produced even a one-layer band, this fails.
2. **Differential (proves `0` is not a fallback):** the same fixture at `bottom = -1` has strictly more at `L_end` and `L_end + 1` (top count = 2), and at `bottom = 3` strictly more at `L_end` … `L_end + 2`. An implementation that treats `0` as "fall back to top" makes anchor 1 fail while these still pass — so the pair is jointly discriminating.

### Rejected alternatives

- **Keeping the merged 210 (210 + 211 in one packet).** Reviewed and ruled `SIZE: must decompose`; re-split by user decision 2026-08-07. The `smooth_branches` collision that motivated the merge is confined to `210a`'s Step 3.
- **Reviving `.ralph/specs/211-support-interface-bottom-layers/` instead of creating this directory.** Rejected: 211's `superseded_by` correctly records that it was absorbed by the merged `210`, and its stated code surface is written against pre-migration `f32` signatures. Reviving it would either falsify the history or require rewriting every signature in it. The directory stays frozen; this packet records the chain in `requirements.md` §Provenance.
- **Add `dist_to_bottom: Option<u32>` to `PlannedSupportNode` and fill it in a second bottom-up pass.** Node sets are consumed layer by layer (`active_nodes = next_nodes`) and never retained, so there is nothing left to walk. Retaining them means keeping every layer's node vector alive for a whole object — a real memory change inside a WASM guest — to recompute what the emitted entries already contain.
- **Record a landing event at the code-1002 drop site into a side table, then match chains against it.** More faithful to *why* a chain stopped, but matching a recorded pre-smoothing position against a post-smoothing endpoint needs a distance tolerance, and a tolerance is exactly the kind of fuzzy join that rots. The direct collision test is exact and deterministic.
- **Emit the band inside the layer loop with a look-ahead of the collision cache.** Requires knowing at layer L that the chain terminates at L — i.e. running the propagation loop twice.
- **Mark band segments with a new `SupportPlanEntry` field or `ExtrusionRole`.** Would make the band ACs absolute rather than differential, but it is an IR/WIT change with cross-crate blast radius for a behaviour that is observable differentially. Revisit only if a downstream consumer needs to distinguish floor from base.
- **Duplicate the gap walk instead of calling `210a`'s helper.** Recreates `DEV-127`'s "two drifted copies" failure mode inside a single file. AC-19 forbids it.
- **Keep code 1003 as an informational note.** `DEV-129`'s stated failure mode is "a warning and unchanged geometry". Once the geometry exists the warning is false, and a false warning is worse than none.
- **Leave the `support_on_build_plate_only` guard inline and keep the end-to-end AC.** Rejected: that AC cannot fail (see §Architecture Constraints). Extracting the predicate is the only way to make the guard falsifiable without adding an IR marker.

## Locked Assumptions and Invariants

- **Locked:** `0` means "no floor band" and never falls back to the top count. Only `< 0` triggers the fallback. AC-14's absolute anchor is the enforcement.
- **Locked (behaviour change):** `support_interface_bottom_layers = -1` — the shipped default — now resolves to `support_interface_top_layers` (default 2) and therefore produces bottom bands on every default slice with model-landing supports. This is canonical, and `CLAUDE.md` puts canonical parity above baseline stability. Reversible only by changing the manifest default, which would itself be a divergence.
- **Locked:** bands attach only where a chain lands on model geometry, never when `support_on_build_plate_only` is true, and always **upward** over `[L_end, L_end + bottom_n)` — never below `L_end`.
- **Locked:** each band layer's `z` comes from that layer's own entry. AC-17's `branch_points_match_entry_layer_z` is the enforcement.
- **Locked:** the bottom band uses the same scan-line emitter, half-extent formula, parity rule and avoidance/collision clipping as the top band, reading both poly sets from the **same** `LayerCollisionCache` entry. Divergence between the two bands is a defect, not a feature.
- **Locked:** the call-site guard is the pure `should_densify_bottom_interface` predicate, not three inline conditions. Re-inlining it makes AC-12 untestable and AC-12b red — AC-12b's first clause searches only `plan_for_object`'s body, so defining and unit-testing the predicate while re-inlining the conditions at the call site does **not** satisfy it (verified on synthetic wired/re-inlined harnesses).
- **Locked:** `smooth_branches` is not reopened by this packet.
- **Not locked:** `densify_bottom_interface`'s exact parameter list. It is private; a small context struct is acceptable if `clippy::too_many_arguments` fires (`push_interface_scan_lines` already carries an `#[allow]` for precisely this). What *is* locked is that it takes **one** cache parameter — `LayerCollisionCache` carries both poly sets.

## Risks and Tradeoffs

- **Default output moves.** Every default slice with model-landing supports gains two densified layers. Both golden pairs and any G-code baseline including tree supports may shift; re-record to the canonical-correct output, never revert the behaviour to keep a baseline green (`CLAUDE.md` §Test Discipline). Drift here is *expected*, which is why AC-N7b clause (c) requires it to be named in `docs/DEVIATION_LOG.md` rather than silently absorbed.
- **Segment-count assertions are coarse.** The band ACs compare `branch_segments.len()` between runs of one fixture. That proves a band appeared where expected and nowhere else, but not its exact line placement — the honest limit of an IR with no interface/base marker. AC-12 and AC-11/AC-11b compensate by testing the guards directly rather than through the plan.
- **The landing approximation produces false positives.** A chain truncated by `max_branches_per_layer` directly above model geometry receives a band canonical would not draw. It produces more interface, never less, and never places geometry inside the model. Filed as a new `Open` deviation row, not buried in `DEV-129`'s closure.
- **`densify_bottom_interface`'s two skip paths are easy to conflate.** The `L_end == 0` early return masks the collision test for every planner-level fixture. Anyone who "simplifies" AC-11 and AC-11b back into one case removes the only coverage the `found_contact == false` path has.
- **Clippy `too_many_arguments`.** Expected on `densify_bottom_interface`. Prefer a context struct over `#[allow]`.
- **The wedge suites are the slow gate and need a fresh guest.** Running AC-17 or AC-N7b's wedge half before `build-guests` is the single most likely way to waste a cycle on a false failure. Both `src/**` and `support-planner.toml` are guest inputs here.
