# Design: 192-infill-linker-anchor-length

## Controlling Code Paths

- Primary code path: `connect_infill` (`modules/core-modules/infill-linker/src/connect.rs`) — the `threshold` computation from `LINK_THRESHOLD_SPACINGS`, the `while let Some(candidate) = nearest_pair_candidate(...)` re-solve loop, and the unconditional `first.points.extend(contour_connector(...)); first.points.extend(second.points);` merge. - Neighboring tests/fixtures: `modules/core-modules/infill-linker/tests/connect_tdd.rs` (6 tests, three of them the ADR-0025 containment guards), `modules/core-modules/infill-linker/tests/orchestrate_tdd.rs` (the `ConfigViewBuilder` / `PerimeterRegionViewBuilder` harness that drives `InfillLinker::run_infill_postprocess` end to end), `modules/core-modules/infill-linker/tests/graph_tdd.rs`, and `crates/slicer-runtime/tests/integration/infill_partitioned_input_tdd.rs` (`ac7*`, the module+linker pair coverage ADR-0025 names).

## Architecture Constraints

- **The anchor decision belongs to the linker module, not `slicer-core`.** ADR-0025's §Future-Reviewer Notes explicitly forbids relocating `connect_infill` into `slicer_core::infill_ops`, and ADR-0026 places linking-algorithm choice in the module. Everything this packet adds stays under `modules/core-modules/infill-linker/`. Before this packet the module's only `slicer-core` use was `polygon_ops::clip_polylines` / `polygon_ops::union_ex`; **this packet adds a second, `slicer_core::flow::line_width_to_spacing`, and that is permitted.** Both `pub mod polygon_ops;` and `pub mod flow;` (`crates/slicer-core/src/lib.rs`) carry **no** `#[cfg(feature = "host-algos")]` attribute — unlike the `algos` / `medial_axis` / `skeletal_trapezoidation` / `voronoi` modules in the same file, which do — and `flow.rs` has no top-level `use` statements at all, so it is wasm-clean; `arachne-perimeters`, itself a guest, already imports from it. Consequently **no `--features host-algos` conjunct belongs on any command in this packet**, and no new host-only dependency is introduced. Any further `slicer-core` module is still out of bounds without re-checking its gate.
- **Containment is already structural and must stay that way.** ADR-0025's containment amendment fixed the two containment holes; `contour_connector` materialises every intermediate ring vertex. The new stub walk must be built from the same ring-vertex machinery so a stub is boundary geometry by construction, exactly as a whole-arc connector is. A stub built as a straight offset ray would reintroduce the chord class of defect that amendment removed.
<!-- snippet: coord-system -->
- Coordinate units: **1 unit = 100 nm** (10⁻⁴ mm), NOT 1 nm like OrcaSlicer. Divide OrcaSlicer constants by 100. Use `Point2::from_mm(x, y)` or `mm_to_units()` at every mm↔unit boundary. Full porting checklist in `docs/08_coordinate_system.md`.
- Applied here: `AnchorParams` stores **mm** (`anchor_length_mm`, `anchor_length_max_mm`) and crosses into IR units exactly once, at the comparison against `BoundaryRing::directed_distance`, which returns units. Canonical's `scale_(params.anchor_length)` at the top of `Fill::connect_infill` is the same single conversion; do not scale twice and do not compare a mm value against a unit value.
<!-- snippet: wasm-staleness -->
- Guest WASM is **not** rebuilt by `cargo build` or `cargo test`. After editing any path in this packet's change surface that feeds the guest build (see `CLAUDE.md` §"Guest WASM Staleness"), the implementer MUST run `cargo xtask build-guests --check` and, if `STALE:` is reported, rebuild without `--check` before re-running the failing test. Stale-guest failures look unrelated to the change but are caused by it.
- Applied here: `modules/core-modules/infill-linker/src/**` and `modules/core-modules/infill-linker/infill-linker.toml` are guest-build inputs. AC-13 runs through real module dispatch and will surface a stale guest as an unrelated-looking failure.
- **Schema/version constants: none are bumped.** No IR struct field, no WIT type, no `min-ir-schema` / `max-ir-schema` bound, and no public version constant changes. Adding `[config.schema.<key>]` entries to a module manifest is additive and does not move `CURRENT_SLICE_IR_SCHEMA_VERSION` or the world version. The one struct that gains fields (`RegionConfig`) is private to `orchestrate.rs`.

## Code Change Surface

- **Selected approach.** Port the canonical *decision*, substituting PnP's existing data structures for canonical's where they already carry the same invariant.

  1. **`AnchorParams` (new, `connect.rs`).** `pub struct AnchorParams { pub anchor_length_mm: f32, pub anchor_length_max_mm: f32 }`, `#[derive(Debug, Clone, Copy, PartialEq)]`. Associated items: `pub const UNLIMITED_MM: f32 = 1000.0` (canonical `FillParams`' default for both members); `pub const DONT_CONNECT_MAX_MM: f32 = 0.05` (canonical `FillParams::dont_connect()`); `pub fn solid() -> Self` (both `UNLIMITED_MM`); `pub fn dont_connect(&self) -> bool` (`anchor_length_max_mm < DONT_CONNECT_MAX_MM`); `pub fn from_config(config: Option<&slicer_ir::ConfigView>, base_spacing_mm: f32) -> Self`.
     `from_config` resolves each key with `ConfigView::get_abs_value(key, base_spacing_mm as f64)` — whose `FloatOrPercent { is_percent: true }` arm computes `value / 100.0 * base`, matching canonical `group_fills`' `params.anchor_length * 0.01 * params.spacing`, and whose `Float` arm passes an absolute mm value through unchanged — falling back to `4.0 * base_spacing_mm` / `20.0` when the key is absent or non-numeric, then applies canonical's `std::min(anchor_length, anchor_length_max)` clamp. Non-finite and negative results clamp to `0.0`.
     **Base choice — the highest-risk decision here, and the obvious answer is wrong.** Canonical's `group_fills` sets `params.spacing = layerm.region().flow(*layer.object(), frInfill, ...).spacing()` and immediately does `params.anchor_length = float(params.anchor_length * 0.01 * params.spacing)`. That is an **extrusion-flow spacing**, never divided by density, and it *agrees* with the key's declared `ratio_over = "sparse_infill_line_width"` — code path and UI label are not in opposition, so neither may be cited to justify a base matching neither. PnP's `sparse_spacing_mm` (`(line_width / density).max(f32::EPSILON)`) is the **line spacing**, 2.0 mm at `line_width = 0.4` / `density = 0.2`; using it would resolve canonical's 400 % default to 8.0 mm against canonical's ≈1.43 mm — 5.6× off, shipped under the closed infill-linker anchor residual.
     PnP therefore passes `base_spacing_mm = slicer_core::flow::line_width_to_spacing(line_width_mm, layer_height_mm)`, which **is** canonical `Flow::rounded_rectangle_extrusion_spacing` (`spacing = width - layer_height * (1 - π/4)`) — the same formula, so this is a port and not an approximation. At `0.4` / `0.2` it gives `0.3570796` mm and `anchor_length ≈ 1.4283185` mm. `slicer-core` is already a dependency of `infill-linker` and `pub mod flow` (`crates/slicer-core/src/lib.rs`) carries no feature gate, so the helper is available to the wasm32 guest.
     **Structural guarantee against regression:** `spacing_mm` was consumed by `connect_infill` **only** for the deleted threshold, so it is removed from `connect_infill` and `chain_or_connect_infill` rather than retained. After this packet no line-spacing value is in scope at the decision site, so the wrong base cannot be reintroduced by a later edit without re-adding a parameter. `link_paths_without_offset` keeps its own `spacing_mm` for `remove_short_polylines`, which has nothing to do with anchoring.
     **Named residual:** canonical's width input is the per-role `frInfill` flow width, which can differ from PnP's generic `line_width` key under auto/percent width resolution. The formula matches; the width *input* is the residual, and it is filed as its own deviation row. `layer_height` is read from the per-region `ConfigView` with `unwrap_or(0.2)` and **is declared** in `infill-linker.toml` — as is `line_width`, a pre-existing dead read. `arachne-perimeters` is the precedent because it **declares** `[config.schema.layer_height]` for this exact purpose (its `description` cites `line_width_to_spacing`), not because it reads the key. An undeclared read is silently dropped by `ConfigView::from_declared`, so declaring is what makes the base live; see §Data and Contract Notes.

  2. **`contour_stub` (new, `graph.rs`).** `pub fn contour_stub(ring: &BoundaryRing, from: f64, direction: RingDirection, budget_units: f64, anchor: &Point3WithWidth) -> Vec<Point3WithWidth>`. Walks `ring.vertices_between`-style in `direction` from `from`, pushing whole ring vertices while the accumulated arc stays under `budget_units`, then emits one final point interpolated along the segment that crosses the budget so the run measures **exactly** `budget_units` — canonical `take_ccw_limited` / `take_cw_limited`'s `t = (length_to_take - lprev) / (l - lprev)`. Every emitted point inherits `anchor`'s `z`, `width` and remaining attributes; unlike `contour_connector` there is no far endpoint to interpolate toward, which is why the existing `lerp` is used for the **position** of the terminal point only. Returns an empty `Vec` for a non-positive or non-finite budget.

  3. **Candidate ordering (`connect.rs`).** `nearest_pair_candidate` keeps its per-endpoint `min_by` on distance and its ring-identity and `compatible_paths` filters, but the terminal `candidates.sort_by` is re-keyed to `left.distance.total_cmp(&right.distance)` **first**, with `endpoint_order(first)` then `endpoint_order(second)` as deterministic tiebreaks. `connect_infill`'s `while let` re-solve loop becomes a single pass over the sorted candidate list with a `consumed: Vec<bool>`-style endpoint guard, mirroring canonical's `if (! arc.intersection->consumed && ! arc.intersection->next_on_contour->consumed)`.
     **Why no explicit `next_on_contour` adjacency structure is needed:** canonical only ever forms an arc between two contour-*adjacent* T-joints. Under shortest-first-with-consumption that property is emergent — if a third endpoint C lies between A and B on the ring, both A–C and C–B are strictly shorter than A–B, so one of them is processed first and consumes A or B, and A–B is skipped. Building the adjacency links explicitly would add a data structure that changes no outcome.

  4. **The branch (`connect.rs`).** For each surviving candidate: if `distance < mm_to_units(anchor_length_max_mm)` take the whole-arc branch — the existing `orient_for_join` + `contour_connector` + `extend` merge, keeping `first_index.min(second_index)` alive, which is already canonical's "lower index survives". Else if `anchor_length_mm > 0.0` take the stub branch — `contour_stub` twice with **opposite** `RingDirection`s (canonical's two `take_limited` calls with opposite `clockwise` flags), appending each run to its own polyline's joining end and leaving both polylines in `active`. Else emit nothing. Both endpoints are marked consumed in both branches, matching canonical, where consumption happens *inside* `take_limited`.
     **Stub clamp (the deliberate divergence):** the budget passed to `contour_stub` is `min(mm_to_units(anchor_length_mm), arc distance from this endpoint to the nearest other boundary position on the same ring in that direction)`. Canonical achieves the same end through `could_take_prev` / `could_take_next` and the `trim_prev` / `trim_next` calls inside `take_limited`; PnP does not port that bookkeeping, so the clamp is what prevents a stub from walking over another T-joint and double-extruding the boundary. The residual (canonical's early-return leaves an endpoint **unconsumed**; PnP always consumes) is filed as a deviation row.

  5. **`chain_or_connect_infill` fork (`connect.rs`).** When `anchor.dont_connect()`, skip `connect_infill` entirely and run only the existing chaining half — canonical `Fill::chain_or_connect_infill` dispatching to `chain_polylines` instead of `Fill::connect_infill`.

  6. **Plumbing (`orchestrate.rs`).** `RegionRecord` gains `anchor_base_mm: f32` and `sparse_anchor: AnchorParams`, both built in `orchestrate_infill`. `anchor_base_mm = line_width_to_spacing(line_width, layer_height).unwrap_or(line_width)` where `layer_height` comes from `config_float(view.config(), "layer_height")` filtered to finite-and-positive with `unwrap_or(0.2)`; `sparse_anchor = AnchorParams::from_config(view.config(), anchor_base_mm)`. **`sparse_spacing_mm` must not be passed here** — it is the line spacing and is 5.6× the correct base at default settings. `RegionConfig` gains `anchor_length: u32` and `anchor_length_max: u32` (`f32::to_bits()`), so the existing `same_config` test in `process_bucket_role` cannot union-link two regions with different anchoring. A new `anchor(records, index, bucket)` helper alongside the existing `spacing` returns `records[index].sparse_anchor` for `PathBucket::Sparse` and `AnchorParams::solid()` for `PathBucket::Solid` — canonical `group_fills`' `surface.is_solid() || is_bridge` forcing to `1000.f`. `link_paths` / `link_paths_without_offset` / `mixed_boundary` thread the value through to `chain_or_connect_infill`.

  7. **Manifest.** Two `[config.schema.*]` blocks as specified in `requirements.md` §In Scope. `infill_anchor`'s default is the **percent string** `"400%"`; `parse_percent_default` (`crates/slicer-scheduler/src/manifest.rs`) parses that into `ConfigValue::FloatOrPercent { value: 400.0, is_percent: true }`, which is exactly canonical's `ConfigOptionFloatOrPercent(400, true)`. `infill_anchor_max`'s default is the bare number `20.0`, which the same function accepts through its `as_float()` arm as `is_percent: false`.

- **Exact functions, traits, manifests, tests, and fixtures.** `connect_infill`, `chain_or_connect_infill`, `nearest_pair_candidate`, `Candidate`, `Endpoint`, `orient_for_join`, `LINK_THRESHOLD_SPACINGS` (deleted), new `AnchorParams` — all `modules/core-modules/infill-linker/src/connect.rs`. `contour_stub`, `lerp`, `BoundaryRing::directed_distance`, `BoundaryRing::vertices_between`, `RingDirection` — `modules/core-modules/infill-linker/src/graph.rs`. `orchestrate_infill`, `RegionRecord`, `RegionConfig`, `process_bucket`, `process_bucket_role`, `link_paths`, `link_paths_without_offset`, `spacing`, new `anchor` — `modules/core-modules/infill-linker/src/orchestrate.rs`. `modules/core-modules/infill-linker/infill-linker.toml`. The `infill_resolution` doc comment in `crates/slicer-ir/src/resolved_config.rs`.

- **Rejected alternatives and reasons.**
  - *Keep the `10 × spacing` gate and add stubs on top.* Rejected: the gate is the deviation. Leaving it would make `infill_anchor_max` a second, weaker threshold and produce a rule that exists in neither codebase.
  - *Port `ContourIntersectionPoint` with prev/next links and trimming.* Rejected for this packet: it is a data-structure port whose blast radius (a new graph type, its construction from `BoundaryInfillGraph`, and the trimming interactions) makes the packet L. The clamp substitute is behaviourally equivalent for the only property that matters here — a stub never crosses another T-joint — and the difference is filed rather than hidden.
  - *Port canonical's `merged_with` union-find.* Rejected: `active: Vec<Option<ExtrusionPath3D>>` with `active[first_index.min(second_index)] = Some(first)` already realises the same lower-index-survives invariant that canonical's `polyline_idx2 < polyline_idx1` move produces.
  - *Resolve the anchors in `lib.rs` and pass them into `orchestrate_infill` as module-global scalars.* Rejected: the percent resolution needs the per-bucket spacing, which only `orchestrate.rs` knows, and the solid bucket must override the value. Resolving in `orchestrate.rs` also mirrors how `line_width` / `infill_density` are already read from `view.config()`.
  - *Add a `float_or_percent` constructor to `ConfigViewBuilder`.* Rejected: `slicer-sdk` is a universal guest dependency, so the edit forces a full guest rebuild for a test-only convenience that `ConfigView::from_map` already provides.
  - *Declare `sparse_infill_anchor` / `sparse_infill_anchor_max` as aliases.* Rejected: PnP has no legacy-key remapping layer, so two spellings would be two independently settable keys with undefined precedence.

## Data and Contract Notes

- **IR/manifest contracts.** Two additive `[config.schema.*]` entries on `com.core.infill-linker`. No `[ir-access]`, `[claims]`, `[compatibility]` or `[stage]` change; `min-ir-schema = "3.0.0"` / `max-ir-schema = "5.0.0"` are untouched. Additive config keys do not require an IR schema bump — the same finding recorded for packet 130.
- **WIT boundary.** Unchanged. The two keys ride the existing `ConfigView` transport. Note that `crates/slicer-wasm-host/src/host.rs` already carries a `ConfigValueStorage::FloatOrPercent` variant that preserves `is_percent` across the host↔guest boundary specifically so a guest's `get_abs_value` sees the percent distinction — and since Packet 185 the live path does *produce* a percent variant: the scheduler's schema-default injection threads `ConfigFieldEntry.parsed_default` (a `ConfigValue::FloatOrPercent` from `parse_percent_default`) into the runtime `ConfigView`, so the transport is exercised on a real slice (the closed percent-transport residual).
- **`parse_percent_default` residual, stated precisely (corrected).** `parse_percent_default` returns the correct `ConfigValue::FloatOrPercent { value: 400.0, is_percent: true }` for `"400%"`. Its caller is **`parse_config_field_entry`** (`crates/slicer-scheduler/src/manifest.rs`) — *not* `read_config_schema`, which merely iterates the `[config.schema]` table and delegates to it. **Since Packet 185 `parse_config_field_entry` RETAINS the parsed value on `ConfigFieldEntry.parsed_default`** (alongside the `v.to_string()` display string on `ConfigFieldEntry.default`), and the scheduler's schema-default injection (`ConfigBoundsIndex::from_modules` → `resolve_global_config` → `ResolvedConfig.extensions` → `to_config_map`) threads it into the runtime `ConfigView`, so `get_abs_value` can take its percent arm on a real slice. The closed percent-transport residual documents the path. The residual that remains is the one stated in the packet's scope: the module's `from_config` fallbacks govern when the key is absent from the incoming config, and the manifest default numerically coincides with the fallback (`400%` of base = `4.0 × base`; `20.0` = `20.0`), so behavior is unchanged either way. Grep for `parse_config_field_entry`; `read_config_schema` does not contain either statement.
- **Determinism/scheduler constraints.** `connect_infill`'s output must stay bit-identical across runs — `connect_deterministic` (`modules/core-modules/infill-linker/tests/connect_tdd.rs`) pins it. The re-keyed sort must therefore keep total-order tiebreaks: `distance.total_cmp` first, then `endpoint_order(first)`, then `endpoint_order(second)`. `f64::total_cmp` is a total order, so `sort_by` cannot panic on it. Do **not** introduce a comparator that is not a strict weak ordering — lightning comparator ordering divergence records exactly that class of bug crashing a Rust `sort_by` where C++'s `stable_sort` merely misbehaved.
- **Scheduler bounds.** `check_scalar` treats a percent as its raw magnitude, so `max = 1000.0` is what makes the `400` in `"400%"` expressible; a `max` below `400` would reject canonical's own default.

## Locked Assumptions and Invariants

- **Locked: the whole-arc branch keeps infill-linker containment contract's containment property.** A merged connector is still produced by `contour_connector` and therefore consists only of ring vertices; a stub is produced by `contour_stub` and consists only of ring vertices plus one point lerped **along a ring edge**. No new geometry in this packet leaves the boundary. Reversing this — e.g. by simplifying the stub to a straight segment — reopens infill-linker containment contract.
- **Locked: the lower path index survives a merge.** `active[first_index.min(second_index)] = Some(first)` is canonical's union-find outcome and is what makes `connect_deterministic` reproducible; changing it changes output ordering for every fixture.
- **Locked: solid and bridge buckets are unlimited.** `PathBucket::Solid` forces `AnchorParams::solid()` and the config keys are ignored for it. This is canonical `group_fills` behaviour, not a PnP convenience, and it is the reason AC-8 asserts sparse and solid diverge under the same config.
- **Locked: `AnchorParams` holds millimetres.** The single mm→unit conversion happens at the comparison site. Any future field added to `AnchorParams` must follow the same rule.
- **Not locked:** the fallback constants `4.0 × base_spacing_mm` and `20.0` mm are reversible by setting the keys; the manifest defaults (threaded into the runtime `ConfigView` since Packet 185) numerically coincide with those fallbacks, so behaviour is unchanged whether the key is present or absent. Write `base_spacing_mm`, never a bare "spacing" — that ambiguity is exactly what the percent-base defect was made of.

## Risks and Tradeoffs

- **Behaviour move on solid fills.** Today the solid bucket links under a `10 × line_width` gate (≈4 mm at `line_width = 0.4`); after this packet it is unlimited, matching canonical. Combined with shortest-first-plus-consumption the effective walk is still bounded by the gap to the adjacent T-joint, but any fixture that pinned solid-fill path counts may move. `connect_tdd`, `orchestrate_tdd` and `infill_partitioned_input_tdd::` are all green today (measured) and are the tripwires; if one moves, verify the new output against canonical's rule before touching the assertion.
- **Behaviour move on sparse fills — large, and larger than a line-spacing reading suggests.** The default sparse gate goes from `10 × sparse_spacing_mm` (line spacing) to `min(4 × base_spacing_mm, 20 mm)` (flow spacing). At the common `line_width = 0.4` / `layer_height = 0.2` / `density = 0.2`: the old budget was `10 × 2.0 = 20` mm and the new one is `min(4 × 0.3570796, 20) = 1.4283185` mm — roughly a **14× reduction**, not the ~2.5× a line-spacing reading would give. This is canonical's number, and it is the single biggest fixture-moving change in the packet: expect many more, much shorter polylines, each carrying anchor stubs. Budget Step 4 accordingly and do not treat a large diff in sparse-fill path counts as a defect without checking it against `min(4 × 0.3570796, 20)` first.
- **Declaring `line_width` moves live infill geometry on non-default slices — disclosed, accepted, and filed.** This is the same mechanism the packet cites as its reason to *defer* `infill_density`, so it must not be left implicit. Measured against the tree: `line_width` is read at **two** sites, both currently dead because `ConfigView::from_declared` drops undeclared keys on **both** binding paths (`bind_module_config_view` in `crates/slicer-scheduler/src/execution_plan.rs` for the module view, and the `resolved_config_to_map(map.config_for(&key))` → `from_declared(..., declared_keys)` construction in `crates/slicer-wasm-host/src/dispatch.rs` for the per-region view).
  1. `<InfillLinker as LayerModule>::on_print_start` (`modules/core-modules/infill-linker/src/lib.rs`) — `unwrap_or(0.4)` into `InfillLinker::line_width`; `run_infill_postprocess` re-reads the key into a local named `spacing_mm` (falling back to `self.line_width`) and passes it as `orchestrate_infill`'s `default_line_width`.
  2. `orchestrate_infill` (`modules/core-modules/infill-linker/src/orchestrate.rs`) — per region, `config_float(view.config(), "line_width").unwrap_or(default_line_width)`, which sets `RegionRecord`'s `sparse_spacing_mm = (line_width / density).max(f32::EPSILON)` and `solid_spacing_mm = line_width.max(f32::EPSILON)`. `spacing(records, index, bucket)` hands those to `remove_short_polylines` (threshold `mm_to_units(0.8 * spacing_mm)`, via `link_paths_without_offset`) and to `ExPolygonWithOffset::for_infill_overlap` (`modules/core-modules/infill-linker/src/offset.rs`'s `aoffset = (infill_overlap - 0.5) * spacing_mm`). They also feed `RegionConfig`'s `line_width` fingerprint, which gates cross-region union linking in `process_bucket_role`'s `same_config` check.

  **Blast radius, stated precisely:** default slices are unmoved — `ResolvedConfig`'s `cli "line_width" line_width: f32 = 0.4` (`crates/slicer-ir/src/resolved_config.rs`) equals the `unwrap_or(0.4)` fallback, verified — so every default-config fixture keeps its current spacing. Any slice with a non-default `line_width` moves: prune threshold, overlap offset, and cross-region grouping all shift with it. **Chosen resolution: keep the declaration in this packet and disclose it, rather than splitting it out.** Splitting is not viable — `anchor_base_mm = line_width_to_spacing(line_width_mm, layer_height_mm)` *is* the packet's percent base, so leaving `line_width` undeclared would pin the base to a compile-time constant on every real slice and close the infill-linker anchor residual as "ported" over a resolution that cannot respond to configuration. That is the exact failure §Architecture Constraints already rejects for `layer_height`. The behaviour move is therefore in scope, and §Doc Impact carries a dedicated `DEV-###` row for it (ID re-derived at the moment of writing). The asymmetry with `infill_density` is deliberate and defensible: `line_width` feeds the anchor base this packet exists to get right; `infill_density` does not feed it at all, and additionally carries an unresolved fraction-vs-percent manifest conflict that must be settled tree-wide first.
- **The stub clamp is a divergence, not parity.** It is filed as a deviation row rather than presented as a port. A reviewer diffing `contour_stub` against `take_limited` will find them structurally different on purpose.
- **Packet size.** Five primary files in one module. The natural split seam, if the swarm finds Step 4 over budget, is between the whole-arc decision (Steps 1-2, config + `anchor_length_max` gate, no stubs, no reordering) and the stub + ordering half (Steps 3-4). Splitting was **not** taken here because a config key with no consumer and a `float_or_percent` gate that behaves like the old float gate is a half-ported state that reads as complete; the aggregate is `M`, and no single step is `L`.
- **Guest staleness.** Editing module sources without rebuilding guests makes AC-13 fail in a way that looks unrelated. Mitigated by the mandatory `cargo xtask build-guests --check` in Steps 2-4 and by the fact that guests were measured at 0 STALE when this packet was authored.

- **RESOLVED at authoring (was `[FWD]`): `PathBucket::Solid`'s role coverage already equals canonical's `is_solid() || is_bridge` set — no mapping fix is needed and the implementer must not re-open this.** The `anchor` helper in `orchestrate.rs` returns `AnchorParams::solid()` for `PathBucket::Solid`, and the question was whether any role reaching `PathBucket::Sparse` is one canonical would treat as solid. Verified against the tree: `roles_for_bucket` does not carry a hard-coded role list — it collects the distinct `path.role` values present in `all_paths(record, bucket)`, which maps `Solid → &record.solid_paths` and `Sparse → &record.sparse_paths`; `orchestrate_infill` sets `solid_paths: region.solid_infill.clone()` and `sparse_paths: region.sparse_infill.clone()` (and the no-matching-view pass-through branch sets `solid` from `region.solid_infill` likewise). So the buckets are exactly whatever the producer put in `solid_infill` / `sparse_infill`. On the producer side, `RectilinearInfill::run_infill` (`modules/core-modules/rectilinear-infill/src/lib.rs`) calls `push_solid_path` from exactly three sites — `top_solid_fill()`, `bottom_solid_fill()` and `bridge_areas()` — yielding `TopSolidInfill` / `BottomSolidInfill` (both via `solid_fill_role`, which relabels depth-≥1 shells to `InternalSolidInfill`) and `BridgeInfill`; `push_sparse_path` has exactly one call site, the `sparse_infill_area()` loop, with role `SparseInfill` only. `RoleBoundaries::for_role` matches the same partition (`TopSolidInfill`/`BottomSolidInfill`/`BridgeInfill`/`InternalSolidInfill` → solid boundaries, `SparseInfill` → sparse, all others `None`). **Conclusion: PnP's Solid bucket = {Top, Bottom, InternalSolid, Bridge} = canonical's `is_solid() || is_bridge`; the Sparse bucket carries only `SparseInfill`. Forcing the Solid bucket to unlimited anchoring is therefore exactly canonical's rule, and nothing under-anchored leaks into Sparse.** If a *future* infill producer adds a new role, this equality must be re-derived — it is a property of the producers, not of `roles_for_bucket`.
