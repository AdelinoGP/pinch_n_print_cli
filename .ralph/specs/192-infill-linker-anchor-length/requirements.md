## Problem Statement

`modules/core-modules/infill-linker` decides whether to join two infill polylines with a **single distance gate**: `LINK_THRESHOLD_SPACINGS = 10.0` multiplied by the fill spacing, converted to IR units in `connect_infill` (`modules/core-modules/infill-linker/src/connect.rs`) and applied in `nearest_pair_candidate`'s `(distance <= threshold).then_some(...)` filter, where `distance` comes from `BoundaryRing::directed_distance` (`modules/core-modules/infill-linker/src/graph.rs`). Every candidate that clears the gate is **merged**; there is no other outcome anywhere in the file.

Canonical `Fill::connect_infill` (`FillBase.cpp`) decides per arc, and has three outcomes:

1. **whole arc** (`arc.arc_length < anchor_length_max`) — reverse the two polylines so their contour endpoints face each other, `take` the full contour run, and merge them into one polyline via the `merged_with` union-find;
2. **stub** (`else if (anchor_length > SCALED_EPSILON)`) — two `take_limited` calls with opposite `clockwise` flags walk the contour only `anchor_length` far off each end, lerping the final partial segment (`t = (length_to_take - lprev) / (l - lprev)`) so each stub is *exactly* `anchor_length`; the two polylines stay separate;
3. **nothing** — when neither branch applies.

Canonical also `std::sort`s the arcs by `arc_length` ascending (unless `params.dont_sort`) and iterates greedily under the guard `if (! arc.intersection->consumed && ! arc.intersection->next_on_contour->consumed)`, so a short arc claims its endpoints before a longer one can.

Three consequences follow, and this packet closes all three as one coherent slice because they share the same decision point:

- PnP **merges across arcs canonical would have refused** (anything under 10 × spacing merges; canonical's default cap is `infill_anchor_max = 20 mm`, and for solid surfaces canonical instead forces both anchors to `1000.f`).
- PnP **leaves no anchor stub** where canonical would have left one, so a rejected candidate contributes no boundary adhesion at all.
- PnP's global candidate selection is **lexicographic-by-endpoint, not shortest-arc-first**. The retired infill-linker anchor label is not recreated; the current `DEV-110` row carries the neighbour-bookkeeping residual and the code remains the source for this ordering description. `nearest_pair_candidate` **does** pick each endpoint's best partner with a `min_by` on distance, but the final `candidates.sort_by` keys on `endpoint_order(first)` and only breaks ties by distance.

Two stale canonical citations are corrected as packet work. They are **not the same class** and must not be described as if they were — only the second is a falsified mapping of the kind D-168 required:

- The `LINK_THRESHOLD_SPACINGS` comment cites canonical's `1000. / density * spacing`. That expression exists only inside an `#if 0` block in the `std::vector<const Polygon*>` overload of `Fill::connect_infill`, gating a disabled `ConnectionCost` pre-pass. Measured: within that overload the only occurrences of `params.density` are those two disabled lines, so `Fill::connect_infill` has **no live density expression at all** — the two live `scale_(spacing) / params.density` hits in `FillBase.cpp` belong to `evaluate_support_arches` and `Fill::connect_base_support`. PnP's only anchor-adjacent constant therefore cites a **disabled block and is not a parity anchor**. This is a dead-citation removal, not a falsified-provenance correction: the comment already calls the value canonical's "disabled candidate threshold". No replacement citation may be written, because there is no live expression to cite.
- `crates/slicer-ir/src/resolved_config.rs` documents `infill_resolution` (default `0.04`) as "OrcaSlicer: `infill_anchor_max`". `infill_resolution` is a path-simplification tolerance with no relationship to anchoring, and the comment makes a reader believe `infill_anchor_max` is already implemented under another name. This one *is* a falsified mapping.

**The percent base is the highest-risk decision in this packet, and the obvious choice is wrong.** PnP's `sparse_spacing_mm` (`orchestrate.rs`: `(line_width / density).max(f32::EPSILON)`) is the **line spacing** — the distance between adjacent infill lines, 2.0 mm at `line_width = 0.4` / `density = 0.2`. It is also the value the deleted `LINK_THRESHOLD_SPACINGS` gate multiplied, which makes it the tempting base. Canonical's `group_fills` instead sets `params.spacing = layerm.region().flow(*layer.object(), frInfill, ...).spacing()` — an **extrusion-flow spacing**, never divided by density — and the very next statement is `params.anchor_length = float(params.anchor_length * 0.01 * params.spacing)`. That base agrees with the key's declared `ratio_over = "sparse_infill_line_width"`; the code path and the UI label do **not** disagree. Resolving canonical's default `infill_anchor = 400%` against the line spacing yields 8.0 mm where canonical yields ≈1.43 mm — a 5.6× divergence that would ship under a `Closed` infill-linker anchor residual row, i.e. recorded as parity. This packet therefore resolves against `slicer_core::flow::line_width_to_spacing(line_width_mm, layer_height_mm)`, which *is* canonical `Flow::rounded_rectangle_extrusion_spacing` (`spacing = width - layer_height * (1 - π/4)`), giving `0.3570796` mm and `anchor_length ≈ 1.4283185` mm at the same settings. `slicer-core` is already an `infill-linker` dependency and `pub mod flow` carries no feature gate, so the helper is available to the wasm32 guest at zero cost.

A consequence worth stating up front: `spacing_mm` was consumed **only** by the deleted gate, so `connect_infill` and `chain_or_connect_infill` lose that parameter and take `AnchorParams` in its place. After this packet no line-spacing value is in scope at the decision site at all, which is the structural guarantee that the wrong base cannot creep back in.

Neither `infill_anchor` nor `infill_anchor_max` (nor `anchor_length` / `anchor_length_max` / the legacy `sparse_infill_anchor*` spellings) has any live config-key definition anywhere in `crates/` or `modules/` today — verified; they appear only in prose (`docs/ORCA_CONFIG_REFERENCE.md` marked `❌`, `docs/DEVIATION_LOG.md`, `docs/adr/0025-...`, and an archived `docs/specs/_OLD/` plan).

**Framing that must not slip.** The infill-linker anchor residual is a **quality** divergence, not a containment one. ADR-0025's 2026-07-24 amendment and infill-linker containment contract (Closed) establish that every connector the linker emits is already contour geometry; `contour_connector` materialises every intermediate ring vertex. Nothing in this packet makes an escaping connector safe, because there are none. No requirement, AC, deviation-row edit, or ADR edit produced by this packet may claim otherwise.

No packet is reopened or superseded.

## Out of Scope

- Canonical's `ContourIntersectionPoint` neighbour bookkeeping — `could_take_prev` / `could_take_next` / `trim_prev` / `trim_next` / `consume_prev` / `consume_next` and the linked prev/next-on-contour structure. This packet substitutes a stub budget clamped to the next boundary position (AC-N3) and files the gap as a residual deviation. In particular, canonical's early-return path where `could_take_*` leaves an endpoint **unconsumed** so a later arc can still claim it has no PnP equivalent.
- Canonical's trailing single-endpoint anchoring pass over `graph.map_infill_end_point_to_boundary` (anchor an unconsumed endpoint by the shorter of its prev/next arcs, rejecting `l > anchor_length_max`). It is a second pass over a different data structure and is a natural follow-on packet.
- Canonical's `merged_with` union-find as a data structure. PnP's existing `active: Vec<Option<ExtrusionPath3D>>` with `active[first_index.min(second_index)] = Some(first)` already realises the same "lower index survives" invariant; adding a union-find would be churn.
- The `params.multiline > 1` skip inside canonical's arc loop (`arc.arc_length < scale_(spacing) * params.multiline`). PnP has no `multiline` key.
- Declaring the legacy aliases `sparse_infill_anchor` / `sparse_infill_anchor_max`. Canonical remaps them in `PrintConfigDef::handle_legacy`; PnP has no legacy-key remapping layer, so declaring both spellings would create two independently settable keys.
- Matching canonical's percent-base **width input** exactly. PnP feeds `line_width_to_spacing` the module's generic `line_width` key; canonical `group_fills` feeds `Flow::spacing()` the per-role `frInfill` flow width, which can differ under auto/percent width resolution. The *spacing formula* is identical (`width - layer_height * (1 - π/4)`), so this is a width-input residual, not a formula divergence — filed as its own deviation row. Adding a per-role infill flow width to the linker would require a flow model the module does not have.
- Declaring `infill_density`, and reconciling its units tree-wide. It stays an undeclared dead read here **on purpose**: `ResolvedConfig` carries `infill_density: f32 = 0.2` (a fraction) and `to_config_map` emits `Float(0.2)`, while `rectilinear-infill`, `gyroid-infill` and `lightning-infill` all declare it `default = 20.0, min = 0.0, max = 100.0` (a percent). The code side is consistent (`rectilinear-infill`'s own fallback is `_ => 0.2`; `crates/slicer-sdk/src/config_resolution.rs`'s tests assert fractions), so the three manifests are the outlier and their bounds simply fail to reject a percent-shaped user value — **not** a live 100× bug in those modules. Declaring the key here would not scale anything either, since `from_declared` copies from `to_config_map` rather than injecting the manifest default; it would instead make the linker start honouring a **user-set** density where it is pinned at `0.2` today, moving `sparse_spacing_mm` and hence `remove_short_polylines` on every non-default-density slice. That behaviour change belongs with the tree-wide unit reconciliation across four manifests plus `ResolvedConfig`; it is filed as its own deviation row. `infill_density` does not feed `anchor_base_mm`, so leaving it dead cannot affect this packet's parity claim.
- Making the percent form **transportable** on the live path. `parse_percent_default` (`crates/slicer-scheduler/src/manifest.rs`) already parses `"400%"` correctly; the transport gap was resolved by Packet 185's schema-default threading, and the current evidence is retained there rather than in a deleted deviation-log row. The substance of this bullet stays true: **no scheduler change lands in THIS packet** — the transport exists and is not touched here.
- Extending `ConfigViewBuilder` (`crates/slicer-sdk/src/test_support/fixtures.rs`) with a `float_or_percent` constructor. `slicer-sdk` is a universal guest dependency and touching it forces a full guest rebuild; `ConfigView::from_map` gives the tests the same fixture with zero blast radius.
- `modules/core-modules/infill-linker/src/offset.rs`, `src/lib.rs`, every other core module, and every host crate other than the `resolved_config.rs` doc-comment line.
