# Packet Contract: 192-infill-linker-anchor-length

## Goal

Port canonical `Fill::connect_infill`'s per-arc anchor decision into `modules/core-modules/infill-linker`: declare `infill_anchor` / `infill_anchor_max` as `float_or_percent` keys with canonical's `ConfigOptionFloatOrPercent(400, true)` / `ConfigOptionFloatOrPercent(20, false)` defaults and resolve them through `ConfigView::get_abs_value` against canonical's own percent base — the **extrusion-flow spacing** `slicer_core::flow::line_width_to_spacing(line_width_mm, layer_height_mm)`, which is canonical `Flow::rounded_rectangle_extrusion_spacing` and therefore the `params.spacing` that `group_fills` multiplies by `0.01 * anchor_length`; replace the single `LINK_THRESHOLD_SPACINGS = 10.0` × spacing gate in `connect_infill` (`modules/core-modules/infill-linker/src/connect.rs`) with the whole-arc-vs-stub branch; add a `contour_stub` walk in `modules/core-modules/infill-linker/src/graph.rs` whose final segment is lerped so a stub is exactly `anchor_length`; and make candidate consumption shortest-arc-first with a consumed-endpoint skip instead of the current lexicographic-by-endpoint sort.

**A percent base that is never reached is worth nothing, so the packet also declares the keys it reads.** `ConfigView::from_declared` (`crates/slicer-ir/src/slice_ir.rs`) copies **only** keys present in the module's declared schema — verified: its body is `for key in declared { if let Some(v) = source.get(key) { … } }` — and `bind_module_config_view` (`crates/slicer-scheduler/src/execution_plan.rs`) feeds it the manifest's schema keys plus `prefix:*` expansions, which `infill-linker` has none of. Measured: `line_width` is read by `orchestrate.rs` and `lib.rs` but declared nowhere in `infill-linker.toml`, so it is a **dead read** today and `unwrap_or(0.4)` is not a fallback but the value. Adding `layer_height` as a third such read would make `anchor_base_mm` a compile-time constant on every real slice while DEV-089 was flipped to `Closed` as ported. This packet therefore declares `layer_height` and `line_width` alongside the two anchor keys — the same dead-read fix packet 150 applied to `classic-perimeters`' `nozzle_diameter`, whose manifest comment records the identical mechanism.

**The percent base is the one thing this packet must not get wrong.** PnP's `sparse_spacing_mm` (`orchestrate.rs`: `(line_width / density).max(f32::EPSILON)`) is the **line spacing** — 2.0 mm at `line_width = 0.4` / `density = 0.2`. Canonical's `params.spacing` is an **extrusion-flow spacing** (~0.357 mm at the same settings), never divided by density, and it agrees with the key's declared `ratio_over = "sparse_infill_line_width"`. Resolving 400 % against the line spacing would yield 8.0 mm where canonical yields ~1.43 mm — a 5.6× divergence shipped under a `Closed` deviation row. `connect_infill` therefore **loses its `spacing_mm` parameter entirely** (it was consumed only by the deleted gate) and takes `AnchorParams` in its place, so no line-spacing value is in scope at the decision site at all.

## Scope Boundaries

Touches the `infill-linker` module only: `src/connect.rs` (the gate, the candidate ordering, the new `AnchorParams`), `src/graph.rs` (`contour_stub`), `src/orchestrate.rs` (per-region/per-bucket anchor resolution, the percent base, and the solid-bucket forcing), `infill-linker.toml` (the two anchor keys, plus `layer_height` and `line_width` to un-deaden the reads that feed the percent base), and its own tests. Canonical's `ContourIntersectionPoint` neighbour-trimming machinery (`could_take_prev` / `could_take_next` / `trim_prev` / `trim_next`) is **deliberately not ported** — this packet substitutes a stub budget clamped to the arc reaching the next boundary position in the walk direction, and files that gap as a new residual deviation rather than claiming full parity. `modules/core-modules/infill-linker/src/lib.rs`, `src/offset.rs`, every other module, and every host crate other than the one-line doc-comment correction in `crates/slicer-ir/src/resolved_config.rs` are out of scope.

**This packet fixes a quality divergence, not a containment bug.** Per ADR-0025's 2026-07-24 amendment and DEV-088 (Closed), every connector the linker emits is already contour geometry; nothing here makes an escaping connector safe, and no AC below may be read as claiming so.

## Acceptance Criteria

**Mandatory conventions for every `cargo test` command below — both are measured defects from sibling packets in this batch, not style preferences:**

1. **`rg "^test result:"` — the colon is load-bearing.** Unanchored `^test result` also matches libtest's per-test NAME line, which carries no `0 failed` and false-reds an otherwise green run.
2. **`--exact` needs the module-qualified path.** Measured on this tree: every test in `modules/core-modules/infill-linker/tests/*.rs` is a top-level `fn` in its own integration binary, so the **bare name is already fully qualified** there — verified: `cargo test -p infill-linker --test connect_tdd -- connect_deterministic --exact` reports `1 passed`, and a name that does not exist reports the FAIL branch. `crates/slicer-runtime/tests/integration/infill_partitioned_input_tdd.rs` is a *module* of the bucketed `integration` binary and must be reached as `infill_partitioned_input_tdd::`.

Guard shape follows **how many `^test result:` summary lines the command can emit**:

- **Single-result-line form** — one `--test <binary>`, with or without a name filter → `… 2>&1 | rg "^test result:" | rg -q "^test result: ok\. [1-9]" && echo PASS || echo "FAIL: …"`. The `[1-9]` rejects a filtered-to-zero run *and* a partial failure.
- **Multi-result-line form** — a whole-crate selector (`-p infill-linker`) → capture the summary lines to a **uniquely keyed** `target/guard-<key>.txt`, then test for red **and** separately for non-emptiness. `rg -q` alone would let one green binary mask a red sibling. Measured on the unfixed tree: `cargo test -p infill-linker` emits **8** summary lines, two of which are legitimately `ok. 0 passed` (the empty `--lib` and doc-test binaries), so an "any `0 passed` ⇒ FAIL" conjunct is **not** available here.
- **`rg -v "0 passed"` / `rg -v "0 failed"` are banned as guards.** `test result: FAILED. 3 passed; 4 failed;` contains neither literal, so both report success on a partial failure.

Static probes are written in `python3` rather than `rg` wherever the pattern contains a backtick or a pipe: inside `bash -c '…'` a backticked pattern in double quotes is command-substituted and the guard becomes permanently non-discriminating. Patterns are built from `chr(96)` / `chr(124)`.
