## Architecture Constraints

- **`overhang_quartile` stays the gate; the prepass-stamped distance supplies only the magnitude.** The module's manifest declares `[ir-access] reads = ["LayerCollectionIR", "LayerCollectionIR.overhang_quartile"]`. If the rewrite stopped reading the quartile, that declaration would become false and the DAG's cross-stage reader/writer validation would be asserting a dependency the code no longer has. Keep `p.overhang_quartile.is_some()` as the per-point "is this an overhang" test (`AC-N1`). **Under option (C) the manifest must also gain `LayerCollectionIR.overhang_distance_mm`** — the same truthfulness requirement applied in the other direction; see §Code Change Surface.
- **The distance is read, never computed.** Under the maintainer's option (C) ruling this module performs **no** cross-layer boundary scan. It reads `Point3WithWidth.overhang_distance_mm`, stamped by the prepass in packet **`193-overhang-distance-prepass-carrier`**. That value is **signed** and already **`+ boundary_offset`-normalised**; its single normative definition is `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract", which this packet and packet 191 both **cite and do not restate**. Consuming it as an unsigned magnitude, or re-adding an offset, is the failure mode that definition exists to prevent.
- **`crates/slicer-core/src/algos/overhang_annotation.rs` is out of bounds, including its `BAND_BOUNDARY_MULTIPLIERS`.** The prepass quartile banding is not touched by this packet. **But do not extend that out-of-bounds status to the module's own private duplicate**: `modules/core-modules/overhang-classifier-default/src/lib.rs` declares its own `const BAND_BOUNDARY_MULTIPLIERS: [f32; 3]` whose **only** reader is `quartile_for_distance`. Deleting `quartile_for_distance` (see §Code Change Surface) orphans that const, `dead_code` fires under `cargo clippy --workspace --all-targets -- -D warnings`, and Step 5 requires that gate clean — so the module's duplicate must be deleted **in the same step as its reader**. Its doc-comment also carries the cross-crate invariant "Keep these two lists numerically identical"; removing the module copy retires that invariant on the module side, and the deletion comment must say so rather than dropping it silently. Whether this packet may restore canonical's six overlap levels at all is an open scope question — see §Open Questions `[BLOCK-1]`/`[BLOCK-2]`/`[BLOCK-3]`.

## Code Change Surface

**This section is written for the maintainer's ruling, option (C).** The module **reads** the prepass-stamped `Point3WithWidth.overhang_distance_mm` delivered by packet 193; it computes no cross-layer distance of its own. The in-module `distance_to_prev_boundary` scan, the segment-list *produce* phase it needed, the `+0.5 × outer_wall_line_width` compensation and the `OuterWall`-only-vs-all-roles question are all **removed from this design**, not deferred — see §Open Questions for the three `[FWD]`s they collapsed into, retained there as an audit trail.

- **Selected approach.** Keep `run_finalization`'s existing two-phase per-layer walk **for the curl feature only** — that feature genuinely needs the previous layer's curled-height point list and ADR-0032 keeps it transient and in-module. Change the *consume* phase from "max quartile over the entity ⇒ one factor" to "per-point **stamped** distance ⇒ per-point speed ⇒ one `SetPointSpeedFactors` vector". **The produce phase is unchanged**: it keeps emitting the `(x, y, curled_height)` point list the curl feature already produces, and does **not** grow a segment list, because nothing in this design measures a boundary distance any more.
- **Exact functions to add / change in `modules/core-modules/overhang-classifier-default/src/lib.rs`:**
  - `const OVERHANG_OVERLAP_LEVELS: [f32; 6] = [90.0, 75.0, 50.0, 25.0, 13.0, 0.0];` — new, with the canonical provenance comment naming `GCode::_extrude`'s stack-local `ConfigOptionPercents overhang_overlap_levels` and the fact that no such config key exists in `PrintConfig.cpp`.
  - `fn build_speed_sections(ref_speed: f32, path_width: f32, config: &ConfigView) -> Vec<(f32, f32)>` — new. **`ref_speed` is an explicit parameter, not derived inside**, and it is the *only* speed this function sees; `original_speed` must not be in scope here (see §Data and Contract Notes and `AC-14`). Six entries; `distance_i = path_width * (1.0 - OVERHANG_OVERLAP_LEVELS[i] / 100.0)` in unscaled millimetres; speeds are **absolute mm/s** — `[ref_speed, oh1, oh2, oh3, oh4, sixth]` where each of `oh1..oh4` falls back to `ref_speed` when its configured absolute value is `< 0.5`, and `sixth` is `oh4` (same guard) when `slowdown_for_curled_perimeters` else `bridge_speed` (no guard). Canonical expresses the same table as percentages resolved by `speed = speeds.get_at(i).percent ? (ext_perimeter_speed * value / 100.0) : value`; PnP's `overhang_*_4_speed` and `bridge_speed` are already plain mm/s floats, so the percent branch collapses — but the **base** is still `ref_speed` and never `original_speed`.
    Then sort ascending by distance with ties broken **higher speed first**, and **flatten, do not de-duplicate**: walk the sorted vector and, for each entry whose distance equals the previous one's, overwrite its speed with the earlier one's, leaving the entry in place. Canonical has no `std::unique` and no `erase`; the table stays six long. `AC-15` pins this because a dedup changes which pair `calculate_speed` brackets, and the canonical literal `{90, 75, 50, 25, 13, 0}` yields already-ascending distances so the sort is a visible no-op that invites the "simplification".
  - `fn calculate_speed(distance: f32, sections: &[(f32, f32)], original_speed: f32) -> f32` — new. Empty table ⇒ `original_speed`. `distance <= sections[0].0` ⇒ `original_speed`. `distance >= sections.last().0` ⇒ `sections.last().1`. Otherwise find the bracketing pair, `t = ((distance - d_i) / (d_{i+1} - d_i)).clamp(0.0, 1.0)`, return `((1.0 - t) * s_i + t * s_{i+1}).round()` — rounding **mm/s**, because the sections are absolute speeds. `original_speed` enters only through the below-first-section branch and the caller's terminal clamp; it never participates in building a section.
  - **`fn distance_to_prev_boundary(…)` — DELETED FROM THIS DESIGN.** It was an unsigned in-module point-to-segment minimum over the previous layer's `OuterWall` centerline. Under option (C) the module performs **no** boundary scan: it reads `p.overhang_distance_mm: Option<f32>` off each point. The replacement is a one-line accessor, not a function. **Three consequences a reader of the old design must not carry forward:**
    1. **The value is SIGNED and already `+ boundary_offset`-normalised.** The old signature promised an *unsigned* minimum with no offset; the carrier is neither. Its normative definition lives in exactly one place — `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract" — and this packet **cites it rather than restating it**, as does packet 191. Negative ⇒ inside the previous layer by more than `boundary_offset`; zero ⇒ on the offset boundary; positive ⇒ overhanging beyond it. Feed the value to `calculate_speed` as-is; do **not** take its absolute value and do **not** re-add or subtract an offset.
    2. **`None` now has a contract, and it is packet 193's, not this packet's.** `None` means "no distance was measured" — no previous layer, or an empty previous-layer boundary for the region. `0.0`, `-1.0` and `f32::MAX` are all forbidden substitutes (packet 193's `AC-N1` enumerates them because each is a live sentinel downstream). This packet's rule for `None` is simply: **treat the point as non-overhanging and give it factor `1.0`**, which is the same outcome the `overhang_quartile.is_some()` gate already produces for an unclassified point (`AC-N1`). The old design's "this packet does not pin when `None` is returned" paragraph is obsolete — it is pinned, upstream, and packet 191's normative unwrap rule rests on it.
    3. **The first layer is still handled in the *caller*.** `run_finalization` skips `idx == 0` (`AC-8`) regardless of what the stamped field holds there, because canonical's gate carries `!on_first_layer()` as an independent conjunct. Do not replace that skip with a `None` check; they are different conditions that happen to coincide on layer 0.
  - `base_speed` — unchanged; it already returns `outer_wall_speed` / `inner_wall_speed` / `thin_wall_speed` and `0.0` for every other role, which is PnP's stand-in for canonical's `(is_bridge || is_perimeter)` conjunct and for `ref_speed`'s external-vs-internal selection.
  - `run_finalization` — gate on `config.get_bool("enable_overhang_speed").unwrap_or(true)`; keep the existing all-zero-overhang-speeds early return; skip the speed path for `idx == 0`; per entity build `factors: Vec<f32>` of `path.points.len()` entries **from each point's stamped `overhang_distance_mm`** and emit one `EntityMutation::SetPointSpeedFactors(factors)`; remove `EntityMutation::SetSpeedFactor` entirely.
  - The *produce* phase — **unchanged.** It keeps recording only the `(x, y, curled_height)` points the curl feature needs. **The `(x0, y0, x1, y1)` `OuterWall` segment list an earlier revision added here is removed**: under option (C) nothing measures a boundary distance in-module, so the segment list has no consumer, and leaving it would trip `dead_code` under the `-D warnings` gate Step 5 requires clean.
  - **`[ir-access]` — one manifest line changes and it is easy to miss.** The module's manifest declares `reads = ["LayerCollectionIR", "LayerCollectionIR.overhang_quartile"]`. Under (C) it also reads `LayerCollectionIR.overhang_distance_mm`, and that declaration must be added or the DAG's cross-stage reader/writer validation is asserting a narrower dependency than the code has. This is the mirror of the §Architecture Constraints rule about not *dropping* the quartile read: the declaration must be true in both directions.
- **Curl merge, in canonical order.** The curl feature already synthesises an *artificial distance* per point (`flow_width * (1 - distance/dist_limit)^2 * (curled_height / (lh * 10))`). Feed that artificial distance to the **same** `calculate_speed` to obtain `curled_speed`, and apply `extrusion_speed = min(curled_speed, extrusion_speed)` **after** the `min(extrusion_speed, original_speed)` clamp — verified as canonical's order in `estimate_extrusion_quality`, and it is why a curled-line slowdown can legitimately push below `original_speed`. Today the module instead buckets the artificial distance through `quartile_for_distance` and merges via `max(overhang_q, curl_q)`; that merge disappears.
- **`quartile_for_distance` and the module's private `BAND_BOUNDARY_MULTIPLIERS` are deleted together.** `quartile_for_distance` has no remaining caller once curl feeds `calculate_speed` directly, and it is the const's only reader. Deleting the function alone orphans the const and trips `-D warnings` on the very gate Step 5 requires clean; deleting both is the only self-consistent option. This touches **only** the module's local duplicate — `crates/slicer-core/src/algos/overhang_annotation.rs`'s `BAND_BOUNDARY_MULTIPLIERS` and banding geometry are out of bounds and stay exactly as they are. **Do not extend that to the whole file:** `[BLOCK-1b]` resolved to "proceed" under option (C), so that file's **doc-comment** must be corrected in-packet (see §Out-of-Bounds Files and `packet.spec.md` §Scope Boundaries) — it would otherwise describe as an intentional deviation something the tree no longer does. The correction is now an obligation, not a conditional. An earlier revision of this sentence said the file "stays exactly as it is", contradicting this design's own carve-out. Record in the deletion comment that the "Keep these two lists numerically identical" invariant no longer has a module-side list to keep in sync.
- **Rejected alternative 1 — derive a pseudo-distance from the quartile.** Map `q ∈ {1,2,3,4}` to a representative distance and interpolate. Rejected: every point in a band shares one distance, so the output is the same step function the module already produces. It would satisfy a naive "interpolation exists" grep and satisfy nothing else, which is why AC-5 asserts **at least two distinct factors within one entity** rather than the presence of interpolation code.
- **~~Rejected~~ SELECTED alternative 2 — carry a continuous per-point overhang distance in the IR.** This is option **(C)**, and the maintainer chose it. It is now this packet's design; see §Selected approach above. **The original rejection is retained below, struck through in substance rather than deleted, so the fork stays auditable** — the earlier revision of this bullet flagged the contradiction as "deliberate and still open" and instructed that the bullet be rewritten if (C) was picked. It was picked, and this is that rewrite. *Original reasoning:* "The faithful analogue of canonical's `ExtendedPoint::distance`, and it would let the prepass (which already works against real slice footprints) supply an unbiased distance. Rejected on blast radius: it means a new field on `Point3WithWidth` — hundreds of exhaustive struct literals across well over a hundred files, plus a `point3-with-width` WIT record change — the same `L` that packet 189 rejected for the speed field, for the same reason." **What that reasoning missed:** it weighed blast radius only, and never weighed ADR-0031 conformance. The blast radius is real and is not disputed — it is why (C) costs a whole prerequisite packet, **`193-overhang-distance-prepass-carrier`**, which splits the sweep into `M` steps exactly as packet 189 splits its own. What changed the answer is that the alternative was not "cheap in-module scan vs expensive IR field" but "reverse a recorded architectural decision vs pay a mechanical sweep once".
- **Rejected alternative 3 — measure against the previous layer's slice boundary *from inside the finalization guest*.** What canonical does, attempted at the wrong tier. Rejected because a `PostPass::LayerFinalization` guest cannot reach `SliceRegionView` at all. **Note what option (C) does with this:** it does not overturn the measurement, it **relocates** it. The previous layer's slice boundary *is* what packet 193 measures against — from the prepass, which can reach it — so option (C) delivers exactly the geometry this alternative wanted, at the only tier where it is available. **Corrected reasoning — the earlier wording here ("a new host service or a new `[ir-access]` read plus DAG re-validation") is what `[BLOCK-3]` itself calls vague and partly wrong, and it survived a round after being flagged:** `[ir-access]` gates DAG validation, not what the WIT hands the guest. Measured: `slice-region-view` is declared in `crates/slicer-schema/wit/deps/ir-types.wit` and every `use` of it sits in `world-layer.wit`; `world-finalization.wit` never imports **`slicer:ir-handles`** — note the package name, which is `slicer:ir-handles` and **not** `slicer:ir-types` despite the file being named `ir-types.wit` (`rg -n '^package' crates/slicer-schema/wit/deps/ir-types.wit` → `package slicer:ir-handles;`; `slicer:ir-types` has **zero occurrences under `crates/`** — the only surviving hits are five lines in archived packets under `.ralph/specs/_OLD/` — so an earlier revision of this paragraph named a package that no live code declares) — its `run-finalization` takes only `(layers, output, config)`, `layer-collection-view` exposes six methods and `host-services` fifteen functions (**five** of them `*-batch` forms), none surface- or region-related. **"Never imports `slicer:ir-handles`" is a claim about *package imports* specifically** — the world does carry three `use` statements reaching into `slicer:config/config-types`, `slicer:types/geometry` and `slicer:common/module-errors`; it is `slicer:ir-handles` alone that it never touches. ## Data and Contract Notes

- **IR/manifest contracts.** `factors.len()` MUST equal the target entity's `path.points.len()`. Packet 189's `apply_to` rejects a mismatch with an `Err`, but `crates/slicer-wasm-host/src/dispatch.rs` swallows that `Err` with `log::warn!` — so in the live WASM path an off-by-one is a **silent no-op**, not a failure. Size the vector from `entity.path.points.len()` directly and never from a filtered subset.
- **Factors are multipliers, not speeds.** `EntitySpeedProfile.factors[i] = per_point_speed_mm_s / base_speed(role)`. `resolve_feedrate` re-applies the role base speed and its `clamp(0.05, 5.0)`; emitting absolute mm/s here would be doubly scaled.
- **`ref_speed` and `original_speed` are two canonically distinct bases that this port deliberately collapses — keep them two separate parameters anyway.** Canonical's `estimate_extrusion_quality(…, float ext_perimeter_speed, float original_speed, …)` resolves every percentage section against `ext_perimeter_speed` and **never** against `original_speed`; `GCode::_extrude` passes `ref_speed` for the first and its own `speed` argument for the second, so the terminal `min(extrusion_speed, original_speed)` compares two mm/s values from different bases. In PnP both currently evaluate to `base_speed(role, config)` — not by coincidence but by definition, because a PnP speed factor *is* a multiplier over that base, so the path's unmutated speed and the role reference speed are the same number. That equality is a property of today's PnP, not of the algorithm: canonical additionally floors `ref_speed` by `filament_max_volumetric_speed / mm3_per_mm` and by `scarf_joint_speed` when sloped, neither of which is available to this module and neither of which is borrowed. **Therefore `build_speed_sections` takes `ref_speed` and `calculate_speed` takes `original_speed` as separate named parameters even though the live caller passes the same value to both**, `AC-14` exercises them with deliberately different values, and the `DEV-009` progress paragraph records the collapse together with the two unborrowed floors. Merging the parameters would make a future divergence unrepresentable and undetectable.
- **Section speeds are absolute mm/s; the conversion to a factor happens once, at the emission boundary.** `calculate_speed` returns mm/s (canonical rounds mm/s), and only when building the `SetPointSpeedFactors` vector is each value divided by `base_speed(role, config)`. Dividing earlier would make the `round` round a multiplier, which quantises to 0 or 1.
- **`path_width` is shared with packet 191, and under option (C) it is fixed upstream rather than chosen here.** Canonical feeds the same `path.width` both to the section-distance formula and to `estimate_points_properties` as `flow_width`. Packet 193 normalises the carrier with `boundary_offset = 0.5 × width` using **the point's own `width`**, so that is what `path_width` must be here and what packet 191's `min_spacing = flow_width × 0.25` and `boundary_offset` must be there. Resolving a second, independently-derived width would silently decouple the six section thresholds from the distances they threshold. Expose it as a named helper rather than computing it inline at a single call site, so all three packets provably share one number.
- **The signedness contract is cited, never restated.** `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract" is the single normative definition of `overhang_distance_mm` for this packet and for packet 191. **Do not paraphrase it into this file.** The three artifacts previously disagreed about signedness — this packet declared an *unsigned* point-to-segment minimum while every predicate packet 191 ports reads canonical's *signed* value plus `boundary_offset` — and a paraphrase is how that disagreement returns. If the contract needs to change, it changes in packet 193 and both consumers re-read it.
- **WIT boundary.** None crossed by this packet beyond the variant packet 189 already added. The manifest gains keys; `[ir-access]`, `[claims]` and `[stage]` are unchanged, so no DAG edge moves.
- **Determinism/scheduler constraints.** `[hints] layer-parallel-safe = false` already holds for this module and must stay false — **but note the reason changed under option (C) and the old reason is now wrong.** It is no longer "the per-point distance depends on the previous layer's produced segment list", because there is no such list: the distance arrives stamped. The load-bearing dependency that remains is the **curl** feature's, which keeps the previous layer's curled-height points as local state across the Z-order walk (ADR-0032 records that as deliberate). Getting this reason right matters: a future reader who removes the curl feature might otherwise conclude the hint can flip, when in fact the curl feature is now its *only* justification. `nearest`-style scans must still break ties deterministically (`total_cmp`, as the existing `nearest_reference_point` does) — `DEV-093` records that the pipeline already has a non-determinism problem and this packet must not add to it.

## Locked Assumptions and Invariants

- **A point with `overhang_quartile == None` is not an overhang**, regardless of its measured distance. Locked; `AC-N1` defends it, and the module's `[ir-access]` declaration depends on it.
- **All four `overhang_*_4_speed` at 0 ⇒ zero mutations**, unchanged from today. Locked by the existing early return; `AC-10` defends it. Without it, the `< 0.5` guard would turn every section into 100 % and emit a full-length all-1.0 profile on every wall entity of every layer — a behaviour change disguised as a no-op.
- **`enable_overhang_speed` absent ⇒ `true`.** Matches canonical's `ConfigOptionBoolsNullable{ true }` default and keeps existing configs behaving as they do today.
- **First layer emits no speed mutation.** Canonical `!on_first_layer()`; also the only layer with no previous-layer geometry to measure against.
- **Reversibility:** setting `enable_overhang_speed = false` restores the pre-packet behaviour of emitting nothing; setting the four overhang speeds to 0 does the same. No behaviour lock is introduced that config cannot undo.

## Risks and Tradeoffs

- **~~The `OuterWall`-centerline proxy biases every distance.~~ DISSOLVED BY OPTION (C).** Retained as an audit trail, not as a live risk.
