## Architecture Constraints

- **`overhang_quartile` stays the gate; the in-module distance supplies only the magnitude.** The module's manifest declares `[ir-access] reads = ["LayerCollectionIR", "LayerCollectionIR.overhang_quartile"]`. If the rewrite stopped reading the quartile, that declaration would become false and the DAG's cross-stage reader/writer validation would be asserting a dependency the code no longer has. Keep `p.overhang_quartile.is_some()` as the per-point "is this an overhang" test (`AC-N1`).
- **`crates/slicer-core/src/algos/overhang_annotation.rs` is out of bounds, including its `BAND_BOUNDARY_MULTIPLIERS`.** The prepass quartile banding is not touched by this packet. **But do not extend that out-of-bounds status to the module's own private duplicate**: `modules/core-modules/overhang-classifier-default/src/lib.rs` declares its own `const BAND_BOUNDARY_MULTIPLIERS: [f32; 3]` whose **only** reader is `quartile_for_distance`. Deleting `quartile_for_distance` (see §Code Change Surface) orphans that const, `dead_code` fires under `cargo clippy --workspace --all-targets -- -D warnings`, and Step 5 requires that gate clean — so the module's duplicate must be deleted **in the same step as its reader**. Its doc-comment also carries the cross-crate invariant "Keep these two lists numerically identical"; removing the module copy retires that invariant on the module side, and the deletion comment must say so rather than dropping it silently. Whether this packet may restore canonical's six overlap levels at all is an open scope question — see §Open Questions `[BLOCK-1]`/`[BLOCK-2]`/`[BLOCK-3]`.

## Code Change Surface

- **Selected approach.** Keep `run_finalization`'s existing two-phase per-layer walk (consume, then produce this layer's reference geometry for the next). Change the *consume* phase from "max quartile over the entity ⇒ one factor" to "per-point distance ⇒ per-point speed ⇒ one `SetPointSpeedFactors` vector", and change the reference geometry produced in the *produce* phase from a point list to a **segment** list so the distance can be point-to-segment.
- **Exact functions to add / change in `modules/core-modules/overhang-classifier-default/src/lib.rs`:**
  - `const OVERHANG_OVERLAP_LEVELS: [f32; 6] = [90.0, 75.0, 50.0, 25.0, 13.0, 0.0];` — new, with the canonical provenance comment naming `GCode::_extrude`'s stack-local `ConfigOptionPercents overhang_overlap_levels` and the fact that no such config key exists in `PrintConfig.cpp`.
  - `fn build_speed_sections(ref_speed: f32, path_width: f32, config: &ConfigView) -> Vec<(f32, f32)>` — new. **`ref_speed` is an explicit parameter, not derived inside**, and it is the *only* speed this function sees; `original_speed` must not be in scope here (see §Data and Contract Notes and `AC-14`). Six entries; `distance_i = path_width * (1.0 - OVERHANG_OVERLAP_LEVELS[i] / 100.0)` in unscaled millimetres; speeds are **absolute mm/s** — `[ref_speed, oh1, oh2, oh3, oh4, sixth]` where each of `oh1..oh4` falls back to `ref_speed` when its configured absolute value is `< 0.5`, and `sixth` is `oh4` (same guard) when `slowdown_for_curled_perimeters` else `bridge_speed` (no guard). Canonical expresses the same table as percentages resolved by `speed = speeds.get_at(i).percent ? (ext_perimeter_speed * value / 100.0) : value`; PnP's `overhang_*_4_speed` and `bridge_speed` are already plain mm/s floats, so the percent branch collapses — but the **base** is still `ref_speed` and never `original_speed`.
    Then sort ascending by distance with ties broken **higher speed first**, and **flatten, do not de-duplicate**: walk the sorted vector and, for each entry whose distance equals the previous one's, overwrite its speed with the earlier one's, leaving the entry in place. Canonical has no `std::unique` and no `erase`; the table stays six long. `AC-15` pins this because a dedup changes which pair `calculate_speed` brackets, and the canonical literal `{90, 75, 50, 25, 13, 0}` yields already-ascending distances so the sort is a visible no-op that invites the "simplification".
  - `fn calculate_speed(distance: f32, sections: &[(f32, f32)], original_speed: f32) -> f32` — new. Empty table ⇒ `original_speed`. `distance <= sections[0].0` ⇒ `original_speed`. `distance >= sections.last().0` ⇒ `sections.last().1`. Otherwise find the bracketing pair, `t = ((distance - d_i) / (d_{i+1} - d_i)).clamp(0.0, 1.0)`, return `((1.0 - t) * s_i + t * s_{i+1}).round()` — rounding **mm/s**, because the sections are absolute speeds. `original_speed` enters only through the below-first-section branch and the caller's terminal clamp; it never participates in building a section.
  - `fn distance_to_prev_boundary(x: f32, y: f32, segments: &[(f32, f32, f32, f32)]) -> Option<f32>` — new; unsigned point-to-segment minimum. Replaces `nearest_reference_point`'s point-to-point scan for the overhang path. **This packet does NOT pin when `None` is returned, and no AC here constrains it.** Implementers should not read a `None ⇔ segments.is_empty()` equivalence into this signature, and downstream packets must not assert one: this packet handles the first layer in the *caller* (`run_finalization` skips `idx == 0`, pinned by `AC-8`), so `distance_to_prev_boundary` is **never reached** on layer 0 under this design and "`None` means the first layer" is false as stated. Packet 191, which consumes this function, rests its normative `None` rule on the reachable case only — a layer whose previous layer contributed no `OuterWall` segments — and does not equate `None` with the first layer. If a future revision wants `None`'s trigger to be contractual, it needs its own AC here.
  - `base_speed` — unchanged; it already returns `outer_wall_speed` / `inner_wall_speed` / `thin_wall_speed` and `0.0` for every other role, which is PnP's stand-in for canonical's `(is_bridge || is_perimeter)` conjunct and for `ref_speed`'s external-vs-internal selection.
  - `run_finalization` — gate on `config.get_bool("enable_overhang_speed").unwrap_or(true)`; keep the existing all-zero-overhang-speeds early return; skip the speed path for `idx == 0`; per entity build `factors: Vec<f32>` of `path.points.len()` entries and emit one `EntityMutation::SetPointSpeedFactors(factors)`; remove `EntityMutation::SetSpeedFactor` entirely.
  - The *produce* phase — record `(x0, y0, x1, y1)` segments of this layer's `OuterWall` loops (closing the loop) in addition to the existing `(x, y, curled_height)` points the curl feature needs. Both lists are per-layer scratch; neither is persisted.
- **Curl merge, in canonical order.** The curl feature already synthesises an *artificial distance* per point (`flow_width * (1 - distance/dist_limit)^2 * (curled_height / (lh * 10))`). Feed that artificial distance to the **same** `calculate_speed` to obtain `curled_speed`, and apply `extrusion_speed = min(curled_speed, extrusion_speed)` **after** the `min(extrusion_speed, original_speed)` clamp — verified as canonical's order in `estimate_extrusion_quality`, and it is why a curled-line slowdown can legitimately push below `original_speed`. Today the module instead buckets the artificial distance through `quartile_for_distance` and merges via `max(overhang_q, curl_q)`; that merge disappears.
- **`quartile_for_distance` and the module's private `BAND_BOUNDARY_MULTIPLIERS` are deleted together.** `quartile_for_distance` has no remaining caller once curl feeds `calculate_speed` directly, and it is the const's only reader. Deleting the function alone orphans the const and trips `-D warnings` on the very gate Step 5 requires clean; deleting both is the only self-consistent option. This touches **only** the module's local duplicate — `crates/slicer-core/src/algos/overhang_annotation.rs`'s `BAND_BOUNDARY_MULTIPLIERS` and banding geometry are out of bounds and stay exactly as they are. **Do not extend that to the whole file:** if `[BLOCK-1b]` resolves to "proceed", that file's **doc-comment** must be corrected in-packet (see §Out-of-Bounds Files and `packet.spec.md` §Scope Boundaries), because it would otherwise describe as an intentional deviation something the tree no longer does. An earlier revision of this sentence said the file "stays exactly as it is", contradicting this design's own carve-out. Record in the deletion comment that the "Keep these two lists numerically identical" invariant no longer has a module-side list to keep in sync.
- **Rejected alternative 1 — derive a pseudo-distance from the quartile.** Map `q ∈ {1,2,3,4}` to a representative distance and interpolate. Rejected: every point in a band shares one distance, so the output is the same step function the module already produces. It would satisfy a naive "interpolation exists" grep and satisfy nothing else, which is why AC-5 asserts **at least two distinct factors within one entity** rather than the presence of interpolation code.
- **Rejected alternative 2 — carry a continuous per-point overhang distance in the IR. NOTE THE CONTRADICTION, IT IS DELIBERATE AND STILL OPEN:** this is exactly what §Open Questions recommends as option **(C)**. The rejection below is the *original* reasoning, retained verbatim so the fork is auditable rather than quietly rewritten; it weighs blast radius only. Option (C) reweighs the same trade-off against ADR-0031 conformance, which the original reasoning never considered, and reaches the opposite conclusion. **If the maintainer picks (C), this bullet is superseded and must be rewritten, not left standing.** Original reasoning follows. The faithful analogue of canonical's `ExtendedPoint::distance`, and it would let the prepass (which already works against real slice footprints) supply an unbiased distance. Rejected on blast radius: it means a new field on `Point3WithWidth` — hundreds of exhaustive struct literals across well over a hundred files, plus a `point3-with-width` WIT record change — the same `L` that packet 189 rejected for the speed field, for the same reason.
- **Rejected alternative 3 — measure against the previous layer's slice boundary.** What canonical does. Rejected because a `PostPass::LayerFinalization` guest cannot reach `SliceRegionView` at all. **Corrected reasoning — the earlier wording here ("a new host service or a new `[ir-access]` read plus DAG re-validation") is what `[BLOCK-3]` itself calls vague and partly wrong, and it survived a round after being flagged:** `[ir-access]` gates DAG validation, not what the WIT hands the guest. Measured: `slice-region-view` is declared in `crates/slicer-schema/wit/deps/ir-types.wit` and every `use` of it sits in `world-layer.wit`; `world-finalization.wit` never imports **`slicer:ir-handles`** — note the package name, which is `slicer:ir-handles` and **not** `slicer:ir-types` despite the file being named `ir-types.wit` (`rg -n '^package' crates/slicer-schema/wit/deps/ir-types.wit` → `package slicer:ir-handles;`; `slicer:ir-types` has **zero occurrences under `crates/`** — the only surviving hits are five lines in archived packets under `.ralph/specs/_OLD/` — so an earlier revision of this paragraph named a package that no live code declares) — its `run-finalization` takes only `(layers, output, config)`, `layer-collection-view` exposes six methods and `host-services` fifteen functions, none surface- or region-related. ## Data and Contract Notes

- **IR/manifest contracts.** `factors.len()` MUST equal the target entity's `path.points.len()`. Packet 189's `apply_to` rejects a mismatch with an `Err`, but `crates/slicer-wasm-host/src/dispatch.rs` swallows that `Err` with `log::warn!` — so in the live WASM path an off-by-one is a **silent no-op**, not a failure. Size the vector from `entity.path.points.len()` directly and never from a filtered subset.
- **Factors are multipliers, not speeds.** `EntitySpeedProfile.factors[i] = per_point_speed_mm_s / base_speed(role)`. `resolve_feedrate` re-applies the role base speed and its `clamp(0.05, 5.0)`; emitting absolute mm/s here would be doubly scaled.
- **`ref_speed` and `original_speed` are two canonically distinct bases that this port deliberately collapses — keep them two separate parameters anyway.** Canonical's `estimate_extrusion_quality(…, float ext_perimeter_speed, float original_speed, …)` resolves every percentage section against `ext_perimeter_speed` and **never** against `original_speed`; `GCode::_extrude` passes `ref_speed` for the first and its own `speed` argument for the second, so the terminal `min(extrusion_speed, original_speed)` compares two mm/s values from different bases. In PnP both currently evaluate to `base_speed(role, config)` — not by coincidence but by definition, because a PnP speed factor *is* a multiplier over that base, so the path's unmutated speed and the role reference speed are the same number. That equality is a property of today's PnP, not of the algorithm: canonical additionally floors `ref_speed` by `filament_max_volumetric_speed / mm3_per_mm` and by `scarf_joint_speed` when sloped, neither of which is available to this module and neither of which is borrowed. **Therefore `build_speed_sections` takes `ref_speed` and `calculate_speed` takes `original_speed` as separate named parameters even though the live caller passes the same value to both**, `AC-14` exercises them with deliberately different values, and the `DEV-009` progress paragraph records the collapse together with the two unborrowed floors. Merging the parameters would make a future divergence unrepresentable and undetectable.
- **Section speeds are absolute mm/s; the conversion to a factor happens once, at the emission boundary.** `calculate_speed` returns mm/s (canonical rounds mm/s), and only when building the `SetPointSpeedFactors` vector is each value divided by `base_speed(role, config)`. Dividing earlier would make the `round` round a multiplier, which quantises to 0 or 1.
- **`path_width` is shared with packet 191.** Canonical feeds the same `path.width` both to the section-distance formula and to `estimate_points_properties` as `flow_width`. Whatever this packet resolves as `path_width` (see §Open Questions `[FWD]`) is what packet 191's `min_spacing = flow_width * 0.25` and `boundary_offset = 0.5 * flow_width` must use — expose it rather than computing it inline at a single call site.
- **WIT boundary.** None crossed by this packet beyond the variant packet 189 already added. The manifest gains keys; `[ir-access]`, `[claims]` and `[stage]` are unchanged, so no DAG edge moves.
- **Determinism/scheduler constraints.** `[hints] layer-parallel-safe = false` already holds for this module and must stay false: the per-point distance depends on the previous layer's produced segment list, so the Z-order walk is load-bearing. `nearest`-style scans must break ties deterministically (`total_cmp`, as the existing `nearest_reference_point` does) — `DEV-093` records that the pipeline already has a non-determinism problem and this packet must not add to it.

## Locked Assumptions and Invariants

- **A point with `overhang_quartile == None` is not an overhang**, regardless of its measured distance. Locked; `AC-N1` defends it, and the module's `[ir-access]` declaration depends on it.
- **All four `overhang_*_4_speed` at 0 ⇒ zero mutations**, unchanged from today. Locked by the existing early return; `AC-10` defends it. Without it, the `< 0.5` guard would turn every section into 100 % and emit a full-length all-1.0 profile on every wall entity of every layer — a behaviour change disguised as a no-op.
- **`enable_overhang_speed` absent ⇒ `true`.** Matches canonical's `ConfigOptionBoolsNullable{ true }` default and keeps existing configs behaving as they do today.
- **First layer emits no speed mutation.** Canonical `!on_first_layer()`; also the only layer with no previous-layer geometry to measure against.
- **Reversibility:** setting `enable_overhang_speed = false` restores the pre-packet behaviour of emitting nothing; setting the four overhang speeds to 0 does the same. No behaviour lock is introduced that config cannot undo.

## Risks and Tradeoffs

- **The `OuterWall`-centerline proxy biases every distance.** Distances measured from the previous layer's wall centerline are ~half an outer-wall width smaller than canonical's slice-boundary distances, which shifts every point toward the "less overhanging" end of the table. Logged as a new `DEV-###` row; the `[FWD]` in §Open Questions proposes the compensation and requires a decision rather than a silent choice.
- **Cost.** The per-point distance is an O(points × prev-layer-segments) scan per layer, on top of the existing O(points × prev-layer-points) curl scan. The module's manifest declares `estimated-ms-per-layer = 10`; if measurement shows that is no longer true, update the hint rather than leaving it stale. Canonical uses an `AABBTreeLines` distancer; this port keeps the linear scan the curl feature already established (the module doc-comment justifies that choice as "reasonable at this codebase's per-layer vertex counts") — but the overhang path visits *every* wall entity, not just `OuterWall`, so the constant is larger.
- **The mirror can rot silently.** `mirrored_run_finalization` duplicates the module's rule in a crate that cannot depend on the module. Its TRIPWIRE is a comment, not a compiler check; AC-9's structural probe is what converts it into something a preflight can verify.
- **Nine new tests plus four rewritten ones in a single binary** is the largest single review surface. Mitigated by giving each AC exactly one named test; the authoritative list is `requirements.md` §In Scope.
