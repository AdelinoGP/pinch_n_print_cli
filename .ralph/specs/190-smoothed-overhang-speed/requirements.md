## Problem Statement

`DEV-009`'s row names "smoothed-speed mode" as one of its two remaining open sub-items, and re-verifies it twice against source: "no interpolation/blending logic anywhere in `resolve_feedrate` or the classifier (confirmed unimplemented, still a flat quantized lookup)". This packet closes that sub-item.

### Three corrections to the plan's premise, each measured

`docs/specs/deviation-backlog-remediation-plan.md` locates DEV-009 in "`crates/slicer-gcode/src/emit.rs` (`resolve_feedrate`)". Grounded:

1. **`resolve_feedrate` holds no lookup table.** It is a per-role `match` selecting a base speed, then `speed_factor.clamp(0.05, 5.0)` times `base_speed * 60.0`, rounded to three decimals. Nothing in it is quantized and nothing in it needs to change for this packet.
2. **The quantization is in this guest module.** `run_finalization` (`modules/core-modules/overhang-classifier-default/src/lib.rs`) takes the **whole-entity maximum** of `overhang_quartile` and emits one `EntityMutation::SetSpeedFactor(overhang_speed(q, config) / base)`. `quartile_for_distance` buckets through `BAND_BOUNDARY_MULTIPLIERS: [f32; 3] = [0.5, 1.0, 1.5]`.
3. **The two DEV-009 features are not independent.** Canonical `ExtrusionQualityEstimator::estimate_extrusion_quality` derives `smallest_distance_with_lower_speed` from the `speed_sections` table this packet builds and passes it as `estimate_points_properties`' `min_distance` argument; the returned `extended_points` — including packet 191's inserted vertices — is the list `calculate_speed` is evaluated over. Verified against the checkout including the `if (!found) smallest_distance_with_lower_speed = -1.f;` fallback. Order is fixed: 189 → 190 → 191.

### The correction that actually shapes this packet: PnP has no per-point overhang distance

Canonical interpolates over a **continuous** per-point distance to the previous layer's boundary. PnP's only per-point overhang signal is `Point3WithWidth.overhang_quartile: Option<u8>` — a four-bucket quantization of that very distance, produced by `annotate_overhangs` (`crates/slicer-core/src/algos/overhang_annotation.rs`) as polygon bands and stamped onto points downstream. **The distance cannot be recovered from the bucket.** Interpolating over quartile-derived pseudo-distances would produce the same step function the module already produces and would be smoothing in name only.

**How the distance is obtained is the question the maintainer ruled on, and the answer is option (C).** This packet **reads** it. The continuous distance is stamped per point by the prepass in packet **`193-overhang-distance-prepass-carrier`**, onto `Point3WithWidth.overhang_distance_mm`, beside the existing `overhang_quartile`. `ADR-0053` is the decision record.

**The design this replaces, stated so a reader of the earlier revision does not reinstate it.** The original draft computed the distance **in-module**, on the reasoning that canonical computes it at G-code time too: `ExtrusionQualityEstimator` builds its distancer from the previous layer's geometry rather than in a prepass, and the module already walks `layers: &[LayerCollectionView]` in Z order with a previous-layer proximity scan for the curled-edge feature. The flaw was not the tier but the **geometry**: canonical measures against `unscaled_prev_layer`, a distancer over the previous layer's **slice boundary**, and a `PostPass::LayerFinalization` guest sees extrusion entities, not slices. The in-module port therefore had to measure against the previous layer's `OuterWall` **centerline** — roughly half an outer-wall width inside the true boundary, biasing every section threshold in the same direction — and then hand-compensate that bias. ADR-0031's Context gives the reason classification moved off walls in the first place: "Walls are merely an inset-by-`line_width/2` proxy for the true cross-section." Compensating a proxy the repo had already rejected outright is what `[BLOCK-2]` was about.

**Under option (C) there is no proxy, no bias, no compensation and no residual row.** Packet 193 measures against the real slice boundary in the prepass, where that geometry is available, and delivers exactly what canonical measures. The `DEV-###` row the option-(B) design owed is **not** filed; packet 193 files its own narrower row for the per-point-vs-per-path `boundary_offset` resolution.

**The carrier's contract is defined once, upstream, and cited here.** `overhang_distance_mm` is **signed** and already **`+ boundary_offset`-normalised** — the same quantity canonical writes into `ExtendedPoint::distance` as `distance_from_lines_extra<SIGNED_DISTANCE>(…) + boundary_offset` under its `<true, true, true, true>` G-code-path instantiation. The normative definition lives at `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract"; this packet and packet 191 both cite it and **neither restates it**. An earlier revision of this packet declared its in-module distance as an *unsigned* point-to-segment minimum, which every predicate packet 191 ports would have read wrongly — that disagreement is what the single-definition rule exists to prevent.

### Two canonical details that a plausible port gets wrong, both measured

1. **Section speeds are absolute mm/s and their percentages resolve against `ext_perimeter_speed`, not `original_speed`.** `estimate_extrusion_quality`'s signature binds the two separately — `(…, float ext_perimeter_speed, float original_speed, …)` — and the construction loop reads `speed = speeds.get_at(i).percent ? (ext_perimeter_speed * value / 100.0) : value`. `GCode::_extrude` passes `ref_speed` for the first and `speed` for the second, so the terminal `min(extrusion_speed, original_speed)` compares two mm/s values derived from **two different bases**. PnP collapses them today (both are `base_speed(role, config)`, because a PnP speed factor is by definition a multiplier over that same base), and that collapse is correct now and becomes silently wrong the moment PnP grows canonical's `filament_max_volumetric_speed` or `scarf_joint_speed` floors on `ref_speed`. The port therefore keeps them as **two separate named parameters**, `AC-14` pins the base, and the `DEV-009` progress paragraph records the collapse. Resolving against the wrong base scales every interpolated speed by the ratio of the two — a defect no absolute-value assertion localises.
2. **The tie handling is a flatten, not a de-duplication.** After the sort (ascending distance, ties **higher speed first**), canonical walks the vector overwriting each equal-distance entry's speed with the earlier one's. There is no `std::unique` and no `erase` in the file: the entry count is preserved at six. For the canonical literal `{90, 75, 50, 25, 13, 0}` the distances come out already ascending, so the sort is a no-op in practice — which is precisely the trap, because "simplifying" the flatten to a dedup looks harmless and changes the section count, and therefore which pair `calculate_speed` brackets. `AC-15` pins it.

A third, load-bearing for packet 191: the `path.width` feeding `distance = path.width * (1.0 - overlap/100.0)` is the **same value** passed as `flow_width` to `estimate_points_properties`. Whatever this packet resolves as `path_width` is therefore what packet 191's `min_spacing = flow_width * 0.25` and `boundary_offset = 0.5 * flow_width` must use.

### The "six-band schedule" exclusion, stated rather than silently omitted

The `DEV-009` row records a **user decision of 2026-07-03**: "Six-band schedule reclassified … this is a permanent, intentional, accepted deviation, not an open TODO", pointing at `crates/slicer-core/src/algos/overhang_annotation.rs`'s own doc-comment ("This is a recorded, intentional deviation — not a bug"). That decision is about **`annotate_overhangs`' four concentric quartile bands** at `{0.5, 1.0, 1.5} × line_width`, i.e. the geometry of the prepass classification. It is **untouched** by this packet.

That is a different table from canonical's `speed_sections`, whose distances come from `overhang_overlap_levels` `{90, 75, 50, 25, 13, 0}` inside `GCode::_extrude`. In canonical the two coincide because canonical has no quartiles at all and goes straight from distance to speed. In PnP they are separable, and this packet separates them: `overhang_quartile` keeps its four bands and keeps its job (is this point an overhang at all — `AC-N1`), while the **speed** table is canonical's six-entry one, built from an in-module distance. Nothing about the prepass banding changes, no `BAND_BOUNDARY_MULTIPLIERS` edit is in scope, and the accepted deviation stays accepted. State this explicitly in the `DEV-009` progress paragraph; do not let a reader infer that the accepted deviation was quietly reopened.

  - a `speed_sections` builder taking the role **reference speed** as its own parameter: six `(distance, speed)` pairs where `distance = path_width * (1.0 - overlap / 100.0)` in unscaled millimetres, and each `speed` is an **absolute mm/s** value. The percentage entries resolve against `ref_speed` (canonical `ext_perimeter_speed`) — the logical table is `[100 %, overhang_1_4, overhang_2_4, overhang_3_4, overhang_4_4, sixth]`, each of the middle four falling back to `100 %` when its configured absolute value is `< 0.5` ("unset means don't slow down"); the sixth is `overhang_4_4_speed` repeated (same guard) when `slowdown_for_curled_perimeters`, else `bridge_speed` as a percentage of `ref_speed` with **no** guard. Sorted ascending by distance with ties broken **higher speed first**, then **flattened, not de-duplicated**: an entry whose distance equals the previous one's has its speed overwritten with the earlier one's and is **retained**, so the table always has six entries (`AC-15`).

  - **reading** each point's `Point3WithWidth.overhang_distance_mm` — the signed, `boundary_offset`-normalised value packet 193 stamps. **No in-module boundary scan is written.** An earlier revision of this line specified "a point-to-segment distance from each point to the previous layer's `OuterWall` polyline segments, replacing the current point-to-point `nearest_reference_point` for the overhang path"; option (C) deletes that work entirely. `nearest_reference_point` stays exactly as it is, serving the curl feature alone, and the produce phase does **not** grow a segment list.
  - the manifest's `[ir-access] reads` list gains `LayerCollectionIR.overhang_distance_mm`. The existing `LayerCollectionIR.overhang_quartile` entry stays — the quartile remains the gate (`AC-N1`). A declaration that under-states the reads is as false as one that over-states them.
  - per-point speed `min(calculate_speed(d_curr), calculate_speed(d_next))`, then `min(…, original_speed)`, then the curl term `min(curled_speed, …)` applied **after** that clamp (canonical order).
  - gate `enable_overhang_speed` (absent ⇒ `true`) and skip `layers[0]` (canonical `!on_first_layer()`); keep the existing all-zero-overhang-speeds early return.
  - emit exactly one `EntityMutation::SetPointSpeedFactors(factors)` per qualifying entity, `factors.len() == path.points.len()`, each entry the per-point speed divided by the role's base speed.
  - remove `EntityMutation::SetSpeedFactor` from the module entirely.
