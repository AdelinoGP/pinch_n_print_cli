# Packet Contract: 189-per-point-speed-factor-carrier

## Goal

Give PnP a per-point speed carrier that does not exist today: add `EntitySpeedProfile` and the `LayerCollectionIR.speed_profiles` side table (`crates/slicer-ir/src/slice_ir.rs`), an additive `EntityMutation::SetPointSpeedFactors(Vec<f32>)` channel from guest to host (`crates/slicer-schema/wit/deps/finalization-layer-finalization/finalization-layer-finalization.wit`, `slicer_sdk::traits::EntityMutation`, `slicer_wasm_host::host::WitEntityMutation`, the `dispatch.rs` and `slicer-macros` translations, and `FinalizationOutputBuilder::apply_to`'s `MergeOp::ModifyEntity` arm), and make `DefaultGCodeEmitter::emit_gcode` (`crates/slicer-gcode/src/emit.rs`) resolve the `F` token per point from that profile — indexed by **original** point index so the per-role polyline simplification cannot shift the mapping — while an absent profile keeps the existing whole-entity `ExtrusionPath3D::speed_factor` behaviour byte-for-byte.

## Scope Boundaries

This packet ships the carrier and nothing that varies speed within an entity in practice: the only live producer of speed mutations, `modules/core-modules/overhang-classifier-default/src/lib.rs`, is deliberately left untouched, so with today's classifier every point of an entity still resolves the same factor and no golden moves. Changing that producer is packet 190; mid-segment vertex insertion is packet 191. `Point3WithWidth` is deliberately **not** given a per-point speed field (see `design.md` §Code Change Surface for the several-hundred-site blast radius that rejects it — a ledger fact to re-derive, not a number to quote), and no config key, no G-code header field, and no `overhang_*` behaviour changes here.

## Acceptance Criteria

**Mandatory conventions for every `cargo test` command below — measured defects, not style:**

1. **`rg "^test result:"` — the colon is load-bearing.** Unanchored `^test result` also matches libtest's per-test NAME line (a test whose own name starts with `result`), which carries no `0 failed` and false-reds an otherwise green run.
2. **`rg -v "0 passed"` and `rg -v "0 failed"` are banned as guards.** `test result: FAILED. 3 passed; 4 failed;` contains neither literal, so both forms report success on a partial failure.
3. **`--exact` needs the test's module-qualified path.** Every binary this packet uses `--exact` against (`gcode_feedrate_emission_tdd`, `finalization_builder_tdd`) is a standalone integration binary whose tests sit at the binary root, so a bare name is already the full path — verified by `--list` on this tree (e.g. `speed_factor_modulates_role_speed: test`, not `something::speed_factor_modulates_role_speed`). **`ir_tests` is NOT such a binary and must not be listed as one:** `rg -n '^mod ' crates/slicer-ir/tests/ir_tests.rs` returns `mod tests {`, so its tests are `tests::<name>` and a bare `--exact` name would select nothing. That is harmless here only because no AC runs `--exact` against it (AC-9 runs the whole binary). Bucketed binaries under `crates/slicer-runtime/tests/{unit,contract,executor,integration,e2e}` are the same case and need the `<file_stem>::` prefix; none is used with `--exact` here either.
4. **Guard shape follows how many `^test result:` lines the command can emit.** Single binary → `… | rg "^test result:" | rg -q "^test result: ok\. [1-9]"`. Whole crate / multi-binary selector → the capture-file form in AC-8, with a **unique** `target/guard-<key>.txt` per criterion so concurrent criteria cannot overwrite each other.
5. **A `python3` probe's verdict is its stdout, never its exit code.** AC-2 and AC-11 are written as `sys.exit(print(…))` / a bare `print(…)`; `print` returns `None`, so `sys.exit(None)` exits **0** and both commands exit 0 whether they printed `PASS` or `FAIL`.
