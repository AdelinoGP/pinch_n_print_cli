# Design: 188-custom-gcode-conditional-points

## Controlling Code Paths

- Primary code path: `run_gcode_postprocess` in `modules/core-modules/machine-gcode-emit/src/lib.rs`, specifically the single forward walk over `commands` that packet 187 introduced for layer boundaries. This packet adds two more site tests to the **same** walk.
- Toolchange site source: `DefaultGCodeEmitter` (`crates/slicer-gcode/src/emit.rs`) pushes `GCodeCommand::ToolChange { after_entity_index, from, to }` at intra-layer tool transitions and at layer-boundary cross-layer tool resets. **Read-only in this packet.**
- Role site source: the same emitter pushes `GCodeCommand::Raw { text: orca_type_label(role).to_string() }` — e.g. `";TYPE:Outer wall"` — whenever `role_equals(prev_role, role)` is false. **This is canonical's `;TYPE:` *tag* gate, which is not the same member as canonical's role-*template* gate.** Measured in `GCode::_extrude`: the three role templates are emitted under `path.role() != m_last_extrusion_role`, while the tag (`GCodeProcessor::ETags::Role`, whose reserved tag string is `"TYPE:"`) is emitted under `path.role() != m_last_processor_extrusion_role`. The two members are assigned independently — the wipe-tower path sets `m_last_processor_extrusion_role = erWipeTower` without touching `m_last_extrusion_role` — so canonical can fire one gate without the other. PnP has only the tag, so it splices there; with no wipe-tower path in the pipeline today the two conditions coincide, and the divergence is recorded rather than modelled. **Read-only in this packet.**
- Neighboring tests/fixtures: `modules/core-modules/machine-gcode-emit/tests/machine_gcode_emit_tdd.rs` (top-level `#[test]` fns; `slicer_sdk::test_prelude::config_with` builds a `ConfigView` with exactly the supplied pairs), `crates/slicer-runtime/tests/integration/machine_start_end_gcode_emission_tdd.rs` (single-material e2e), and `crates/slicer-runtime/tests/executor/cube_4color_gcode_output_tdd.rs` (four-tool e2e via `run_slice` and `SliceRunOptions`, whose `config_overrides: HashMap<…>` field is the hook AC-8 needs).
- OrcaSlicer comparison: see `requirements.md` §OrcaSlicer Reference Obligations; do not repeat delegation rules.

## Architecture Constraints

<!-- snippet: wasm-staleness -->
- Guest WASM is **not** rebuilt by `cargo build` or `cargo test`. After editing any path in this packet's change surface that feeds the guest build (see `CLAUDE.md` §"Guest WASM Staleness"), the implementer MUST run `cargo xtask build-guests --check` and, if `STALE:` is reported, rebuild without `--check` before re-running the failing test. Stale-guest failures look unrelated to the change but are caused by it.

- Config key strings must be snake_case in Rust and in the manifest. All six new keys already are.
- `ConfigView::keys` (`crates/slicer-ir/src/slice_ir.rs`) returns its own `fields` map sorted, with manifest scoping applied by the host at construction rather than by `keys()` itself. This is why AC-N3 works: an undeclared `file_start_gcode` is simply invisible to the module, so leaving it out of the manifest is a sufficient and observable way to "not implement" it.
- A guest `ModuleError` is mapped by `crates/slicer-wasm-host/src/dispatch.rs` to `slicer_ir::PostpassError::FatalModule` with the message `"module error (code={}, fatal={}): {}"`, returned unchanged by `crates/slicer-runtime/src/postpass.rs` and rendered as `"postpass failed: {e}"` by `crates/slicer-runtime/src/pipeline.rs`.
- No geometry and no millimetre/internal-unit conversion occurs here. `layer_z` / `max_layer_z` remain packet 187's carried **text**, and the new variables are integers or role labels, so the `coord-system` constraint does not apply and `mm_to_units` must not appear in this change surface.
- Determinism: the walk stays a single forward pass; per-site state is `(toolchange_count, current_tool, last_role_label)` plus 187's layer state. No map iteration may enter the emitted text.

## Code Change Surface

- **Registry extension.** `InjectionSite` gains four variants — one per distinct splice position: `FilamentEnd` and `FilamentChange` (before a `ToolChange`, in that order), `FilamentStart` (after it), and `ExtrusionRoleChange` (before a `;TYPE:` marker, carrying all three role options in table order). `INJECTION_POINTS` grows from five entries to eleven. The table's declaration order is the emission order within a site, so the three role entries must appear in the order `change_extrusion_role_gcode`, `filament_change_extrusion_role_gcode`, `process_change_extrusion_role_gcode`, and the two pre-toolchange entries in the order `filament_end_gcode`, `change_filament_gcode`.
- **Toolchange placement.** Canonical `GCode::set_extruder`'s multi-extruder path emits, in order: retract, `filament_end_gcode`, ooze-prevention pre-toolchange, `change_filament_gcode`, `;_FORCE_RESUME_FAN_SPEED`, `m_writer.reset_e`, `m_writer.toolchange` (the `T<n>` select), `m_writer.set_temperature`, `filament_start_gcode`. PnP's `GCodeCommand::ToolChange` is the analogue of `m_writer.toolchange`, so the two "before" templates precede it and `filament_start_gcode` follows it. **The tool-select is always re-emitted.** Canonical drops the writer's `T<n>` text only when `custom_gcode_changes_tool` finds a matching `T<id>` inside the parsed `change_filament_gcode`; PnP does not parse the template and must not invent that suppression, because dropping a `ToolChange` the emitter produced would silently change which tool prints.
- **Role placement.** Canonical `GCode::_extrude` emits all three role templates **before** the `;_EXTRUSION_ROLE:` block and the `;TYPE:` tag. PnP splices them before the `;TYPE:` `Raw`. `extrusion_role` is the substring **after** `;TYPE:`. **`orca_type_label` returns the prefix as part of its value** (`-> &'static str`, arms like `ExtrusionRole::OuterWall => ";TYPE:Outer wall"`), and `emit.rs` pushes that whole string as the `Raw` text, so the module must strip `";TYPE:"` before binding. An earlier draft said the label *is* `orca_type_label`'s output and added "no re-mapping is needed or wanted" — that sentence was actively harmful and is deleted. What remains true after stripping: the residue is already the exact string OrcaSlicer's viewer parses (`ExtrusionEntity::string_to_role`), so no *label translation* is needed — only prefix removal. `last_extrusion_role` is the previous marker's label, empty before the first. Canonical's initial value is `erNone`, whose rendered spelling PnP does not attempt to reproduce; the empty string is used and the divergence is recorded.
- **Per-option variable sets, transcribed not unioned.** From canonical `s_CustomGcodeSpecificPlaceholders`:
  - the three role options → `{layer_num, layer_z, extrusion_role, last_extrusion_role}` — note **no** `max_layer_z`, which is what AC-N1 tests, **and note that `layer_num` here is N+1, not N**. Canonical's extrusion-role block in `GCode::_extrude` sets it from `m_layer_index + 1`, while every other site in this packet and in 187 resolves it to N. The role sites therefore need their **own** context value; reusing 187's `LayerContext` unchanged transcribes the variable *names* correctly while unioning the *value semantics*, which is the precise shortcut AC-N1 and AC-N2 exist to prevent. AC-19 pins the contrast (`R=3` at a role site vs `T=2` at a toolchange site in the same layer). **The N invariant is positional, not expressional; port the value, never the expression.** `before_layer_change_gcode` textually reads `m_layer_index + 1` and still resolves to **N**, because it runs *before* `GCode::change_layer`, which holds the file's sole `++m_layer_index`; the role block reads the identical expression and resolves to **N+1** only because it runs *after* it. Copying `m_layer_index + 1` into a post-increment position silently produces the off-by-one AC-19 denies. Relatedly, `change_layer` increments only under `if (m_layer_count > 0)`, so canonical `set_extruder` calls made during start G-code legitimately observe `layer_num == -1`; the toolchange sites must tolerate "no layer has begun" rather than assume a layer index exists;
  - `change_filament_gcode` → `{layer_num, layer_z, max_layer_z, previous_extruder, next_extruder, toolchange_count}` (canonical's full set also carries the flush/travel group, which PnP does not model — see the residual row);
  - `filament_end_gcode` → `{layer_num, layer_z, max_layer_z, filament_extruder_id}`, with `filament_extruder_id` bound to the **old** tool (canonical uses `get_extruder_id(old_filament_id)` on this path);
  - `filament_start_gcode` → `{layer_num, layer_z, max_layer_z, filament_extruder_id}` (all four at N-semantics; AC-20 pins that the three layer variables actually resolve here) with `filament_extruder_id` bound to the **new** tool — **not** the bare `{filament_extruder_id}` the table lists. That entry is a third table drift: the runtime `DynamicConfig` at the `placeholder_parser_process("filament_start_gcode", …)` site in `GCode::set_extruder` also sets the three layer variables, and transcribing the table literally would fatally reject `[layer_num]` there under packet 186's rule. Still **no** `next_extruder` / `previous_extruder`, which is what AC-N2 tests — those were confirmed by exhaustive grep to be set only on the two `change_filament_gcode` configs, and neither name is a config option, so the parser's config fallback cannot reach them either.
  Implement this as a `site → &[&str]` mapping consulted when building each site's lookup, so a reviewer can diff it against the canonical table line by line.
- **`toolchange_count`** is 1-based and increments across the whole print (canonical `m_toolchange_count`), not per layer.
- **Exact functions, manifests, tests, and fixtures.**
  - `run_gcode_postprocess` — two new site tests inside 187's forward walk; three new pieces of walk state.
  - `InjectionSite` — four new variants; `INJECTION_POINTS` — six new entries.
  - `machine-gcode-emit.toml` — six new `[config.schema.*]` string blocks, `default = ""`, `group = "Machine G-code"`.
  - `machine_gcode_emit_tdd.rs` — add `toolchange_trio_brackets_the_tool_select_in_canonical_order`, `toolchange_variables_carry_from_to_and_running_count`, `role_trio_precedes_the_type_marker_with_current_and_last_role`, `unset_toolchange_and_role_points_emit_nothing`, `role_sites_carry_layer_num_plus_one_while_toolchange_sites_do_not` (AC-19), `layer_variables_resolve_at_filament_start_gcode` (AC-20), `max_layer_z_in_role_gcode_is_fatal`, `next_extruder_in_filament_start_gcode_is_fatal`. **All eight are required** — the §Context Discipline Note makes this section the authoritative change list, so a test omitted here is a test the implementer never writes.
  - `machine_start_end_gcode_emission_tdd.rs` — add `role_change_gcode_precedes_every_type_marker`.
  - `cube_4color_gcode_output_tdd.rs` — add a `config_overrides`-accepting sibling of `slice_fixture_file` and `change_filament_gcode_precedes_every_tool_select`.
- **Rejected alternatives.**
  - *Deriving role changes from `GCodeCommand::Move { role }` instead of the `;TYPE:` marker.* Rejected — role equality in the emitter goes through `role_equals`, which treats `ThinWall` and `InnerWall` as the same label; a module-side re-implementation would drift from it, and the marker already encodes the emitter's decision.
  - *A separate forward pass per site class.* Rejected — a `ToolChange` can occur inside a role run and a `;TYPE:` marker inside a layer; separate passes make the interleaving depend on pass order rather than stream order.
  - *One shared variable set across all eleven points.* Rejected — it would make `[max_layer_z]` silently resolvable at a role site and `[next_extruder]` at `filament_start_gcode`, where canonical errors, and would erase the only observable difference between the sites. AC-N1 and AC-N2 exist to catch exactly this shortcut.
  - *Emitting `file_start_gcode` after `; HEADER_BLOCK_END`.* Rejected as a fake. Canonical's contract is "above `; HEADER_BLOCK_START`"; a point that lands elsewhere is worse than an absent one because it looks implemented.
  - *Declaring the five unreachable keys with a "not yet wired" note.* Rejected — a declared key that silently does nothing is precisely the failure mode `DEV-085`'s second half describes for the ten fictional macros.
  - *Modelling `custom_gcode_changes_tool`.* Rejected — it requires parsing the user's template for a `T<id>` and conditionally dropping an emitter-produced command.

## Data and Contract Notes

- **IR/manifest contracts.** Six new scalar string keys on one module's `[config.schema]`, taking it from eight to fourteen. No IR schema version change, no new struct field on a shared type, no public version constant bump — the struct-literal blast-radius discipline does not apply. `crates/slicer-runtime/tests/integration/manifest_default_reconcile_tdd.rs` enrols `classic-perimeters` and `arachne-perimeters` only. `gcode_header_thumbnail_config_blocks_tdd`'s CONFIG_BLOCK assertion is a lower bound ("at least 80 key-value lines"). The `integration` harness `slice_with_raw` seeds manifest defaults generically from `module.config_schema().entries`, routing string defaults to `binding_source` as the real value and to `pipeline_source` as an empty sentinel, so six `default = ""` keys need no harness edit. The `executor` harness goes through `run_slice` / `SliceRunOptions` and picks the schema up the same way.
- **The host↔module marker contracts.** `GCodeCommand::ToolChange` is a typed IR variant, so the toolchange site is structurally safe. The `;TYPE:` role marker is **text**, like packet 187's layer markers, and carries the same fragility: a future emitter change to `orca_type_label`'s prefix would silently stop the role sites from firing. Unlike the layer markers there is no malformed-state to detect — an absent `;TYPE:` marker is indistinguishable from a print with one role — so no `ERR_*` guard is possible here. State that limitation in the module's doc comment and rely on AC-7's end-to-end count equality (one `; PNP_ROLE` per `;TYPE:`) as the regression detector.
- **WIT boundary.** Unchanged. No `crates/slicer-schema/wit/**` edit and therefore no bindgen invalidation — but `modules/core-modules/machine-gcode-emit/src/**` and its `.toml` **are** guest-WASM inputs, so the freshness gate still applies.
- **Determinism/scheduler constraints.** `machine-gcode-emit` is the sole module registered at `PostPass::GCodePostProcess`, so there is no sibling-ordering interaction. All new state is scalar and advances monotonically through the single forward pass.

## Decisions of Record (ADR-0050 / ADR-0051) and Packet-Local Invariants

**This packet inherits, and does not re-decide, the architecture recorded in `docs/adr/0050-custom-gcode-architecture.md` (unknown-key fail-the-slice policy with no escape syntax; the placeholder domain as one module's manifest keys plus the alias table; engine ownership private to `machine-gcode-emit`; `INJECTION_POINTS` as a private closed `const` with declaration-order precedence — which is what lets this packet's three role templates share one `;TYPE:` site in canonical order) and in `docs/adr/0051-gcode-marker-contract-ownership.md` (the `;LAYER_CHANGE` / `;Z:` / `;HEIGHT:` marker contract; the `;TYPE:` role marker is the same class of unversioned host-published contract and is covered there). Both ADRs are authored by a separate workstream — **do not author or edit them from this packet.** The `filament_extruder_id` id-space constraint is an ADR-0050 decision with its own `DEV-###` row (AC-21). Below are only the invariants this packet itself owns.

- **Locked: the `;TYPE:` prefix is the role-change site.** A future emitter change to `orca_type_label`'s prefix must update this module in the same commit. There is no runtime tripwire; AC-7's count equality is the test-time one.
- **Locked: `GCodeCommand::ToolChange` is always re-emitted.** The module may bracket it but must never drop or reorder it.
- **Locked: per-option variable sets.** Widening any site's set to make a macro "just work" is a contract break, not a convenience.
- **Locked: the five unreachable points stay undeclared.** AC-N3 is the guard; adding any of them to the manifest without also solving its site is a regression.
- **Locked: `toolchange_count` is print-scoped and 1-based.**
- Not locked: the `InjectionSite` variant names, or whether the three role options share one variant or take three; only the emission order and the per-option variable sets are contractual.

## Risks and Tradeoffs

- **The role site depends on host-emitted comment text with no runtime tripwire.** Weaker than packet 187's layer sites, which can detect a malformed triple. Mitigated by AC-7's end-to-end count equality and by AC-12's guard that the emitter is untouched.
- **`filament_start_gcode` / `filament_end_gcode` / `filament_change_extrusion_role_gcode` are scalar where canonical is per-filament.** A user with different purge routines per material cannot express them. Recorded as a residual rather than half-modelled.
- **`change_filament_gcode`'s flush/travel variable group is absent**, so an imported OrcaSlicer toolchange template will fail the slice under packet 186's rule. That is the intended visible outcome, and it is exactly the asymmetry packet 186's own residual row already describes; this packet's row makes the toolchange instance of it concrete.
- **AC-10 is slow.** The four-colour bucket runs a full 3MF slice per test. Budget for it and do not re-run it to "see more output" — read the capture file named in AC-10's own command (`target/log-188-c4c.txt`). Every `cargo test` command in this packet writes a **distinct** capture path for exactly this reason: a shared `target/test-output.log` is clobbered within seconds by any concurrent run, which silently turns "read the log" into reading someone else's evidence.
- **Guest staleness.** Every `--test integration` and `--test executor` result is meaningless until `cargo xtask build-guests --check` is clean.

## Open Questions

- **Resolved, not `[FWD]`.** Canonical's `m_last_extrusion_role` starts at `erNone`; PnP substitutes the empty string before the first `;TYPE:` marker and does **not** attempt to reproduce that spelling. This is now a recorded residual with a verification hook: AC-16's row predicate requires the token `erNone`, so the decision cannot land undocumented. Do not guess a rendered spelling.
- **A decision of record, not an Open Question — see `docs/adr/0050-custom-gcode-architecture.md` and its own `DEV-###` row (AC-21).** `filament_extruder_id` binds the **old** tool at `filament_end_gcode` and the **new** tool at `filament_start_gcode` — confirmed. The re-derivation also surfaced an asymmetry that must be ported rather than tidied: canonical uses `int(get_extruder_id(old_filament_id))` at the end site (an **extruder** id) but raw `int(new_filament_id)` at the start site (a **filament** id), so the same key name carries two id spaces and the two differ on multi-extruder-per-filament configs. PnP's `GCodeCommand::ToolChange { from, to }` carries tool indices only and has no such distinction, so it binds `from` at the end site and `to` at the start site: the **direction** is faithful, the **id space** is not representable. **This is not merely a residual and is no longer recorded as a token.** An earlier draft's entire record of it was the string `get_extruder_id` inside AC-16's row predicate — which proves a token occurs in a table row, not that the constraint is a decision anyone can find, cite, or close. It is an **IR-level constraint binding future MMU / multi-extruder work**: any packet that gives PnP more than one extruder per filament must either extend `GCodeCommand::ToolChange` to carry both ids or knowingly substitute the wrong id at one of the two sites. It therefore gets **its own `DEV-###` row** (AC-21; re-derive the id at the moment of writing, never hardcode it) **and** is recorded in ADR-0050. Do not "fix" the asymmetry, and do not fold this back into AC-16.
