## Problem Statement

The overhang-speed parity record names "`ADD_INTERSECTIONS` mid-segment splitting" as its last remaining open sub-item after packet 190 closes smoothed speed, and re-verifies it twice against source: "zero matches for mid-segment vertex insertion at overhang-threshold crossings anywhere in `crates/`/`modules/` (confirmed unimplemented)". This packet closes it and closes the row.

### Why this packet is last, and why that ordering is structural rather than stylistic

The plan (`docs/specs/deviation-backlog-remediation-plan.md`) lists the overhang-speed parity record's two features as independent. Measured against the checkout, they are not, and the direction of the dependency puts this packet third:

- Canonical `ExtrusionQualityEstimator::estimate_extrusion_quality` computes `smallest_distance_with_lower_speed` **from the `speed_sections` table** and passes it as the `min_distance` argument to `estimate_points_properties`. `min_distance` is the primary gate on the segmentation branch this packet ports. Packet 190 builds `speed_sections`; before it exists there is no `min_distance` to compute, and the `!found ⇒ -1.f` fallback that routes the branch to its `line_len > 4.0` disjunct has nothing to fall back from.
- An inserted vertex only *does* anything if adjacent vertices can carry different speeds. That capability is packet 189's `LayerCollectionIR.speed_profiles` carrier consumed by packet 190's per-point interpolation. Run this packet first and every insertion produces two collinear points at the identical feed rate: strictly more G-code, strictly no behaviour change, plus the geometric risk of touching wall-loop point lists. **Near-zero observable value at non-zero risk** — which is the whole argument for the ordering.

The coupling is a resolution amplifier, not a correctness dependency: canonical's `!found ⇒ -1.f` branch means (a) degrades gracefully at the original vertex density, so 190 is complete and useful without 191. The order is nonetheless fixed: **193 and 189 (independent of each other, either order) → 190 → 191.** Packet 193 joined the chain with the maintainer's option (C) ruling: it stamps the continuous `Point3WithWidth.overhang_distance_mm` that 190 interpolates over and that every predicate this packet ports reads.

### The channel this packet must open, and why nothing existing will do

`estimate_points_properties` returns a **longer point list** than it was given. PnP's finalization mutation surface cannot express that. `slicer_sdk::traits::EntityMutation` has exactly two cases today (`SetSpeedFactor`, `SetFlowFactor`) plus whatever packet 189 added (`SetPointSpeedFactors`). `FinalizationOutputBuilder`'s **geometry-affecting** methods are `push_entity_to_layer`, `push_entity_with_priority`, `insert_entity_at`, `set_entity_order`, `sort_layer_by`, `insert_synthetic_layer_after` and `insert_synthetic_layer` — every one of which adds or reorders **whole entities**, and none of which rewrites an existing entity's point positions, widths or count. (That is the geometric subset, not the whole API: `modify_entity`, `get_ordered_entities`, `push_annotation` and `push_fan_speed` also exist and are non-geometric.) **One nuance worth stating precisely, because it is easy to overstate:** `SetFlowFactor`'s `apply_to` arm *does* write a per-point field in place (`for pt in e.path.points.iter_mut() { pt.flow_factor = v; }`), so the gap is not "no per-point write path exists" — it is that no primitive can change a point's **position, width, or the point count itself**, which is exactly what an insertion requires. This packet therefore adds `EntityMutation::SetPathPoints(Vec<Point3WithWidth>)` across the same five-file channel packet 189 established.

### Corrections to the canonical description, each measured against the checkout

Three claims that a careless port gets wrong, all verified:

1. **`t1` is not symmetric with `t0`.** The code computes `a0 = clamp((curr.distance + 3*boundary_offset)/line_len, 0, 1)` but `a1 = clamp(1.0f - (next.distance + 3*boundary_offset)/line_len, 0, 1)` — note the leading `1.0f -` — and only then `t0 = min(a0,a1)`, `t1 = max(a0,a1)`. The symmetric reading is the natural guess and places the second vertex on the wrong side of every asymmetric crossing.
2. **`<true,true,true,true>` is not the only instantiation repo-wide.** It is the only one on the G-code speed path. `Support/SupportSpotsGenerator.cpp` also instantiates `<true,true,false,false>` (in `estimate_malformations` and `estimate_supports_malformations`) and both forms inside `check_extrusion_entity_stability`. Port the G-code-path instantiation; do not restate the stronger claim.
3. **`ADD_INTERSECTIONS` is a non-type `bool` template parameter, not a macro.** The four parameters in order are `SCALED_INPUT`, `ADD_INTERSECTIONS`, `PREV_LAYER_BOUNDARY_OFFSET`, `SIGNED_DISTANCE`. A repo-wide grep for `#define ADD_INTERSECTIONS` returns nothing.

A fourth, recorded as a residual rather than a correction: the `p1` candidate's spacing test compares against `curr.position` rather than against `p0`, so `p0` and `p1` can land closer to each other than `min_spacing`. That is a latent upstream quirk; whichever way the implementer resolves it, `packet.spec.md` §Doc Impact Statement requires one `DEV-###` row saying so.
