# 191-overhang-add-intersections

## Goal

Port canonical `estimate_points_properties`' (`GCode/ExtrusionProcessor.hpp`) mid-segment vertex insertion into `modules/core-modules/overhang-classifier-default/src/lib.rs`: both the **threshold-crossing** branch (where a segment crosses the previous-layer boundary offset, insert one synthetic vertex per crossing carrying `distance = boundary_offset`, filtered by the two-sided `min_spacing = flow_width * 0.25` test) and the **segmentation** branch (up to two interior vertices at `t0`/`t1`, gated on `min_distance > 0 && (|curr.distance| > min_distance || |next.distance| > min_distance) && line_len >= 2mm` or on `min_distance <= 0 && line_len > 4mm`), with `min_distance` supplied by canonical's `smallest_distance_with_lower_speed` derived from packet 190's `speed_sections` table and its `!found ⇒ -1.f` fallback — carried into the IR by a new `EntityMutation::SetPathPoints(Vec<Point3WithWidth>)` geometry channel, and closing the overhang-speed parity record.

## Problem Statement

The overhang-speed parity record names "`ADD_INTERSECTIONS` mid-segment splitting" as its last remaining open sub-item after packet 190 closes smoothed speed, and re-verifies it twice against source: "zero matches for mid-segment vertex insertion at overhang-threshold crossings anywhere in `crates/`/`modules/` (confirmed unimplemented)". This packet closes it and closes the row.

### Why this packet is last, and why that ordering is structural rather than stylistic

The plan (`docs/specs/deviation-backlog-remediation-plan.md`) lists the overhang-speed parity record's two features as independent. Measured against the checkout, they are not, and the direction of the dependency puts this packet third:

- Canonical `ExtrusionQualityEstimator::estimate_extrusion_quality` computes `smallest_distance_with_lower_speed` **from the `speed_sections` table** and passes it as the `min_distance` argument to `estimate_points_properties`. `min_distance` is the primary gate on the segmentation branch this packet ports. Packet 190 builds `speed_sections`; before it exists there is no `min_distance` to compute, and the `!found ⇒ -1.f` fallback that routes the branch to its `line_len > 4.0` disjunct has nothing to fall back from.
- An inserted vertex only *does* anything if adjacent vertices can carry different speeds. That capability is packet 189's `LayerCollectionIR.speed_profiles` carrier consumed by packet 190's per-point interpolation. Run this packet first and every insertion produces two collinear points at the identical feed rate: strictly more G-code, strictly no behaviour change, plus the geometric risk of touching wall-loop point lists. **Near-zero observable value at non-zero risk** — which is the whole argument for the ordering.

The coupling is a resolution amplifier, not a correctness dependency: canonical's `!found ⇒ -1.f` branch means (a) degrades gracefully at the original vertex density, so 190 is complete and useful without 191. The order is nonetheless fixed: **193 and 189 (independent of each other, either order) → 190 → 191.** Packet 193 joined the chain with the maintainer's option (C) ruling: it stamps the continuous `Point3WithWidth.overhang_distance_mm` that 190 interpolates over and that every predicate this packet ports reads.

### The channel this packet must open, and why nothing existing will do

`estimate_points_properties` returns a **longer point list** than it was given. PnP's finalization mutation surface cannot express that. `slicer_sdk::traits::EntityMutation` has exactly two cases today (`SetSpeedFactor`, `SetFlowFactor`) plus whatever packet 189 added (`SetPointSpeedFactors`). `FinalizationOutputBuilder`'s **geometry-affecting** methods are `push_entity_to_layer`, `push_entity_with_priority`, `insert_entity_at`, `set_entity_order`, `sort_layer_by`, `insert_synthetic_layer_after` and `insert_synthetic_layer` — every one of which adds or reorders **whole entities**, and none of which rewrites an existing entity's point positions, widths or count. (That is the geometric subset, not the whole API: `modify_entity`, `get_ordered_entities`, `push_annotation` and `push_fan_speed` also exist and are non-geometric.) **One nuance worth stating precisely, because it is easy to overstate:** `SetFlowFactor`'s `apply_to` arm *does* write a per-point field in place (`for pt in e.path.points.iter_mut() { pt.flow_factor = v; }`), so the gap is not "no per-point write path exists" — it is that no primitive can change a point's **position, width, or the point count itself**, which is exactly what an insertion requires. This packet therefore adds `EntityMutation::SetPathPoints(Vec<Point3WithWidth>)` across the same five-file channel packet 189 established.

### Corrections to the canonical description, each measured against the checkout

Three claims that a careless port gets wrong, all verified:

1. **`t1` is not symmetric with `t0`.** The code computes `a0 = clamp((curr.distance + 3*boundary_offset)/line_len, 0, 1)` but `a1 = clamp(1.0f - (next.distance + 3*boundary_offset)/line_len, 0, 1)` — note the leading `1.0f -` — and only then `t0 = min(a0,a1)`, `t1 = max(a0,a1)`. The symmetric reading is the natural guess and places the second vertex on the wrong side of every asymmetric crossing.
2. **`<true,true,true,true>` is not the only instantiation repo-wide.** It is the only one on the G-code speed path. `Support/SupportSpotsGenerator.cpp` also instantiates `<true,true,false,false>` (in `estimate_malformations` and `estimate_supports_malformations`) and both forms inside `check_extrusion_entity_stability`. Port the G-code-path instantiation; do not restate the stronger claim.
3. **`ADD_INTERSECTIONS` is a non-type `bool` template parameter, not a macro.** The four parameters in order are `SCALED_INPUT`, `ADD_INTERSECTIONS`, `PREV_LAYER_BOUNDARY_OFFSET`, `SIGNED_DISTANCE`. A repo-wide grep for `#define ADD_INTERSECTIONS` returns nothing.

A fourth, recorded as a residual rather than a correction: the `p1` candidate's spacing test compares against `curr.position` rather than against `p0`, so `p0` and `p1` can land closer to each other than `min_spacing`. That is a latent upstream quirk; whichever way the implementer resolves it, `packet.spec.md` §Doc Impact Statement requires one `DEV-###` row saying so.

## Architecture Constraints

- **Inserted vertices must lie exactly on the original polyline.** Every insertion is a parameterisation of an existing segment (`t ∈ [0,1]` between two existing endpoints, or the intersection of that segment with the previous-layer boundary). No point may move and no new geometry may be introduced — the packet changes *sampling density*, never shape. `AC-7` asserts a `1e-4 mm` perpendicular tolerance.
- **Wall-loop closure is an invariant, not a convention.** `ExtrusionPath3D::is_closed()` compares `points.first().xy == points.last().xy`, and `crates/slicer-gcode/src/emit.rs` carries a defensive check that treats an unclosed wall as evidence "a wall mutator dropped the closing repeat". A geometry channel that can open a loop makes that check fire from outside the emitter's blame radius, which is why `apply_to` — not the module — enforces closure for `ExtrusionRole::is_loop()` roles (`AC-N1`).
- **Mutation ordering is part of the contract.** `apply_to` iterates `for op in self.merge_ops` in submission order. `SetPathPoints` must precede the same entity's `SetPointSpeedFactors`, because packet 189's profile branch length-checks against the entity's *current* point count. Documented in `docs/02_ir_schemas.md` §IR 10 by this packet.

- Coordinate units: **1 unit = 100 nm** (10⁻⁴ mm), NOT 1 nm like OrcaSlicer. Divide OrcaSlicer constants by 100. Use `Point2::from_mm(x, y)` or `mm_to_units()` at every mm↔unit boundary. Full porting checklist in `docs/08_coordinate_system.md`.

Canonical's `estimate_points_properties` works in *unscaled* millimetres too (its `unscaled_prev_layer` name says so), so the `2.f` and `4.0f` length gates and the `0.25`/`0.5`/`3 *` factors transfer as-is with **no** division by 100 and **no** `mm_to_units()`. The snippet is present because the packet adds geometry code; the concrete instruction it carries is *do not convert*, and a reviewer should check for a spurious `mm_to_units` rather than for a missing one.
- **No schema/version constant is bumped.** `CURRENT_LAYER_COLLECTION_IR_SCHEMA_VERSION` moved in packet 189; `CURRENT_PERIMETER_IR_SCHEMA_VERSION` moved in packet 193; adding a WIT variant case does not move an IR schema version, and no test hard-asserts one here.
- **Every distance this packet reads is signed and already `+ boundary_offset`-normalised, and that contract lives in exactly one place.** `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract" is normative; packets 190 and 191 both cite it and neither restates it. Three predicates in §Code Change Surface depend on it and would silently misbehave against an unsigned or un-offset value: the XOR crossing test (`> boundary_offset + EPSILON`) degenerates, the outer proximity test's `> -boundary_offset` half becomes unreachable, and `a0`/`a1`'s `+ 3 × boundary_offset` shifts both inserted vertices along the segment on every evaluation. **This was a live contradiction across the packet set for a round** — packet 190's original draft declared an *unsigned* point-to-segment minimum while this packet's every predicate reads canonical's signed value — and 193 exists in part to resolve it once rather than three times.
- **This module becomes a geometry mutator, which departs from ADR-0031's Decision text; `ADR-0053` is the superseding record and an amendment row is owed.** See §"ADR-0031 departure: the amendment this packet owes" below. Disclosure alone is not an amendment, and an earlier revision of this packet disclosed the departure while filing nothing.

## Data and Contract Notes

- **The distance contract is packet 193's, cited and never restated.** `Point3WithWidth.overhang_distance_mm` is the **signed** perpendicular distance in millimetres from the point to the **previous layer's slice boundary**, already normalised by `+ boundary_offset` where `boundary_offset = 0.5 × width` of that point. The single normative statement is `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract", which grounds it in canonical's `estimate_points_properties` (`OrcaSlicerDocumented/src/libslic3r/GCode/ExtrusionProcessor.hpp`) — `distance = distance_from_lines_extra<SIGNED_DISTANCE>(…) + boundary_offset`, instantiated `<true, true, true, true>` on the G-code speed path so both `SIGNED_DISTANCE` and `PREV_LAYER_BOUNDARY_OFFSET` are true. **Consumers read the value as already-normalised** and must not re-derive or re-add `boundary_offset` in order to *interpret* it; they do need `boundary_offset` as a literal in their own predicates, and there the rule is 193's: `0.5 × ` the point's own `width`. **Do not paraphrase any of this into this file** — a paraphrase is precisely how 190 came to declare an unsigned minimum while this packet's predicates read a signed offset value.
- **IR/manifest contracts.** `SetPathPoints` replaces `path.points` wholesale. `apply_to` rejects an empty vector and rejects a list that breaks the closing repeat when `ExtrusionRole::is_loop()` is true for the entity's role. It does **not** check that the new points lie on the old polyline — that is the producer's obligation and `AC-7`'s assertion, because a general geometry channel should not encode one consumer's parity rule.
- **Ordering.** `SetPathPoints` then `SetPointSpeedFactors`, same entity, same `merge_ops` sequence. Packet 189's profile branch length-checks against the entity's current point count, so the reverse order is rejected — and, at the WASM boundary, rejected *silently*: `crates/slicer-wasm-host/src/dispatch.rs` swallows `modify_entity`'s `Err` with `log::warn!`. Get the order right in the producer; do not rely on a fatal.
- **WIT boundary.** `set-path-points(list<point3-with-width>)` is additive on an existing `variant`, but `point3-with-width` is **not currently imported** by `finalization-layer-finalization` (its `use slicer:types/geometry.{…}` names only `extrusion-path3d, extrusion-role`). Both edits are required in the same change or the WIT does not parse. `crates/slicer-schema/wit/deps/types.wit` already defines the record, so no type is added — only an import.
- **Determinism/scheduler constraints.** `[hints] layer-parallel-safe = false` already holds and must stay false. `segment_intersections` must order its results deterministically along the segment; `DEV-093` records a pre-existing whole-pipeline non-determinism and this packet must not add to it. No `[ir-access]`, `[claims]` or `[stage]` entry changes, so no DAG edge moves.
- **Payload size.** A `SetPathPoints` payload is a full point list per mutated entity, crossing the WIT boundary once per entity per layer. That is larger than the two scalars the pre-existing mutations carry; it is bounded by the entity's own vertex count and only paid for entities that actually gained vertices (the module must emit no `SetPathPoints` when the list is unchanged — `AC-N2`).

## Locked Assumptions and Invariants

- **Insertions never move geometry.** Every inserted vertex lies on the original polyline within `1e-4 mm`. Locked; `AC-7` defends it.
- **Wall-loop closure survives every geometry mutation.** Locked at the `apply_to` boundary; `AC-N1` defends it.
- **Geometry mutation precedes the profile for the same entity.** Locked by packet 189's exact-length rule; `AC-2` defends it.
- **Insertion is strictly inside packet 190's gates.** Zero overhang speeds, or `enable_overhang_speed = false`, or the first layer ⇒ no mutation of any kind. Locked; `AC-9` defends it. Reversible entirely through config.
- **An inserted vertex inherits a non-`None` `overhang_quartile`.** Otherwise it would fall out of packet 190's `overhang_quartile.is_some()` gate and be assigned factor 1.0, producing a speed *spike* exactly where the port meant to add resolution.
- **A `None` distance takes the no-insertion path, everywhere.** The carrier is `Point3WithWidth.overhang_distance_mm: Option<f32>` (packet 193), and `None` is reachable. **Its two triggers are packet 193's `AC-N1` to define, not this packet's to invent:** a layer with no previous layer, and **a region whose previous-layer slice boundary is empty**. (**Not "i.e. the first layer"** — packet 190 skips `layers[0]` in the caller, pinned by its `AC-8`, so layer 0 never reaches this code. **And not "the previous layer contributed no `OuterWall` segments"** — that framing belonged to the option-(B) in-module scan, which option (C) deletes; under (C) this module never looks at previous-layer walls at all. `AC-N3`'s fixture must be re-grounded on 193's second trigger, the empty previous-layer *slice* boundary.) Every gate that consumes a distance must treat `None` exactly as it treats a failed gate: a segment either of whose endpoint distances is `None` is skipped by the crossing branch **and** the segmentation branch, and a candidate whose interpolated distance derives from a `None` endpoint is discarded rather than admitted. `0.0`, `f32::MAX` and `-1.0` are all forbidden substitutes — **packet 193's `AC-N1` enumerates exactly these three and is normative for this rule**; do not re-litigate the list here. `0.0` reads as "exactly on the boundary" and, because the carrier is *signed*, is a perfectly legitimate measured value rather than an out-of-band marker; `-1.0` is likewise a legitimate signed measurement *and* collides with `min_distance`'s own not-found sentinel; either would route such an entity into the `min_distance <= 0 && line_len > 4.0` disjunct and insert vertices where nothing was ever measured. `f32::MAX` satisfies `|d| > min_distance` and routes it into the other disjunct. **Defended by `AC-N3`, whose fixture must carry `line_len > 4.0` mm and `min_distance <= 0`** — with no stamped distance the crossing branch cannot fire at all, so the segmentation gate is the only discriminator, and a short segment or a positive `min_distance` would let a coerced implementation pass. Until round 3 this rule existed in exactly one prose sentence in §Code Change Surface, with no test, no AC and no entry here — and its failure mode is silent.
- **Canonical constants are not tunables.** `0.5 * flow_width`, `flow_width * 0.25`, `3 *`, `2.0`, `4.0` stay literals with provenance comments; no config key is added.

## Risks and Tradeoffs

- **`a1`'s leading `1.0 -` is the single most likely defect.** It is asymmetric with `a0`, it is easy to "tidy up" into symmetry, and a symmetric version still produces plausible-looking output. `AC-5` requires a fixture where **`(next.distance + 3 * boundary_offset) / line_len != 0.5`** so the asymmetry is actually exercised. **Not `a0 != 1.0 - a1`**, which an earlier draft specified here and in Step 1: writing `B = (next.distance + 3*boundary_offset)/line_len`, the correct `a1 = clamp(1 - B)` and the symmetric guess `clamp(B)` coincide exactly when `B == 0.5`, so that condition reduces to `curr.distance != next.distance` and is neither necessary nor sufficient — a fixture satisfying it can still pass under both implementations.
- **Point-count changes are invisible to whole-output G-code diffing.** `DEV-093` records that two runs of the same unmodified binary already differ by ~100-160 lines of exactly the "loops appear/disappear" shape, so byte comparison cannot attribute this packet's effect. Every criterion here is therefore structural or unit-level.
- **The `p0`/`p1` `min_spacing` asymmetry is an upstream quirk the port inherits or fixes.** Either choice is defensible; an undocumented choice is not. `packet.spec.md` §Doc Impact Statement requires one `DEV-###` row either way.
- **Cost.** `segment_intersections` is O(segments × boundary-segments) on top of packet 190's O(points × boundary-segments) distance scan, and it runs only for segments that pass the crossing predicate. Packet 190 authorises changing the module's `estimated-ms-per-layer` hint in-packet, so **re-read its current value rather than assuming `10`**; if this packet's additions make it wrong again, update it here rather than leaving a known-wrong scheduler input.
- **A larger `EntityMutation` payload crosses the WIT boundary per mutated entity.** Bounded by vertex count, and paid only where vertices were actually added.
