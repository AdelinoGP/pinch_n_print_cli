# Packet Contract: 185-arachne-width-bridge-parity

## Goal

Close the three open arachne-side flow/width parity deviations in `modules/core-modules/arachne-perimeters`: retype the two wall-width config keys to `float_or_percent` and resolve them through `ConfigView::get_abs_value` with canonical's explicit-zero→auto rule (D-164, arachne half); move `ArachneParams::default`'s wall-simplification tolerances from the 10×/5× tighter `0.05 mm`/`0.005 mm` to canonical's `0.5 mm`/`0.025 mm` and correct the falsified provenance comments (D-168); and add the per-vertex bridge exemption to `build_walls`'s spacing→width back-conversion so thick-bridge vertices carry canonical's bridge-thread width instead of a beading-derived one (D-163).

## Acceptance Criteria

Value assertions below are anchored (leading `: ` or a whole-line `^…$`) because `0.0025` is a strict prefix of nothing here but `0.25` **is** a substring of `0.0025`, and `0.005` is a substring of `0.0005`. Every unanchored substring check on these constants passes on the unfixed tree.

**Two mandatory conventions for every `cargo test` command below — both are measured defects this packet's preflight caught, not style preferences:**

1. **`rg "^test result:"` — the colon is load-bearing.** Unanchored `rg "^test result"` also matches libtest's per-test NAME line. Measured on this tree: `cargo test -p slicer-core --features host-algos` emits **75** `^test result` matches but only **74** `^test result:` summary lines; the extra is `test result_order_is_deterministic_for_same_input ... ok`, which carries no `0 failed` and therefore trips an `rg -v "0 failed"` guard on a genuinely green run.
2. **`--exact` requires the module-qualified test path.** Measured: `cargo test -p arachne-perimeters --lib -- wall_maximum_resolution_wired --exact` reports `1 filtered out`, `tests::wall_maximum_resolution_wired --exact` reports `1 passed`; `cargo test -p slicer-runtime --test integration -- arachne_manifest_defaults_are_the_code_fallbacks --exact` reports `247 filtered out`, the `manifest_default_reconcile_tdd::`-qualified form reports `1 passed`. A bare-name `--exact` command reports `0 tests ran` **forever**, including after a perfect implementation. In-crate `--lib` tests live under `tests::`; `crates/slicer-runtime/tests/integration/manifest_default_reconcile_tdd.rs` is reached as `manifest_default_reconcile_tdd::`.

Guard shape follows **how many `^test result:` summary lines the command can emit**, and the two forms are **not** interchangeable. Both reject a partial failure; they differ in how they detect a run that selected **zero** tests, which is the failure mode a name filter and a dropped feature flag both produce.

- **Single-result-line form — one test binary, with or without a name filter** → `… 2>&1 | rg "^test result:" | rg -q "^test result: ok\. [1-9]" && echo PASS || echo "FAIL: …"`. The `[1-9]` rejects a filtered-to-zero run *and* a partial failure in one test. Use it for every `--test <binary>` or `--lib -- <name> --exact` command. The older `| rg -v "0 passed"` shape is **banned**: `test result: FAILED. 3 passed; 4 failed;` contains no literal `0 passed`, so it reports success on a partial failure (verified against that exact string).
- **Multi-result-line form — a whole crate or a multi-binary target selector** (`-p slicer-core --features host-algos`, `-p arachne-perimeters --tests`) → capture the summary lines to a file, then test for a red **and** separately for non-emptiness:
  `… 2>&1 | rg "^test result:" > target/guard-<key>.txt; rg -q "[1-9][0-9]* failed|^test result: FAILED" target/guard-<key>.txt && echo "FAIL: …" || (rg -q "^test result: ok\. [1-9]" target/guard-<key>.txt && echo PASS || echo "FAIL: zero tests ran")`
  Do **not** use the single-result-line form here: `rg -q` succeeds on *any* one matching line, so one green binary would mask a red sibling. Do **not** use the bare `| rg -v "0 failed" && echo FAIL || echo PASS` form either — it prints **PASS** when every selected binary ran zero tests (measured: `cargo test -p slicer-core` with `--features host-algos` dropped yields dozens of binaries at `0 passed; 0 failed` and the bare form reports PASS). The first conjunct catches a red among greens; the second catches an **entirely** empty sweep; an empty capture falls through to `FAIL: zero tests ran`. **The second conjunct does not detect a partially-vacuous run** — one where a feature flag silenced some binaries while unrelated siblings still passed. Where that is the hazard (AC-9), the guard must add a third conjunct pinning a binary that is provably gated on the feature; see AC-9 for the measured reason and the exact form. `<key>` must be **unique per criterion** (`guard-ac9` for AC-9 and the identical §Verification command, `guard-s4-ap-tests` for Step 4's `-p arachne-perimeters --tests` sweep) so two criteria run concurrently cannot overwrite each other's capture. Only those two commands in this packet are multi-result-line; every other `cargo test` command here selects a single binary (`--lib` or `--test <name>`) and takes the single-result-line form.
