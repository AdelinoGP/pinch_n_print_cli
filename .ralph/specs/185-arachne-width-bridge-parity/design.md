## Architecture Constraints

<!-- snippet: coord-system -->
- Coordinate units: **1 unit = 100 nm** (10⁻⁴ mm), NOT 1 nm like OrcaSlicer. Divide OrcaSlicer constants by 100. Use `Point2::from_mm(x, y)` or `mm_to_units()` at every mm↔unit boundary. Full porting checklist in `docs/08_coordinate_system.md`.

<!-- snippet: wasm-staleness -->
- Guest WASM is **not** rebuilt by `cargo build` or `cargo test`. After editing any path in this packet's change surface that feeds the guest build (see `CLAUDE.md` §"Guest WASM Staleness"), the implementer MUST run `cargo xtask build-guests --check` and, if `STALE:` is reported, rebuild without `--check` before re-running the failing test. Stale-guest failures look unrelated to the change but are caused by it.

- **Which values are mm and which are units, in the same loop.** Every value this packet touches — wall widths, `1.125 × nozzle_diameter`, the simplification tolerances, and the bridge thread diameter `dmr` — is a plain-mm scalar and must **not** be scaled. The one exception sits inside the same function: `ring_pts_units` maps `p.x` / `p.y` through `mm_to_units` because it is compared against `polygons`, which live in scaled units. Hoisting `ring_pts_units` (Step 4) moves that boundary earlier in the function but does not change which side of it anything lives on.
- **Tolerances are squared mm², not units².** `smallest_line_segment_squared` and `allowed_error_distance_squared` are the *squares* of mm tolerances, squared directly with no ÷100. `0.5 mm → 0.25` and `0.025 mm → 0.000625`. Do not apply the coordinate divisor to either the value or its square.
- **The manifest default must stay a numeric TOML scalar.** `assert_exhaustive_reconcile`'s `Float(v)` arm calls `default.as_float().or_else(as_integer)` and **panics** on a string. The existing `float_or_percent` keys in this manifest (`overhang_reverse_threshold`, `min_width_top_surface`) use string defaults (`"0.0"`) and are consequently classified `Str("0.0")` in the reconcile table. Retyping the wall-width keys while keeping `default = 0.4` as a bare number is what lets their `Float(0.4)` rows stay untouched. Writing `default = "0.4"` would silently convert an AC-7 pass into a panic.
- **`field_type` is unvalidated.** `crates/slicer-scheduler/src/manifest.rs`'s `parse_config_field_entry` stores `field_type` as a free-form `String` and never checks it against `slicer_schema::VALID_CONFIG_TYPES` (that const has zero Rust consumers). A typo'd type string loads silently and behaves as an unknown type. Write `float_or_percent` exactly.
- **`parse_percent_default` is a validator, not a converter.** Its returned `ConfigValue` is discarded; `ConfigFieldEntry.default` keeps `v.to_string()`. So the retype changes what the manifest *accepts and validates*, not what it *transports*.
- **Range checks treat percents as raw magnitudes.** `crates/slicer-scheduler/src/config_resolution.rs`'s `is_numeric_field_type` / `check_scalar` compare the raw number against `min`/`max` regardless of the percent flag. With `min = 0.1` an explicit `0` auto sentinel is rejected before it ever reaches the module. Lowering `min` to `0.0` is therefore not cosmetic — it is what makes the retype functional.
- **Non-negotiable ordering inside `build_walls`.** `pt.width` must be finalised *before* `let widths: Vec<f32> = path.points.iter().map(|p| p.width).collect();` snapshots it into the width profile. The exemption therefore has to live inside the existing conversion loop, not in a later pass.

## Code Change Surface

### Selected approach

**D-164 (arachne half) — capability-only, residual filed.** Retype both wall-width keys to `float_or_percent`, lower `min` to `0.0`, keep `default = 0.4`, and resolve at the read site with:

```
match config.get_abs_value(key, nozzle_diameter_mm) {
    Some(v) if v > 0.0 => v,                       // explicit mm, or a resolved percent-of-nozzle
    Some(_)            => 1.125 * nozzle_diameter_mm,  // canonical Flow::auto_extrusion_width
    None               => defaults.<field>,            // key absent — unchanged 0.4
}
```

then feed the result through the existing `line_width_to_spacing` conversion **unchanged**. `get_abs_value` handles `Percent(p)` and `FloatOrPercent{is_percent:true}` as `p/100 × base` (returning `None` when `base <= 0`), and passes `Float(f)` and `FloatOrPercent{is_percent:false}` through verbatim. Default-config geometry does not move on this axis (AC-3).

The `<= 0 → auto` cut matches canonical `Flow::new_from_config_width`'s `if (!width.percent && width.value <= 0.)` test, and `1.125f * nozzle_diameter` is canonical `Flow::auto_extrusion_width`'s return for `frExternalPerimeter` / `frPerimeter`. **The originating plan said "0 → nozzle_diameter"; that is wrong** and would emit `0.4` where canonical emits `0.45`.

**D-168 — constants plus provenance correction.** `smallest_line_segment_squared: 0.0025 → 0.25`, `allowed_error_distance_squared: 0.000025 → 0.000625`, in both `crates/slicer-core/src/arachne/pipeline.rs` and the duplicate in `crates/slicer-sdk/src/host.rs`; manifest defaults `0.05 → 0.5` and `0.005 → 0.025`; `ARACHNE_FALLBACKS` rows to `Float(0.5)` / `Float(0.025)`.

**D-168's stated cause is false and must be corrected, not repeated.** The deviation row claims PnP "transcribed the `meshfix_*` constants instead of the wall ones". Canonical `meshfix_maximum_resolution()` and `meshfix_maximum_deviation()` are inline functions in `Arachne/WallToolPaths.hpp` returning `scaled<coord_t>(0.5)` and `scaled<coord_t>(0.025)` — **identical to the wall defaults**, and `WallToolPathsParams` initialises `wall_maximum_resolution = meshfix_maximum_resolution()` and `wall_maximum_deviation = meshfix_maximum_deviation()` from exactly those. No canonical constant is `0.05` or `0.005`. The nearest source of `0.005` is the *default argument* of the free `simplify(Polygons&, …)` in `WallToolPaths.cpp`, which `WallToolPaths::generate` overrides with the wall params anyway. The fix direction is unaffected; the in-code provenance comments and the log row's cause both are.

The third tolerance in the same `Default` impl — `maximum_extrusion_area_deviation` — **is already resolved and is out of this packet's scope.** It was ported out of band as `DEV-094`: comment, value (`2e-6 mm²`, derived from canonical's `scaled<coord_t>(2.)`) and the non-canonical formula it gated were all corrected together. Step 2a therefore has two comments to fix, not three. See §Open Questions for why the constant could not be fixed on its own, and for the two errors older revisions of this packet carried about it (the ratio and its direction).

**D-163 — a per-vertex, thick-bridges-gated width substitution.**

Three facts fix the design, and each contradicts a plausible reading of the deviation row:

1. **The exemption fires only when `thick_bridges` is on.** Canonical's predicate is `role == erOverhangPerimeter && flow.bridge()`. `flow.bridge()` returns `m_bridge`, which is set true **only** by the private bridge-taking `Flow` constructor, whose **only** caller is the static factory `Flow::bridging_flow`. `LayerRegion::bridging_flow` calls that factory on its `thick_bridge == true` branch; its `thick_bridge == false` branch returns `base_flow.with_flow_ratio(bridge_flow_ratio)` from an ordinary `Flow::new_from_config_width`-derived flow, which carries `m_bridge == false`. (`with_width` / `with_height` / `with_cross_section` all `assert(!m_bridge)`, so no non-thick path can produce one.) With `thick_bridges` off, canonical applies the ordinary `with_width(unscale(w) + height × (1 - π/4))` conversion to overhang perimeters like any other role. Verified by delegated read of `LayerRegion.cpp` and `Flow.hpp`.
2. **The substituted width is the bridge thread diameter, not the retained spacing.** Canonical substitutes `flow` *wholesale*; `Flow::bridging_flow(dmr, nozzle_diameter)` constructs `Flow{ dmr, dmr, bridge_extrusion_spacing(dmr), nozzle_diameter, true }`, so `width() == dmr` where `dmr = nozzle_diameter × √bridge_flow_ratio`. The naive transcription — "skip the back-conversion, leave the beading spacing" — is **wrong** and would reintroduce D-160 Bug B (a `0.357 mm` width on a `0.4 mm` wall) at bridge vertices, precisely the failure `crates/slicer-runtime/tests/executor/arachne_perimeters_simple_square.rs` exists to catch.
3. **It must be per-vertex.** PnP's `is_bridge` lives in `slicer_ir::WallFeatureFlags`, one per vertex, sized by `slicer_core::perimeter_utils::build_wall_flags` and pinned per index by `arachne_parity_arachne_path_is_bridge_flag_set_per_vertex`. A PnP wall loop can be **partially** bridged. Canonical's path-level exemption therefore has no PnP analog at path granularity; the only faithful transcription is per vertex.

Resulting shape inside `build_walls`, replacing the current uniform loop:

```
let is_outer_or_inner = matches!(loop_type, LoopType::Outer | LoopType::Inner);
// HOISTED above the conversion loop — the per-vertex bridge test now gates it.
let ring_pts_units: Vec<Point2> = /* unchanged mm_to_units mapping */;
let bridge_vertex: Vec<bool> = if !bridge_areas.is_empty() && is_outer_or_inner {
    ring_pts_units.iter().map(|p| point_in_any_polygon(p, bridge_areas)).collect()
} else { vec![false; path.points.len()] };
let bridge_thread_dmr_mm = nozzle_diameter_mm * bridge_flow_ratio.sqrt();
for (i, pt) in path.points.iter_mut().enumerate() {
    pt.z = z;
    if thick_bridges && bridge_vertex[i] { pt.width = bridge_thread_dmr_mm; }
    else { pt.width = flow_to_width(pt.width, layer_height_mm); }
}
```

and the existing marking block reuses `bridge_vertex[i]` instead of recomputing `point_in_any_polygon`.

**The hoist is provably inert.** `ring_pts_units` reads only `p.x` and `p.y`; the conversion loop writes only `p.z` and `p.width`. Moving the construction earlier cannot change its contents. `build_wall_flags` continues to receive `Some(&ring_pts_units)` unchanged. The `bridge_vertex` gate deliberately inherits the existing `Outer | Inner` restriction so `ThinWall` / `GapFill` / `NonPlanarShell` loops are never exempted — restating it rather than relying on the later block's copy.

**No double-counting.** With `pt.width = dmr` and the existing `flow_factor = bridging_flow(ratio, true, nozzle, pt.width, h) = π·dmr² / (4 · dmr · h) = π·dmr / (4h)`, the emitted volumetric rate is `width × h × flow_factor = π·dmr²/4` — byte-for-byte canonical `Flow::bridging_flow`'s `mm3_per_mm()` circular branch. The `height × (1 - π/4)` term is applied zero times, not twice.

**Test-vacuity hazard, called out because it will bite.** `bridge_vertices_get_round_section_factor_when_thick_bridges_on` derives its expected `flow_factor` from `pt.width` itself. Because the flow factor is *defined* as `(bridge area)/(width × h)`, that assertion holds under **any** width substitution and is therefore completely insensitive to this change. It will stay green whether the fix lands correctly, incorrectly, or not at all. The proof must be the new AC-12 test asserting `pt.width == dmr` **and** the resulting volumetric product, plus AC-N2's non-bridge control. Re-blessing the existing test is not evidence.

**Honest statement of the canonical anchor's limits.** PnP's in-code comment names `VariableWidth.cpp::thick_polyline_to_multi_path` as the source of this back-conversion. That is an **analogy by formula, not a call-graph correspondence**, and this packet does not upgrade the claim. `thick_polyline_to_multi_path` and `thick_polyline_to_extrusion_paths_2` both take a `ThickPolyline` — the classic / medial-axis path — and canonical's `variable_width` actually routes to the latter, which has **no** exemption. PnP's seam is `ExtrusionLine → ExtrusionPath3D`, which corresponds to canonical's Arachne `PerimeterGenerator.cpp::traverse_extrusions` → `extrusion_paths_append`. What justifies the port is that the formula `unscale(w) + height × (1 - π/4)` is byte-identical in all three places, and that the *reason* for the exemption (a bridge flow's width may not be re-derived; `Flow::with_width` asserts `!m_bridge`) applies identically at PnP's seam. Do not write, in code comments or the deviation log, that PnP's seam *is* `thick_polyline_to_multi_path`.

### Rejected alternatives and reasons

- **Adopt canonical's `0` default for the wall-width keys** (manifest `default = "0.0"`, code fallback `1.125 × nozzle`). Rejected **on fixture-stability grounds**: it widens default arachne walls from `0.4` to `0.45 mm` and moves every `ArachneParams::default()`-driven arachne fixture, stacked on top of D-168's tolerance move in the same packet. A secondary, *conditional* reason: packet 182 (`status: draft`, **not landed** — `crates/slicer-gcode/src/serialize.rs` still holds `outer_wall_line_width: 0.42`) intends to set a `; outer_wall_line_width = 0.4` header default, which this fallback would keep truthful. Do not restate 182 as landed; the rejection stands on the fixture-stability ground alone if 182 changes. Recorded as `[FWD]` below; reversing it is a one-line change in Step 1.
- **Fix D-164's ingestion half by teaching ingestion to produce a percent-bearing `ConfigValue`.** Rejected as out of scope: it touches `ResolvedConfig`'s producers, stales all 34 guest WASMs, and belongs with TASK-301 / TASK-302. Note the fix is **not** in `ResolvedConfig::to_config_map` — that function already transports arbitrary variants through its `extensions` merge (see §Data and Contract Notes). The missing piece is a live-path *producer*; today the only constructor, `parse_percent_default`, has its result discarded. Filed as a residual deviation worded about the parser.
- **Skip the back-conversion entirely at bridge vertices** (the literal reading of "exemption"). Rejected: reintroduces D-160 Bug B. See fact 2 above.
- **Apply the exemption at path granularity** (exempt a whole loop if any vertex is a bridge). Rejected: PnP loops are partially bridgeable; this would widen non-bridge vertices of a partially-bridged loop.
- **Apply the exemption regardless of `thick_bridges`.** Rejected: canonical's `flow.bridge()` is false on the non-thick branch, so this would over-apply. It would also break `bridge_vertices_get_bridge_flow_ratio_when_thin` for a correct reason, which is a good sign the gate is real.
- **Unify `simplify.rs`'s `ultra_short_threshold` with `allowed_error_distance_squared`.** Rejected: verified independent — it is the `ExtrusionLine.cpp` ~5 µm ultra-short-segment bypass, a hard-coded local that merely *coincides* with the old default value. Unifying them would couple two unrelated tolerances.
- **Fix `overhang_reverse_threshold`'s `get_float`/`float_or_percent` mismatch while nearby.** Rejected: it is a distinct pre-existing inconsistency with its own behavioural surface, and folding it in would make Step 1's blast radius unbounded.

## ADR Alignment

- **`docs/adr/0043-derive-arachne-bead-widths-from-wall-flows.md` — CONTRADICTED, amended by this packet.** §Decision item 2 specifies `outer_wall_line_width` / `inner_wall_line_width` on `arachne-perimeters` as "(plain mm floats, default 0.4, range [0.1, 2.0], group Walls — mirroring `classic-perimeters`)". AC-1 retypes both to `float_or_percent` and lowers `min` to `0.0`, which contradicts the *type* and *range* clauses. It **conforms** on the rest of item 2: the keys stay declared and read on `arachne-perimeters`, `preferred_bead_width_outer` still sources from the outer key and `optimal_width` from the inner key, `line_width_to_spacing` stays exactly where it is (AC-4), and the default stays `0.4` (AC-3), so no double-conversion is reintroduced. Item 1 (the retired `optimal_width` / `preferred_bead_width_outer` config keys) and item 3 (`ArachneParams`' canonical field names) are untouched.
- **The ADR authorizes this direction itself.** Its §Consequences already closes with: "Upstream models both wall-width keys as `coFloatOrPercent` with default `0` = 'auto from nozzle'; PnP's plain float `min 0.1` cannot express auto — logged as its own deviation row rather than silently narrowed." That deviation row is D-164, which is exactly what this packet closes (arachne half). **Do not re-scope the design to conform to decision item 2** — the ADR's own Consequences section anticipates the amendment.
- **Handling follows the established amend-in-place convention** — the two committed precedents are `D-161-ADR-0037-AMENDED` and `D-283-ADR-0046-AMENDED` (both verified present in `docs/DEVIATION_LOG.md`): the ADR text is edited as **packet work in Step 5b**, and a `D-185-ADR-0043-AMENDED` row is filed in `docs/DEVIATION_LOG.md` quoting the contested clause. ## Data and Contract Notes

- **IR/manifest contracts.** `slicer_ir::ConfigView::get_abs_value(key, base) -> Option<f64>`: `Percent(p)` → `p/100 × base` (`None` if `base <= 0`); `FloatOrPercent{is_percent:true}` → same; `FloatOrPercent{is_percent:false}` → `value` verbatim; `Float(f)` → `f`; otherwise `None`. `get_float` returns `None` for `Percent` and for percent-flagged `FloatOrPercent`, but **does** unwrap `FloatOrPercent{is_percent:false}`. The only other `get_abs_value` call sites in the workspace outside `slicer-ir`'s own tests are arachne's own `min_feature_size` and `wall_transition_length`, both against `nozzle_diameter_mm` — copy that shape.
- **The decisive ingestion constraint is the PARSER, not `to_config_map`.** No live-path code constructs a `Percent` or `FloatOrPercent`: the workspace's only non-test constructor of either variant is `parse_percent_default` (`crates/slicer-scheduler/src/manifest.rs`), and its returned `ConfigValue` is **discarded** — `parse_config_field_entry` calls it purely for its validating side effect and stores `ConfigFieldEntry.default` as `v.to_string()`. Every other occurrence in the tree is a consumer (`ConfigView::get_abs_value` / `get_float`, `config_value_to_storage`, the `slicer-macros` guest decoder, `serialize.rs`'s `{p}%` formatter, `check_scalar`). With no producer, `get_abs_value` on a real slice always takes the `Float(f)` arm and passes the value through unscaled. **`ResolvedConfig::to_config_map` does *not* emit only `Bool`/`Int`/`Float`/`String`** — that claim is false as stated: it emits a `ConfigValue::List` for `filament_density`, and it *ends* with `for (k, v) in &self.extensions { m.insert(k.clone(), v.clone()); }`, a verbatim pass-through of a `BTreeMap<String, ConfigValue>` that can carry **any** variant. `outer_wall_line_width` is not a declared `ResolvedConfig` field (zero hits in `crates/slicer-ir/src/resolved_config.rs`), so it routes through exactly that pass-through. **Direction matters:** `extensions` is a *transparent channel* — the packet's ally, not its obstacle. The retype becomes transportable end to end the moment ingestion learns to parse a percent literal into a `ConfigValue`; nothing in `to_config_map` needs to change for that. This packet makes the percent form **declarable and validated**, not yet **producible**. Word the residual deviation row about the parser; do not word it about `to_config_map`, and do not claim D-164 is fully closed in behaviour.
- **WIT boundary:** unchanged. No WIT type, interface or `crates/slicer-schema/wit/**` file is edited. Guest artifacts still go stale because `modules/core-modules/*/src/**` and `crates/slicer-sdk/**` are guest-build inputs.

  - **What this packet originally recorded, and what was wrong with it.** It stated that canonical `meshfix_maximum_extrusion_area_deviation()` returns `scaled<coord_t>(2.)` against PnP's `0.005` and called that "~400× tighter". Two errors. **The ratio was wrong**: `scaled<coord_t>(2.)` is a *scaled* quantity compared against a scaled-area accumulation, so its millimetre equivalent is `2s` (s = canonical's scaling factor) = `2e-6 mm²`; the ~400× came from comparing `2.0` against `0.005` directly, which is a length against an area. The real ratio is ~2500×. **The direction was also wrong**: a larger threshold admits *more* removals, so PnP's `0.005` was ~2500× more **permissive**, not tighter — the opposite of what the bullet claimed, and it inverted the stated consequence.
  - **The defect was not the constant.** `calculate_extrusion_area_deviation_error` (`crates/slicer-core/src/arachne/simplify.rs`) implemented `0.5 * width_at_b * |cross(AB, AC)| / |AC|` and attributed it to canonical `ExtrusionLine.cpp`. That formula is not in canonical. Canonical's `ExtrusionLine::calculateExtrusionAreaDeviationError` computes the difference between the true extrusion area over `A→B→C` and the area of the single segment `A→C` at the length-weighted average width, and has a second branch for near-equal widths. The threshold was therefore gating a quantity it was never chosen for, and "fixing" the constant alone would have been confidently wrong. Both the formula and the threshold are now ported.
  - **What remains true for this packet:** nothing here is in scope. Step 2a's comment correction and Step 5a's second `DEV-###` row are both **already done** — the comments now carry the derivation and `DEV-094` is filed. Step 5a files **one** new `DEV-###` row (the shared absent-key residual), not two. If Step 2a finds the comment already correct, that is the expected state, not a missing precondition.
