# Packet Contract: 184-classic-perimeter-flow-parity

## Goal

Bring `classic-perimeters`' wall-width resolution and wall-spacing arithmetic to OrcaSlicer parity in three ordered moves — retype `outer_wall_line_width` / `inner_wall_line_width` to `float_or_percent` and resolve them through `ConfigView::get_abs_value` with canonical's `0` → `1.125 × nozzle_diameter` auto sentinel; replace the inline width-average wall gap with `slicer_core::flow::line_width_to_spacing`; and gate the `only_one_wall_top` collapse on `min_width_top_surface` the way the arachne half already does. Closes the classic halves of `D-164-WALL-WIDTH-KEYS-NOT-FLOAT-OR-PERCENT`, `D-105-FLOW-NOT-WIRED` (roadmap task `T-052-WIRE-FLOW`), and `D-152-CLASSIC-MIN-WIDTH-TOP-SURFACE-REMAINDER`.

## Scope Boundaries

Touches `modules/core-modules/classic-perimeters/src/lib.rs` (the R2 config-read block at the top of `run_perimeters`, the two `only_one_wall_top` sites, and the inset loop plus gap-fill block inside `emit_walls`), `modules/core-modules/classic-perimeters/classic-perimeters.toml` (three `[config.schema]` entries), the classic-driving tests that hard-assert the old width-average spacing, and the one byte-identical G-code golden those numbers reach. `arachne-perimeters` is not edited: its halves of all three deviations already landed (packets 150/151/152) and this packet mirrors their shape rather than changing them. Config **ingestion** of a real percent value is explicitly not closed — the barrier is the config **parser**, not the IR: no live-path producer of a `ConfigValue::Percent`/`FloatOrPercent` exists in the workspace today (see `design.md` §Architecture Constraints), so the retype makes the percent form declarable and validated but not yet round-trippable; that residual is filed as a new deviation, not fixed here.

## Acceptance Criteria

Assertion hazards, stated once and applying throughout: `type = "float"` is a strict prefix of nothing but `"float"` only because the closing quote is matched — **always quote the closing `"`** in manifest type assertions, or `"float"` will appear to match `"float_or_percent"`. Manifest-section assertions use the windowed form `\[config\.schema\.<key>\][^\[]*<assertion>`, which cannot leak into the next section because `[` terminates the window; any `description` string added by this packet must therefore contain no `[` character.

**Shared test-result guard, stated once.** Every cargo-run criterion below ends in `| rg "^test result" | rg -q "^test result: ok\. [1-9]" || echo "FAIL: …"`. This is a single **positive** match and it is deliberate: the earlier two-stage form `rg "^test result" | rg -v "0 passed"` is unsound, because `test result: FAILED. 1 passed; 1 failed;` contains no literal `0 passed`, so `rg -v` exits `0` and the `|| echo FAIL` never fires — a partially red suite reports success. The `[1-9]` requirement simultaneously rejects a filtered-to-zero run, which prints `test result: ok. 0 passed; 0 failed; N filtered out` and would otherwise sail through the `ok\.` match. All three cases were exercised against real `cargo test` output before this packet was written: a passing narrow run (`ok. 1 passed`) exits `0` silently; a filter matching no test (`ok. 0 passed; 0 failed; 247 filtered out`) prints `FAIL`; a mixed binary (`FAILED. 1 passed; 1 failed`) prints `FAIL`. Each AC here runs exactly one `--test` binary, so exactly one `test result` line reaches the guard; do **not** reuse this form for a multi-binary run, where `rg -q` would match a passing binary and mask a failing sibling.
