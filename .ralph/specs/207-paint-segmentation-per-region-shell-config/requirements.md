## Problem Statement

`execute_paint_segmentation` (`crates/slicer-core/src/algos/paint_segmentation/mod.rs`) resolves the shell parameters it hands to `propagate_top_bottom` with `match region_map.configs.first()`. That is a dead placeholder in production, so every painted slice places shells with `top = 3`, `bottom = 3`, `layer_height = 0.2` and a width of `0.45` regardless of user config. The chain is:

- `RegionMapIR.configs` is an **interned pool**, not a positional list. The region→config mapping is `RegionPlan.config: ConfigId`, resolved by `RegionMapIR::config_for(&RegionKey)`. `docs/02_ir_schemas.md` §"Config Interner Contract (Normative — Packet 91)" already makes `config_for` the *only supported read path*; `configs.first()` violates a rule that was normative before the defect was written.
- `RegionMapIR`'s hand-written `Default` pre-seeds `configs: vec![ResolvedConfig::default()]` so `ConfigId::default()` is always valid.
- `ResolvedConfig`'s hand-written `PartialEq` compares `extensions`, and `run_slice` (`crates/slicer-runtime/src/run.rs`) inserts `slice_has_paint = ConfigValue::Bool(true)` into the config source whenever any object carries `paint_data`. So on exactly the slices where paint segmentation does real work, the effective config never equals `ResolvedConfig::default()`; `intern_config` pushes it at `ConfigId(1)` or above and `configs[0]` is never overwritten.
- Therefore `configs.first()` always returns `Some(placeholder)`, the `None => (3, 3, 0.4, 0.2)` arm is dead, and the in-file comment calling index 0 "the BASE `ResolvedConfig`" is wrong about production.

Consequences are user-visible. `PrePass::ShellClassification` marks N solid layers using the real per-region value — `resolve_shell_counts` (`crates/slicer-runtime/src/slice_postprocess_prepass.rs`) resolves `top_shell_layers` / `bottom_shell_layers` correctly via `config_for` — while paint segmentation projects the face colour down only 3, so a user setting either key to anything but 3 gets a colour/shell mismatch. A non-default `line_width` or `layer_height` changes `propagate_top_bottom`'s `shell_step = spacing + width` and its `0.5 * width` anti-sliver `opening()` radius, moving tool assignment on internal solid infill.

Two secondary defects sit at the same site. `RoleWidthContext` is built with a file-local hardcoded `DEFAULT_NOZZLE_DIAMETER_MM` and `..Default::default()`, which leaves `outer_wall_line_width` at `0.0`, so `resolve_role_width(OuterWall, …)` can never return a per-role width. And the dead `None` arm's `0.4` disagrees with the live `Some` arm's own `0.45`, so the two "defaults" were never the same number.

**This is not greenfield.** Packet 128 / `TASK-253` ("Paint-segmentation shell-depth per-object propagation") already worked this territory. It re-keyed the shell-depth propagation accumulator from a per-layer-global `Option::or` to a `BTreeMap<ObjectId, Option<u8>>` (first-`Some`-wins per object), made the Phase 6/7 `None` arm stamp `object_id` from the painted colour's source object by adding `source_objects: BTreeSet<String>` to the `painted_subsets` value tuple, added `assert_per_object_shell_index_invariant` under `#[cfg(debug_assertions)]`, and added five tests. It explicitly did **not** touch config resolution: `configs.first()`, the `None` arm, `RoleWidthContext`, and `propagate_top_bottom`'s signature were all left alone, and its spec listed no `SlicedRegion` schema change, no guest-WASM change, and no OrcaSlicer parity work. Packet 128 is not reopened or superseded; this packet extends its per-object keying from the shell *index* accumulator to the *config* the shell math reads.

Fixing this to genuine per-config granularity is not a local edit. `propagate_top_bottom` takes scalar shell params for a whole-layer-stack call, there is exactly one production call site, and it sits inside `for ((sname, value), (semantic, painted_mesh, source_objects)) in &painted_subsets` — a map that merges triangles across objects. Per-object values require re-keying that map.

**The correct granularity is per `variant_chain`, not merely per object.** The subset key's `(sem_name, PaintValue)` pair *is* one `RegionKey.variant_chain` element. `execute_region_mapping_inner` (`crates/slicer-core/src/algos/region_mapping.rs`) enumerates each object's paint chains, folds the matching per-semantic config in with `overlay_resolved` — the `paint_config:<semantic>:<key>` overlay produced by `resolve_per_paint_semantic_configs` (`crates/slicer-scheduler/src/config_resolution.rs`) — and calls `intern_config` on the result, storing the returned `ConfigId` on a `RegionPlan` under a `RegionKey` carrying `variant_chain: chain`. `overlay_resolved` is a hand-written per-field diff with explicit arms for `top_shell_layers`, `bottom_shell_layers`, `line_width` and `layer_height` (plus an unconditional `extensions` merge), so those keys are fully overlayable per painted semantic. Resolving from the object's BASE chain would drop every such overlay — DEV-122's own failure mode one axis down.

The per-chain distinction lives in `RegionMapIR.entries` (`HashMap<RegionKey, RegionPlan>`), **not** in the `configs` pool: `intern_config` is a linear-scan dedup on `ResolvedConfig`'s `PartialEq` and hands back the *existing* `ConfigId` for an equal config, so two chains with identical resolved configs share one id. `docs/02_ir_schemas.md`'s interner-contract bullet says the same ("equivalent configs reuse the same `ConfigId`"). That is why the resolver must key on `RegionKey.variant_chain` and read through `config_for` — and why the granularity fixtures must intern configs that genuinely differ.

`execute_paint_segmentation` already contains the `region_map.entries` scan idiom the resolver needs, but **in its Phase-4 block, not at the call site**: Phase 4 filters `region_map.entries` keys on `rk.global_layer_index == global_layer_index && rk.variant_chain == chain_key` (and, for BASE, on `base_chain_key`). The Phase-6/7 loop's own `chain_key` — the one immediately after the `propagate_top_bottom` call — carries the right *value* but filters SliceIR regions (`region.variant_chain == chain_key`), never `region_map`. The resolver reuses the Phase-4 idiom, widened to `object_id`, unpinned from the layer index, and reduced with `min_by_key`; it reuses the Phase-6/7 binding's value by hoisting it. See `design.md` §Controlling Code Paths for the full three-binding inventory.

Note: the in-code comment in `execute_region_mapping_inner` that cites `slicer-scheduler::config_resolution::resolve_paint_overrides` names a function that does not exist — the real symbol is `resolve_per_paint_semantic_configs`. That dangling comment is where earlier drafts of this packet picked up the wrong name. It is **not** fixed here; `region_mapping.rs` is outside this packet's change surface.

## In Scope

- Re-keying `painted_subsets` from `(sem_name, PaintValue)` to `(ObjectId, sem_name, PaintValue)` in `execute_paint_segmentation`'s accumulation loop, so each `propagate_top_bottom` invocation covers exactly one object's painted triangles. The value tuple keeps `source_objects: BTreeSet<String>` (packet 128's field) so the Phase 6/7 `None` arm is untouched; after the re-key it is always a singleton.
- A new per-`variant_chain`, per-object shell-parameter resolver in the same file: locate the `RegionKey` whose `object_id` matches the subset's object and whose `variant_chain` equals the subset's own `chain_key` (`vec![(sem_name, value)]`), resolve it through `RegionMapIR::config_for`, and return the four scalars `propagate_top_bottom` needs. It borrows `resolve_shell_counts`' `config_for`-plus-fallback *shape* but NOT its empty `variant_chain`. Exact signatures and types live in `design.md` §Code Change Surface — this file states the requirement, not the shape.
- Deterministic plan selection at every ladder tier: scan `region_map.entries` for keys whose `object_id` matches and whose `variant_chain` equals the requested chain, and take the minimum by `(global_layer_index, region_id)`. `entries` is a `HashMap`, so the selection MUST be an explicit `min_by_key`, never a first-iteration pick. Because the key is derived *from* `entries`, no separate `contains_key` guard is needed — unlike `resolve_shell_counts`, which constructs a key from a timeline and must therefore check. Absence is expressed by the selection returning `None`, which advances the ladder.
- Replacing the `match region_map.configs.first()` block with a per-subset `resolve_shell_params(&region_map, object_id, &chain_key)` call inside the Phase 6/7 loop, reusing (by hoisting, not duplicating) the `chain_key` binding the loop already constructs for its region filter, and deleting the dead `None => (3, 3, 0.4, 0.2)` arm and the `TODO:` comment that flagged this work.
- Repairing the `RoleWidthContext` construction: `line_width` and `initial_layer_line_width` from the resolved `ResolvedConfig`'s typed fields, and `nozzle_diameter`, `outer_wall_line_width`, `inner_wall_line_width`, `bridge_line_width` read from `ResolvedConfig.extensions` (those four are not typed fields on `ResolvedConfig`; unknown keys route to `extensions`). A local percent-aware helper mirrors `ConfigView::get_abs_value` (`crates/slicer-ir/src/slice_ir.rs`) clause for clause across all seven `ConfigValue` variants — including `FloatOrPercent { value, is_percent }`, which is the variant the WIT config bridge produces and which `outer_wall_line_width` uses upstream. Note that canonical `get_abs_value` deliberately does NOT coerce `Int`; the mirror must not add an `Int` arm. Exact clause list in `design.md` §Code Change Surface.
- A documented two-tier fallback ladder with a single terminal default: painted-chain `RegionKey` → the object's BASE (`variant_chain == []`) `RegionKey` → `top = 3`, `bottom = 3` (matching `resolve_shell_counts`' own fallback) with width and layer height derived from `ResolvedConfig::default()`. Tier 2 is a lookup, not a second default value, so the old two-value disagreement (`0.45` live, `0.4` dead) stays eliminated. AC-N4 pins tier 2, AC-N1 pins tier 3.
- Ten new tests, split across two homes because the five new items are **module-private** and `crates/slicer-core/tests/*.rs` is a separate crate that cannot reach them:
  - a new integration file `crates/slicer-core/tests/paint_segmentation_per_region_shell_config_tdd.rs`, opening with `#![cfg(feature = "host-algos")]` to match the sibling `paint_segmentation_mmu_partition_tdd.rs`, carrying the four ACs that drive the public `execute_paint_segmentation` (AC-2, AC-6, AC-9, AC-N2);
  - a new in-crate `#[cfg(test)] mod shell_config_resolver_tests` in `crates/slicer-core/src/algos/paint_segmentation/mod.rs`, sibling to the existing `driver_v2_tests`, carrying the six ACs that unit-call `resolve_shell_params` / `shell_params_from_config` / `ext_abs_mm` (AC-1, AC-4, AC-5, AC-N1, AC-N3, AC-N4).

  The items stay private — they are not made `pub` to satisfy a test. Rationale and the per-AC homing table are in `design.md` §Test Homing.
- `docs/DEVIATION_LOG.md` DEV-122 closure and the `docs/02_ir_schemas.md` interner-contract sharpening listed in `packet.spec.md` §Doc Impact Statement, plus `cargo xtask check-deviations` regeneration.

- Packet 128's shell-index propagation block, `assert_per_object_shell_index_invariant`, and the Phase 6/7 `None`-arm `object_id` stamping. AC-7 guards them; none is edited.
- Granularity finer than `(object_id, variant_chain)` — i.e. keying on the geometric `region_id` as well. `painted_subsets` accumulates triangles from a 3D mesh, while `region_id` is a per-layer, post-slicing concept, so `(object_id, variant_chain)` is the finest key the data structure supports. **Per-`variant_chain` resolution itself is IN scope** — it is this packet's core decision (user decision, 2026-08-07; see `design.md` §Locked Assumptions "Granularity lock"), because `execute_region_mapping_inner` writes one `entries` row per chain whose `RegionPlan.config` points at a config with the `paint_config:<semantic>:<key>` overlay folded in, and resolving from the BASE chain would silently drop those overlays. (The `ConfigId` itself is deduped across equal configs by `intern_config`'s linear scan; the chain distinction is carried by the `RegionKey` in `entries`, which is what `config_for` resolves through.) Where one object/chain spans several regions or layers with divergent shell configs, the lowest-`(global_layer_index, region_id)` plan wins, as `resolve_shell_counts` takes `timeline.first()`. Recorded as a `[FWD]` in `design.md`.
- The seam-annotation writer packet 206 adds to `execute_paint_segmentation`'s head guards and tail. This packet edits the middle of the same function and must not disturb it.
- `crates/slicer-runtime/src/slice_postprocess_prepass.rs`. `resolve_shell_counts` is the precedent to copy, not a file to change; it is already correct.
- Adding `nozzle_diameter`, `outer_wall_line_width`, `inner_wall_line_width` or `bridge_line_width` as typed fields on `ResolvedConfig`. That would be a `slicer-ir` schema change with a struct-literal blast radius across the workspace; this packet reads them from `extensions`, which is where the macro already routes them.
- Any change to `run_slice`'s `slice_has_paint` injection, to `ResolvedConfig`'s `PartialEq`/`Hash`, or to `intern_config`'s linear-scan dedup. Those three are the *cause* of the placeholder's survival but are all correct as written.
- Hand-editing `docs/07_implementation_status.md`'s Open Deviation Map or `docs/15_config_keys_reference.md`'s `<!-- BEGIN GENERATED: ... -->` tables: both are generated views. **They share one entry point**: `cargo xtask check-deviations` runs `check_deviations::run` and then `gen_config_docs::run` (`xtask/src/main.rs`), and its own `USAGE` text reads "Exit 1 if doc 07 **or doc 15** generated sections are stale"; `docs/15_config_keys_reference.md` likewise states that the CI `check-deviations --check` step "invokes the same `gen-config-docs --check` code path". ## Step Completion Expectations

- The `painted_subsets` re-key and the resolver must land in the **same** step. Re-keying without the resolver changes multi-object projection behaviour for no benefit; adding the resolver without the re-key leaves it unable to name an object.
- Packet 128's six invariant tests (AC-7) must be run immediately after the re-key, before any width work. They are the earliest signal that the `source_objects` singleton assumption holds.
- `cargo xtask build-guests --check` runs after every step that edits `crates/slicer-core/**`. A stale `slicer-core` does not fail typed instantiation — it silently runs the previous geometry code — so a green runtime suite after a `slicer-core` edit means nothing until `--check` is clean.
- Do not run `cargo test -p slicer-core` without `--features host-algos` at any point in this packet. If a run reports a binary count or pass count lower than a previous run, the lower number is the blind one; reconcile before concluding anything.
