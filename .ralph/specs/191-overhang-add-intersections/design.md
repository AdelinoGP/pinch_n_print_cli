## Architecture Constraints

- **Inserted vertices must lie exactly on the original polyline.** Every insertion is a parameterisation of an existing segment (`t ∈ [0,1]` between two existing endpoints, or the intersection of that segment with the previous-layer boundary). No point may move and no new geometry may be introduced — the packet changes *sampling density*, never shape. `AC-7` asserts a `1e-4 mm` perpendicular tolerance.
- **Wall-loop closure is an invariant, not a convention.** `ExtrusionPath3D::is_closed()` compares `points.first().xy == points.last().xy`, and `crates/slicer-gcode/src/emit.rs` carries a defensive check that treats an unclosed wall as evidence "a wall mutator dropped the closing repeat". A geometry channel that can open a loop makes that check fire from outside the emitter's blame radius, which is why `apply_to` — not the module — enforces closure for `ExtrusionRole::is_loop()` roles (`AC-N1`).
- **Mutation ordering is part of the contract.** `apply_to` iterates `for op in self.merge_ops` in submission order. `SetPathPoints` must precede the same entity's `SetPointSpeedFactors`, because packet 189's profile branch length-checks against the entity's *current* point count. Documented in `docs/02_ir_schemas.md` §IR 10 by this packet.

- Coordinate units: **1 unit = 100 nm** (10⁻⁴ mm), NOT 1 nm like OrcaSlicer. Divide OrcaSlicer constants by 100. Use `Point2::from_mm(x, y)` or `mm_to_units()` at every mm↔unit boundary. Full porting checklist in `docs/08_coordinate_system.md`.
- **…but this module works entirely in millimetres, and that is the trap here.** `Point3WithWidth.x/.y/.z/.width` are millimetres. Canonical's `estimate_points_properties` works in *unscaled* millimetres too (its `unscaled_prev_layer` name says so), so the `2.f` and `4.0f` length gates and the `0.25`/`0.5`/`3 *` factors transfer as-is with **no** division by 100 and **no** `mm_to_units()`. The snippet is present because the packet adds geometry code; the concrete instruction it carries is *do not convert*, and a reviewer should check for a spurious `mm_to_units` rather than for a missing one.
- **No schema/version constant is bumped.** `CURRENT_LAYER_COLLECTION_IR_SCHEMA_VERSION` moved in packet 189; `CURRENT_PERIMETER_IR_SCHEMA_VERSION` moved in packet 193; adding a WIT variant case does not move an IR schema version, and no test hard-asserts one here.
- **Every distance this packet reads is signed and already `+ boundary_offset`-normalised, and that contract lives in exactly one place.** `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract" is normative; packets 190 and 191 both cite it and neither restates it. Three predicates in §Code Change Surface depend on it and would silently misbehave against an unsigned or un-offset value: the XOR crossing test (`> boundary_offset + EPSILON`) degenerates, the outer proximity test's `> -boundary_offset` half becomes unreachable, and `a0`/`a1`'s `+ 3 × boundary_offset` shifts both inserted vertices along the segment on every evaluation. **This was a live contradiction across the packet set for a round** — packet 190's original draft declared an *unsigned* point-to-segment minimum while this packet's every predicate reads canonical's signed value — and 193 exists in part to resolve it once rather than three times.
- **This module becomes a geometry mutator, which departs from ADR-0031's Decision text; `ADR-0053` is the superseding record and an amendment row is owed.** See §"ADR-0031 departure: the amendment this packet owes" below. Disclosure alone is not an amendment, and an earlier revision of this packet disclosed the departure while filing nothing.

## Code Change Surface

- **Selected approach.** Compute the insertions in the guest, where packet 190 already holds the `speed_sections` table and each point's prepass-stamped `overhang_distance_mm`, and ship the whole rewritten point list through one additive mutation. **Under option (C) the guest does NOT hold "the previous layer's boundary segments"** — an earlier revision of this sentence said so, and that was the option-(B) design; the crossing branch must source its boundary polyline consistently with packet 193's stamping site (see §Open Questions) rather than assume packet 190 left one lying around. The alternative shapes are rejected below.
- **Exact additions to `modules/core-modules/overhang-classifier-default/src/lib.rs`:**
  - `fn segment_intersections(seg: ((f32,f32),(f32,f32)), boundary: &[(f32,f32,f32,f32)]) -> Vec<(f32,f32)>` — in-module segment-segment intersection. No host service provides one: `slicer_sdk::host` exposes `clip_polygons`, `offset_polygons`, `simplify_polygon`, `medial_axis`, `generate_arachne_walls`, `raycast_z_down`, `surface_normal_at`, `object_bounds`, the logging family and `now_us` — nothing line-level. Must return intersections ordered along the segment and must break ties deterministically (`total_cmp`), per `DEV-093`'s standing warning about non-determinism.
  - `fn min_distance_from_sections(sections: &[(f32, f32)], original_speed: f32) -> f32` — smallest section distance whose speed is `<= original_speed`; `-1.0` when none. Canonical's `infinity()` + `found` flag collapses to this.
  - `fn insert_extended_points(points: &[Point3WithWidth], distances: &[Option<f32>], boundary: &[(f32,f32,f32,f32)], flow_width: f32, min_distance: f32) -> (Vec<Point3WithWidth>, Vec<Option<f32>>)` — **note the `Option`**: the carrier is `Point3WithWidth.overhang_distance_mm: Option<f32>` (packet 193), not an `f32`, and an earlier draft of this packet typed the slice as `&[f32]`, silently assuming a total value. **The `None` case is real and reachable under option (C)**, and its two triggers are packet 193’s to define, not this packet’s: `193`’s `AC-N1` stamps `None` for **a layer with no previous layer (the first layer)** and for **a region whose previous-layer slice boundary is empty**. The first is unreachable here (packet 190 skips `layers[0]` in the caller, pinned by its `AC-8`); **the second is the live case and the one `AC-N3` must be grounded on.** **Do NOT write "i.e. the first layer".** Packet 190 skips `layers[0]` in the *caller*, pinned by its `AC-8` ("no speed mutation for any entity on that layer"), so layer 0 never reaches this function at all; the first-layer equation was asserted as settled fact at four sites in this packet for a round and it is not the contract. **Nor is it "the previous layer contributed no `OuterWall` segments"** — that framing belonged to the option-(B) in-module scan and dies with it, because under (C) nothing in this module ever looks at the previous layer's walls. `AC-N3` now rests on 193's second `AC-N1` trigger alone — **a region whose previous-layer *slice* boundary is empty**, which is a prepass fact about slice geometry and not a finalization-time fact about walls. **Unwrap rule, normative — and it is packet 193's rule, not this packet's:** `193`'s `AC-N1` enumerates the forbidden substitutes and is normative here. A `None` distance means "not measured", and every gate that consumes it must take the **no-insertion** path — the same path a failed gate takes. Concretely: a segment either of whose endpoint distances is `None` is skipped by both the crossing branch and the segmentation branch, and a candidate whose interpolated distance derives from a `None` endpoint is discarded rather than admitted. Never substitute `0.0`, `f32::MAX` or `-1.0` for a `None`: `0.0` would read as "exactly on the boundary" (and under (C) the value is *signed*, so `0.0` is a legitimate in-range measurement, not a sentinel), and `-1.0` collides with `min_distance`'s own not-found sentinel. Returns the densified point list **and** its parallel distance list, so the caller can run packet 190's `calculate_speed` over the new vertices without re-deriving the originals.
    - `boundary_offset = 0.5 * flow_width`; `min_spacing = flow_width * 0.25`. **`flow_width` is the point's own `width`** — the same width packet 193 normalised the carrier against, per that packet's §"The signedness contract". Deriving a second, independent width here silently decouples these predicates from the distances they threshold.
    - Crossing branch: XOR of `(d_prev > boundary_offset + EPSILON) != (d_next > boundary_offset + EPSILON)`; one vertex per intersection with the boundary polyline; the inserted vertex's distance is assigned **`boundary_offset`** verbatim; two-sided `min_spacing` test against both neighbours. **This predicate only behaves as canonical does against a *signed* `d`** — for two endpoints on the same side of the wall but straddling the offset, an unsigned magnitude cannot flip it. Packet 193 guarantees the signedness; see §Architecture Constraints.
    - Segmentation branch: outer proximity test `d_curr > -boundary_offset && d_curr < boundary_offset + 2.0` (**its negative half is unreachable against an unsigned carrier** — the second reason 193's signedness contract is load-bearing here), then `min_distance > 0 && (|d_curr| > min_distance || |d_next| > min_distance) && line_len >= 2.0` **or** `min_distance <= 0 && line_len > 4.0`; `a0 = clamp((d_curr + 3*boundary_offset)/line_len, 0, 1)`, `a1 = clamp(1.0 - (d_next + 3*boundary_offset)/line_len, 0, 1)`, `t0 = min(a0,a1)`, `t1 = max(a0,a1)`; each candidate's distance is **linearly interpolated between the segment endpoints at its own `t`** — see §"Under option (C): interpolate, do not re-measure" below — and passes the same admission test `(|d| > min_distance) || (min_distance <= 0)` plus the `min_spacing` filter.
    - Interpolated vertex fields: `x`, `y` from `t`; `z` from the segment endpoints; `width` and `flow_factor` linearly interpolated between the endpoints; `overhang_quartile` inherited from the endpoint whose distance is closer to the inserted vertex's (an inserted vertex must not become `None` and silently drop out of the packet-190 gate); `dist_to_top_mm` interpolated; **`overhang_distance_mm` interpolated** — required by ADR-0053 §Consequences ("Every synthetic point must carry an interpolated `overhang_distance_mm`; leaving it at the struct default silently zeroes the field the segmentation gate reads"). Omitting it is the highest-consequence silent defect in this packet: `Point3WithWidth`'s struct default is not a legitimate distance, and every synthetic vertex would read as sitting exactly on the boundary.

- **Under option (C): interpolate, do not re-measure — and record the divergence.** Canonical's `estimate_points_properties` genuinely re-measures each candidate against `unscaled_prev_layer`. This module cannot: it has no boundary geometry (see §Architecture Constraints), and nothing upstream stamped a point that did not exist. It therefore interpolates `overhang_distance_mm` linearly between the two segment endpoints at the candidate's `t`. The error is bounded by the segment's own curvature relative to the previous-layer boundary and is exactly zero where the boundary is locally straight — but it is a real algorithmic divergence with a different error profile, ADR-0053 §Decision item 3 names it as such, and `packet.spec.md` §Doc Impact Statement requires a `DEV-###` row for it (id re-derived at the moment of writing). The **crossing** branch is unaffected: canonical assigns the intersection vertex `boundary_offset` verbatim rather than measuring it, so that half of the algorithm is byte-for-byte canonical under (C).
  - `run_finalization` — after building the per-point distances, call `insert_extended_points`; when the returned list is longer than the original, emit `EntityMutation::SetPathPoints(new_points)` **then** `EntityMutation::SetPointSpeedFactors(new_factors)`; when it is the same length, emit only the profile exactly as packet 190 does.
- **Exact additions to the channel:** one variant case, one `use` list entry in the WIT, one enum case in `slicer_sdk::traits::EntityMutation`, one `apply_to` branch with the empty/closure rejections, and one match arm each in `host.rs`, `dispatch.rs` and `slicer-macros/src/lib.rs`.
- **Rejected alternative 1 — do the insertion at emit time in `crates/slicer-gcode/src/emit.rs`.** Would avoid the geometry-mutation channel entirely. Rejected: the emitter has no previous-layer boundary, no `speed_sections` table and no `min_distance`; supplying them would mean carrying all three through the IR, which is strictly more surface than one additive mutation case. It would also put a parity-critical geometry algorithm downstream of the per-role simplification that thins points, i.e. densify-then-thin in the wrong order.
- **Rejected alternative 2 — push a replacement entity and re-order.** Expressible today via `insert_entity_at` + `set_entity_order` with no new WIT. Rejected: it changes `entity_id`, which travel anchors (`TravelMove.entity_id`) and packet 189's `speed_profiles` rows are both keyed by, so every anchor into the replaced entity would dangle. `docs/02_ir_schemas.md` records that anchoring-by-id exists precisely so "inserting or sorting entities cannot invalidate anchors" — this alternative would defeat that.
- **Rejected alternative 3 — a `SplicePathPoints(index, Vec<Point3WithWidth>)` splice mutation.** Smaller payloads. Rejected: a splice is order-dependent against other splices on the same entity and makes the closure invariant awkward to check; a wholesale replacement is idempotent, trivially checkable, and matches how canonical returns a fresh `extended_points` vector rather than patching in place.
- **`max_line_length` is deliberately not ported.** `estimate_extrusion_quality` passes `-1`, disabling it on the G-code path.

## Data and Contract Notes

- **The distance contract is packet 193's, cited and never restated.** `Point3WithWidth.overhang_distance_mm` is the **signed** perpendicular distance in millimetres from the point to the **previous layer's slice boundary**, already normalised by `+ boundary_offset` where `boundary_offset = 0.5 × width` of that point. The single normative statement is `.ralph/specs/193-overhang-distance-prepass-carrier/design.md` §Data and Contract Notes §"The signedness contract", which grounds it in canonical's `estimate_points_properties` (`OrcaSlicerDocumented/src/libslic3r/GCode/ExtrusionProcessor.hpp`) — `distance = distance_from_lines_extra<SIGNED_DISTANCE>(…) + boundary_offset`, instantiated `<true, true, true, true>` on the G-code speed path so both `SIGNED_DISTANCE` and `PREV_LAYER_BOUNDARY_OFFSET` are true. **Consumers read the value as already-normalised** and must not re-derive or re-add `boundary_offset` in order to *interpret* it; they do need `boundary_offset` as a literal in their own predicates, and there the rule is 193's: `0.5 × ` the point's own `width`. **Do not paraphrase any of this into this file** — a paraphrase is precisely how 190 came to declare an unsigned minimum while this packet's predicates read a signed offset value.
- **IR/manifest contracts.** `SetPathPoints` replaces `path.points` wholesale. `apply_to` rejects an empty vector and rejects a list that breaks the closing repeat when `ExtrusionRole::is_loop()` is true for the entity's role. It does **not** check that the new points lie on the old polyline — that is the producer's obligation and `AC-7`'s assertion, because a general geometry channel should not encode one consumer's parity rule.
- **Ordering.** `SetPathPoints` then `SetPointSpeedFactors`, same entity, same `merge_ops` sequence. Packet 189's profile branch length-checks against the entity's current point count, so the reverse order is rejected — and, at the WASM boundary, rejected *silently*: `crates/slicer-wasm-host/src/dispatch.rs` swallows `modify_entity`'s `Err` with `log::warn!`. Get the order right in the producer; do not rely on a fatal.
- **WIT boundary.** `set-path-points(list<point3-with-width>)` is additive on an existing `variant`, but `point3-with-width` is **not currently imported** by `world-finalization` (its `use slicer:types/geometry.{…}` names only `extrusion-path3d, extrusion-role`). Both edits are required in the same change or the WIT does not parse. `crates/slicer-schema/wit/deps/types.wit` already defines the record, so no type is added — only an import.
- **Determinism/scheduler constraints.** `[hints] layer-parallel-safe = false` already holds and must stay false. `segment_intersections` must order its results deterministically along the segment; `DEV-093` records a pre-existing whole-pipeline non-determinism and this packet must not add to it. No `[ir-access]`, `[claims]` or `[stage]` entry changes, so no DAG edge moves.
- **Payload size.** A `SetPathPoints` payload is a full point list per mutated entity, crossing the WIT boundary once per entity per layer. That is larger than the two scalars the pre-existing mutations carry; it is bounded by the entity's own vertex count and only paid for entities that actually gained vertices (the module must emit no `SetPathPoints` when the list is unchanged — `AC-N2`).

## Locked Assumptions and Invariants

- **Insertions never move geometry.** Every inserted vertex lies on the original polyline within `1e-4 mm`. Locked; `AC-7` defends it.
- **Wall-loop closure survives every geometry mutation.** Locked at the `apply_to` boundary; `AC-N1` defends it.
- **Geometry mutation precedes the profile for the same entity.** Locked by packet 189's exact-length rule; `AC-2` defends it.
- **Insertion is strictly inside packet 190's gates.** Zero overhang speeds, or `enable_overhang_speed = false`, or the first layer ⇒ no mutation of any kind. Locked; `AC-9` defends it. Reversible entirely through config.
- **An inserted vertex inherits a non-`None` `overhang_quartile`.** Otherwise it would fall out of packet 190's `overhang_quartile.is_some()` gate and be assigned factor 1.0, producing a speed *spike* exactly where the port meant to add resolution.
- **A `None` distance takes the no-insertion path, everywhere.** The carrier is `Point3WithWidth.overhang_distance_mm: Option<f32>` (packet 193), and `None` is reachable. **Its two triggers are packet 193's `AC-N1` to define, not this packet's to invent:** a layer with no previous layer, and **a region whose previous-layer slice boundary is empty**. (**Not "i.e. the first layer"** — packet 190 skips `layers[0]` in the caller, pinned by its `AC-8`, so layer 0 never reaches this code. **And not "the previous layer contributed no `OuterWall` segments"** — that framing belonged to the option-(B) in-module scan, which option (C) deletes; under (C) this module never looks at previous-layer walls at all. `AC-N3`'s fixture must be re-grounded on 193's second trigger, the empty previous-layer *slice* boundary.) Every gate that consumes a distance must treat `None` exactly as it treats a failed gate: a segment either of whose endpoint distances is `None` is skipped by the crossing branch **and** the segmentation branch, and a candidate whose interpolated distance derives from a `None` endpoint is discarded rather than admitted. `0.0`, `f32::MAX` and `-1.0` are all forbidden substitutes — **packet 193's `AC-N1` enumerates exactly these three and is normative for this rule**; do not re-litigate the list here. `0.0` reads as "exactly on the boundary" and, because the carrier is *signed*, is a perfectly legitimate measured value rather than an out-of-band marker; `-1.0` is likewise a legitimate signed measurement *and* collides with `min_distance`'s own not-found sentinel; either would route such an entity into the `min_distance <= 0 && line_len > 4.0` disjunct and insert vertices where nothing was ever measured. `f32::MAX` satisfies `|d| > min_distance` and routes it into the other disjunct. **Defended by `AC-N3`, whose fixture must carry `line_len > 4.0` mm and `min_distance <= 0`** — with no stamped distance the crossing branch cannot fire at all, so the segmentation gate is the only discriminator, and a short segment or a positive `min_distance` would let a coerced implementation pass. Until round 3 this rule existed in exactly one prose sentence in §Code Change Surface, with no test, no AC and no entry here — and its failure mode is silent.
- **Canonical constants are not tunables.** `0.5 * flow_width`, `flow_width * 0.25`, `3 *`, `2.0`, `4.0` stay literals with provenance comments; no config key is added.

## Risks and Tradeoffs

- **`a1`'s leading `1.0 -` is the single most likely defect.** It is asymmetric with `a0`, it is easy to "tidy up" into symmetry, and a symmetric version still produces plausible-looking output. `AC-5` requires a fixture where **`(next.distance + 3 * boundary_offset) / line_len != 0.5`** so the asymmetry is actually exercised. **Not `a0 != 1.0 - a1`**, which an earlier draft specified here and in Step 1: writing `B = (next.distance + 3*boundary_offset)/line_len`, the correct `a1 = clamp(1 - B)` and the symmetric guess `clamp(B)` coincide exactly when `B == 0.5`, so that condition reduces to `curr.distance != next.distance` and is neither necessary nor sufficient — a fixture satisfying it can still pass under both implementations.
- **Point-count changes are invisible to whole-output G-code diffing.** `DEV-093` records that two runs of the same unmodified binary already differ by ~100-160 lines of exactly the "loops appear/disappear" shape, so byte comparison cannot attribute this packet's effect. Every criterion here is therefore structural or unit-level.
- **The `p0`/`p1` `min_spacing` asymmetry is an upstream quirk the port inherits or fixes.** Either choice is defensible; an undocumented choice is not. `packet.spec.md` §Doc Impact Statement requires one `DEV-###` row either way.
- **Cost.** `segment_intersections` is O(segments × boundary-segments) on top of packet 190's O(points × boundary-segments) distance scan, and it runs only for segments that pass the crossing predicate. Packet 190 authorises changing the module's `estimated-ms-per-layer` hint in-packet, so **re-read its current value rather than assuming `10`**; if this packet's additions make it wrong again, update it here rather than leaving a known-wrong scheduler input.
- **A larger `EntityMutation` payload crosses the WIT boundary per mutated entity.** Bounded by vertex count, and paid only where vertices were actually added.

## Option (C) is the ruling, and this section records how it was worked through

**Not a contingency any more.** The maintainer ruled **option (C)** — a prepass-stamped continuous `overhang_distance_mm` on `Point3WithWidth`, delivered by packet `193-overhang-distance-prepass-carrier`. `docs/adr/0053-overhang-emission-time-speed-sections.md` is the decision record, and its Scope paragraph names *this* packet explicitly ("Scope covers packets 190 *and* 191 … both are therefore in scope here"), which is what this section previously warned would otherwise not be true. The three places this packet changes shape are each **worked through in the body above**, not left hypothetical:

1. **"Each segmentation candidate re-queries its own distance via `distance_to_prev_boundary`" — RESOLVED.** There is no query and no such function. §Code Change Surface now specifies **linear interpolation of `overhang_distance_mm` between the segment endpoints** at the candidate's `t`, with the divergence from canonical (which genuinely re-measures) written up in §"Under option (C): interpolate, do not re-measure" and carrying a `DEV-###` row in `packet.spec.md` §Doc Impact Statement. The crossing branch is unaffected — canonical assigns `boundary_offset` verbatim there rather than measuring.
2. **The interpolated-field list was missing `overhang_distance_mm` — RESOLVED.** §Code Change Surface now names it, with ADR-0053 §Consequences' warning attached ("leaving it at the struct default silently zeroes the field the segmentation gate reads"). `AC-N4` gates it structurally, because a defaulted field produces plausible-looking output.
3. **Step 0's `rg -q "fn distance_to_prev_boundary"` probe would have FAILED and halted this packet on a genuinely-landed prerequisite — RESOLVED.** `implementation-plan.md` Step 0's probe now asserts the *field and its stamping site* rather than a helper symbol: under (C) packet 193 delivers **data, not an API**, so there is no function name to probe for. Packet 190's own Step 0 probe was corrected the same way.

`distances: &[Option<f32>]` survives (C) unchanged — a stamped value is `Some`, an unmeasured one is `None` — so the normative unwrap rule in §Locked Assumptions holds either way. What does **not** survive is that rule's old *justification*: "the previous layer contributed no `OuterWall` segments" describes a mechanism the tree will not contain. It has been re-grounded, everywhere it appeared, on packet 193's `AC-N1` — which is the only artifact entitled to define when `overhang_distance_mm` is `None`, and which names two triggers: a layer with no previous layer (unreachable here, since packet 190 skips `layers[0]`) and **a region whose previous-layer slice boundary is empty** (the live case).
